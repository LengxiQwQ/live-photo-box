# 1. 当前路线的最终结论

正式核心架构：

```text
Source Media
    ↓
Source Inspector
    ↓
Source Extractor
    ↓
Source Protocol Cleaner
    ↓
Media Converter
    ↓
NeutralMediaBundle
    ↓
OutputProfile
    ↓
Target Protocol Writer
    ↓
Target Protocol Validator
```

产品调用关系：

```text
GUI / CLI
   ↓
C# Core — Control Plane / Orchestration
   ↓
LivePhotoBox.Native — Result-affecting Data Plane
   ↓
Project-owned protocol/container truth
+
Evidence-approved third-party native media primitives
```

核心思想：

> **Source → Neutral → Target，而不是 Vendor A → Vendor B 的 N×N 转换。**

以后新增来源协议，只扩 Source 侧。
以后新增目标协议，只扩 Target 侧。
Target Writer 不应依赖“来源原来是哪一家”。

# 2. 唯一正式阶段顺序

```text
P0   Rebuilt-only Runtime Closeout                    ✅ Completed
 ↓
P1   Source Inspector Reliability                     ← CURRENT
 ↓
P2   Extractor Reliability
 ↓
P3   Cleaner Reliability
 ↓
P4   Native Media Toolchain Evaluation & Foundation
 ↓
P5   Converter Reliability
 ↓
P6   Neutral Pipeline Closeout
 ↓
P7   System Torture / Malformed / Regression Campaign
 ↓
P8   Split / Merge Product Foundation
 ↓
P9   Target Protocol Writers + Target Protocol Validators
 ↓
P10  Repair
```

P7 不是“到 P7 才开始真实样本测试”。

从 P1 开始，所有**影响媒体结果或协议 correctness** 的阶段都应在当场完成：

```text
implementation
→ automated tests
→ real media samples
→ malformed / negative cases
→ regression
```

P7 负责把前面持续积累的验证提升为系统级、攻击性、组合式压力验证。


纯 build/platform/diagnostic infrastructure 不需要为了形式主义强行绑定真实照片；它必须提供与自身风险匹配的 build、dependency、platform、fault-injection 等证据。

```text

→ 最后统一跑测试
```

# 4. 架构职责边界

## 4.1 C# Core 负责

```text
orchestration
request/result models
workspace
progress
cancellation
file lifecycle
queue/batch
error mapping
product flow
target selection
output naming / destination
product-level publish orchestration
Native interop
```

## 4.2 LivePhotoBox.Native 负责

```text
binary/container structure
JPEG / TIFF / EXIF / XMP / MakerNote
HEIF / HEIC structure
ISO-BMFF / MOV / MP4 structure
SEF
vendor protocol semantics
source inspection
exact ranges
exact extraction
source protocol cleaning
result-affecting image/video processing
target protocol structured writing
trusted low-level structural parsing/validation primitives
platform-level safe file primitives where appropriate
```

底层 `create → validate → atomic replace/publish` primitive 可以位于 Native；这不与 Core 的产品级 output publishing orchestration 冲突。

## 4.3 UI-only 能力不强制进入 Native

例如：

```text
thumbnail
preview
display resize
preview cache
renderer
```

判断标准：

> **它是否影响正式处理产物。**

---

# 5. Native 的真正目标：统一能力层，不是重写世界

目标：

> **正式媒体处理不依赖外部 media executable，同时项目继续掌握 Live/Motion Photo 的协议与容器语义，并按证据复用成熟 native media primitives。**

以下只是**候选例子，不是最终选型**：

```text
JPEG codec / lossless transform:
  libjpeg-turbo or equivalent

HEIC pixel codec:
  libheif-based stack / platform codec / equivalent

Video codec/transcode:
  Media Foundation / minimal FFmpeg libav* / focused backend / equivalent

Color management:
  lcms2 / backend capability / equivalent, only if needed
```

允许：

```text
dynamic linking
static linking
controlled native dependency DLLs
platform-specific approved backends behind one contract
```

最终技术组合必须由 P4 在执行时根据：

```text
correctness
real-device compatibility
preservation
security
license/distribution
maintenance
performance
memory
binary size
portability
build reproducibility
```

决定。

第三方 library 只能承担成熟通用 media primitive，不能成为 Live/Motion Photo protocol truth source。

# 7. Neutral Media Contract

永久规则由：

```text
12-Neutral-Media-Contract.md
```

定义。

最关键原则：

> **Target Writer 只根据 NeutralMediaBundle + OutputProfile 生成目标协议，不得重新依赖 Source vendor private protocol 决定输出。**

`SourceProvenance` 可以用于：

```text
diagnostics
history
debug/evidence
```

但不能成为目标 Writer 的隐藏 vendor branch。

---

# 8. Target profile vocabulary

为避免重复模型，Roadmap 统一使用以下三个概念：

```text
TargetProtocol
= 目标厂商/协议 identity，例如 Apple / Google / Samsung / Huawei / vivo / OPPO

MediaFormatRequirement
= 图片容器、视频容器、codec、fps 等通用媒体要求

OutputProfile
= TargetProtocol
  + MediaFormatRequirement
  + 目标协议版本/选项/能力要求
```

Roadmap 不再使用 `TargetProfile` 作为另一套并行概念。

当前已有 `MediaFormatRequirement` 可继续演进；不要因为本文而机械新增重复模型。

---

# 9. Target-side 闭环

```text
NeutralMediaBundle
↓
OutputProfile
↓
Target Protocol Writer
↓
flush / close
↓
reopen final output from disk
↓
Target Protocol Validator
↓
independent external/reference evidence where useful
↓
real device acceptance
↓
Publish
```

## 9.1 Validator 的“独立”是什么意思

独立的是：

```text
validation control flow
observed-facts reconstruction
target conformance rules
decision/result
```

而不是强制复制一整套底层 parser。

允许 Writer 与 Validator 共享：

```text
已经被独立测试证明可靠的
JPEG / TIFF / XMP / HEIF / ISO-BMFF / SEF 等低层结构 parser/primitives
```

禁止：

```text
Validator 读取 Writer 内存状态
Validator 读取“刚才写过哪些字段”的 operation flags
Writer 返回 success → Validator 直接 PASS
Validator 复用 Writer 的目标正确性判断
```

Validator 必须重新从磁盘打开最终产物，重新解析 observed facts，再用独立的 target conformance rules 判定。

外部工具/系统 decoder/真实设备是额外独立证据，不替代项目自己的 Validator。

类似：

```text
UI index
↓
UI Adapter
↓
TargetProtocol + MediaFormatRequirement
↓
OutputProfile
↓
Core
```

原因：

> **Core 不应该知道“下拉框第 3 项是什么”。**

# 11. P8 与 P9 的边界

P8 负责：

```text
Split product flow
Merge input discovery/preparation
Neutral preparation
typed target/output selection
queue/batch/progress/cancel
GUI/CLI/Core wiring
Writer orchestration boundary
```

P8 **不负责**正式重写厂商 Target Writer。

正确迁移例子：

```text
Split single
Split batch
Merge single input preparation
Merge batch orchestration
typed OutputProfile selection
CLI/GUI error/progress integration
```

如果当前 production 仍有已有 Target Writer：

```text
P8 可以通过明确 adapter/boundary 暂时调用它
```

但 P8 不应：

```text
把该 Writer 当作新 Writer 架构已经完成
大规模重写目标协议结构
因为“清旧逻辑”而在没有 P9 replacement 的情况下删除仍是合法 production writer 的实现
```

每个旧 Target Writer 的真正替换/删除时机：

```text
P9 新 structured Writer
→ Target Validator
→ independent/device evidence
→ product cutover
→ 删除对应旧 Writer
```

任何阶段都禁止 silent fallback。

# 12. P10 Repair 原则

Repair 是独立副功能，不阻塞主：

```text
Split
Merge
Target Writer
Target Validator
```

Repair 只处理：

```text
已知
可诊断
修改范围可解释
结果可验证
```

的问题。

默认不覆盖原文件。

# 17. 最终工程目标

最终目标不是：

```text
所有东西自己写
所有代码都在 C++
仓库没有第三方库
所有平台共用 UI
```

最终目标是：

> **Live Photo Box 自己掌握 Live/Motion Photo 的协议与容器语义；可靠复用经证据批准的媒体 primitive；把任何支持来源安全转成 NeutralMediaBundle，再以结构化、可验证、可扩展的方式生成目标协议。**

总体架构默认冻结。

从现在开始：

> **执行 > 无证据的总体重设计。**

## AI 执行硬规则

1. **先读当前 HEAD，再动代码。** Roadmap 定义目标、边界和验收，不替代当前实现事实；文档中记录的审计点必须在执行时重新核对。
2. **只执行当前阶段。** 未满足当前 Phase Gate，不提前实现后续阶段，不以“顺手整理”为理由扩大范围。
3. **验证证据必须与风险匹配。** 任何影响媒体产物、协议 correctness、兼容性或 preservation 的 Process，都必须同时具备代码证据、自动化测试和真实媒体样本证据；纯 build/platform/diagnostic infrastructure 使用与其风险匹配的 build smoke、dependency report、fault injection、platform proof 等证据。真实媒体样本不是 P7 才开始。
4. **测试失败必须可定位。** 错误应携带阶段、能力、关键输入事实、失败类别和技术原因；CLI/产品层必须能把核心错误清楚呈现。
5. **Production runtime 不恢复外部媒体 CLI 子进程依赖。** `ffmpeg.exe`、`ffprobe.exe`、`ExifTool.exe`、`jpegtran.exe`、`heif-enc.exe`、`heif-dec.exe`、`magick.exe` 等可以用于研究、测试和独立验证，但不能重新成为正式处理后端。
6. **第三方 C/C++ 媒体库是候选能力，不是预先锁定的架构承诺。** 是否采用、如何裁剪、静态或动态链接、平台 backend 组合等，由 P4 的实际证据决定；不得因为 Roadmap 举例提到某个库就机械引入，也不得为了“全部自研”重复实现成熟 codec。
7. **C# 是 Control Plane；Native 是 result-affecting Data Plane。** 产品级命名、目标目录、队列、UI/CLI orchestration 由 Core 管理；底层临时文件、原子 replace/publish 等事务 primitive 可以保留在 Native，但应置于明确的 platform/filesystem boundary。UI-only 的缩略图、预览、显示缩放和缓存不强制进入 Native。
8. **不猜协议事实，也不猜 Writer 写入位置。** 字符串命中、固定 offset、同文件名、magic number、`hit + N` 只能用于 research/candidate/evidence，不能直接成为 destructive authority 或 production Writer authoritative write location。
9. **源文件默认不原地覆盖。** Destructive/repair/write 流程优先使用新文件或安全临时输出；只有在结构与媒体验证通过后，才进入正式 publish。失败或取消不得留下“看起来成功”的半成品。
10. **所有 Done 都由证据宣布。** 代码存在、API 返回成功、文件能打开、播放器能播放，都不能单独证明阶段完成。
11. **当前 Roadmap 不主动修改用户可见文档。** README、CLI 用户手册、商店/Release 用户说明等，只有用户明确要求时才更新。
