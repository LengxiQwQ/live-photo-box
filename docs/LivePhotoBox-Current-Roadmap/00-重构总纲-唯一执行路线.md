# Live Photo Box 重构总纲 — 唯一执行路线 V4.0

> **Document role:** Master Roadmap / 唯一阶段调度与长期架构权威  
> **Audience:** AI coding agents / maintainers  
> **Status:** Active / Architecture baseline  
> **Current delivery platform:** Windows x64  
> **Future architectural targets:** WebAssembly first; Linux / macOS optional and deferred  
> **Architecture rule:** 当前不为未来平台牺牲 Windows correctness；同时从现在开始，不允许把本可平台无关的协议/容器/媒体语义无理由写死到 Windows。  
> **Protocol authority:** `docs/实况照片协议分析文档/` 文件夹内的全部文档，以及后续由真实设备/样本验证补充的协议事实。  
> **User-facing documentation:** 除非用户明确要求，本 Roadmap 不主动修改 README、商店文案、Release 用户说明或 CLI 用户手册。

# 1. 最终产品架构

正式媒体主线：

```text
Source Media
    ↓
Source Inspector
    ↓
Source Extractor
    ↓
Source Protocol Cleaner
    ↓
Media Converter
    ↓
NeutralMediaBundle
    ↓
OutputProfile
    ↓
Target Protocol Writer
    ↓
Target Protocol Validator
```

产品调用关系：

```text
GUI / CLI
   ↓
C# Core — Control Plane / Product Orchestration
   ↓
Stable C ABI
   ↓
LivePhotoBox.Native — Result-affecting Data Plane
   ↓
┌──────────────────────────────┐
│ Portable Native Core         │
│ protocol/container/metadata  │
│ neutral semantics/validators │
└──────────────┬───────────────┘
               │
       Backend Contracts
        ┌──────┴──────┐
        │             │
   Media Backend   Platform Backend
        │             │
  codec/color     file I/O/publish
```

永久核心思想：

> **Source → Neutral → Target，而不是 Vendor A → Vendor B 的 N×N 转换。**

新增来源协议只扩 Source 侧。  
新增目标协议只扩 Target 侧。  
Target Writer 不根据“来源原来是哪一家”决定目标结构。

# 2. 平台战略

## 2.1 当前产品事实

当前只要求：

```text
Windows x64
= first-class production target
= 当前 P0–P10 的正式交付、性能与兼容性验收平台
```

Roadmap **不要求现在实现**：

```text
Linux GUI
Linux CLI
macOS GUI/CLI
Web 产品
跨平台 C# Core
```

## 2.2 未来优先级

```text
1. Web / WebAssembly
2. Linux
3. macOS（可选，可能永不作为产品目标）
```

未来平台的目的不是“现在就做”，而是：

> **以后新增平台时，主要工作应是实现既有 backend / host integration，而不是重写协议引擎。**

## 2.3 跨平台不是“禁用 Windows API”

正确规则：

```text
跨平台方案明显更好
→ 全平台优先使用跨平台方案

跨平台方案与 Windows 原生方案大致相当
→ 优先跨平台方案，减少分叉与重复维护

Windows 原生方案有可证明的显著优势
→ 保留 Windows-specific backend

协议/容器 truth
→ 不得因 backend 选择而分叉
```

Windows API 可以继续用于：

```text
atomic publish
Windows filesystem semantics
Media Foundation
WIC（仅在某能力确有优势时）
其他明确的 Windows platform/backend 能力
```

但不得无理由进入：

```text
protocol parser
container semantics
source recognition authority
neutral semantics
target writer correctness
target validator correctness
```

# 3. 技术决策优先级

所有 dependency/backend 决策统一按以下顺序判断：

```text
1. Correctness / 文件结构正确性
2. Real-device compatibility / 真实设备兼容性
3. Preservation / HDR / metadata / color 完整性
4. Stability / malformed / failure behavior
5. Output quality
6. Performance / hardware acceleration
7. Maintainability
8. Portability
9. License / distribution / patent handling
10. Binary/package size
11. Dependency count
```

**依赖数量本身不是目标。**

如果 3 个小而专的库比 1 个“万能框架”更兼容、更稳定、更小或更可维护，就使用 3 个。  
如果一个库可以可靠覆盖多个已需要的能力，也应优先复用，避免重复 codec/runtime。

# 4. Dependency Consolidation Rules

## 4.1 Capability-first，不以“库数量最少”为目标

引入第三方 Native dependency 前必须回答：

```text
现有已批准 dependency 是否已经可靠覆盖该能力？
是否会重复引入同一种 codec/runtime？
新增库带来的 compatibility / correctness / performance 收益是什么？
总发布体积是增加还是减少？
是否导致两套长期维护的同义 backend？
```

## 4.2 No Duplicate Codec Without Evidence

两个 production dependency 如果提供相同的：

```text
JPEG
HEVC
H264
color transform
resampling
container remux
```

能力，只有在以下至少一项有明确证据时才允许同时进入发布包：

```text
compatibility
correctness
platform acceleration
quality
fallback requirement
security isolation
measurable performance
```

“以后可能有用”不是理由。

## 4.3 大型框架必须按最小 feature set 构建

禁止为了一个小功能直接携带完整：

```text
FFmpeg CLI/runtime feature universe
ImageMagick feature universe
unused codec/plugin collection
unused network/protocol/device support
```

发布包中的每个启用 feature / native binary 都应有实际调用者。

# 5. 已拍板的默认 Native 技术方向

这些不是“每个 AI 都重新选一次”的候选池，而是 **V4.0 默认技术决策**。  
只有真实证据证明不适合 Live Photo Box 时才允许替换。

| Capability | Default decision |
|---|---|
| Protocol / vendor semantics | Project-owned C++ |
| JPEG / TIFF / EXIF / XMP / MakerNote structural truth | Project-owned C++ |
| HEIF / ISO-BMFF / MOV / MP4 / SEF structural truth | Project-owned C++ |
| Public Native boundary | Stable C ABI |
| Canonical Native build | CMake |
| Windows Native dependency declaration | vcpkg manifest as primary strategy |
| JPEG decode / encode | libjpeg-turbo |
| JPEG lossless transform | libjpeg-turbo transform API |
| HEIF/HEIC generic codec gateway | libheif |
| HEIC HEVC decode default | libde265 through libheif |
| HEIC HEVC encode default | x265 through libheif, subject to P4 distribution/license/patent record |
| Alternative HEIC encoder | Kvazaar as benchmark/fallback candidate, not default |
| ICC transform | lcms2 only when an actual color transform is required |
| MP4/MOV vendor/container structural mutation | Project-owned ISO-BMFF engine |
| Windows filesystem/atomic publish | Win32 behind PlatformFilesystem boundary |
| SHA-256 | Project-owned/portable algorithm over neutral byte/stream I/O |
| Production external media CLI | Forbidden |
| Web future | Same Portable Core compiled to WASM; no second protocol engine |

### 5.1 仍必须由 P4 用真实证据决定的主要事项

```text
Windows video codec/transcode backend:
Media Foundation
vs
minimal libav* library backend
vs
hybrid split by capability
```

以及由此派生的：

```text
hardware vs software encode policy
specific static/dynamic linking choices
whether any WIC path remains beneficial
exact codec feature set
```

P4 不再从零重选 JPEG/HEIF/build architecture。

# 6. C# / Native 长期职责

## 6.1 C# Control Plane

负责：

```text
GUI / CLI orchestration
queue / batch
workspace
progress / cancellation
output naming / destination
product flow
history
error presentation
typed target selection
Native interop
product-level publish orchestration
```

当前 `LivePhotoBox.Core` 可以继续是 Windows-specific。  
本 Roadmap **不要求为了未来 Linux/Web 把 .NET 层现在改成跨平台**。

## 6.2 Native Data Plane

负责所有会改变或判断正式媒体结果的：

```text
protocol semantics
container structure
metadata semantics
source inspection
exact extraction
source cleaning
result-affecting image/video conversion
HDR/GainMap math and representation
target structured writing
target validation
repair diagnosis/mutation primitives
```

## 6.3 UI-only 例外

以下可以继续留在 Windows/UI 层，且不要求强制复用 Native：

```text
thumbnail
preview
display resize
preview cache
renderer
UI-only image loading
```

判断标准只有一个：

> **它是否影响正式输出文件。**

# 7. Portable Core / Backend 边界

## 7.1 Portable Core

应尽量只依赖：

```text
standard C/C++
project-owned structural primitives
approved portable libraries
backend contracts
```

不应直接出现：

```text
HANDLE
CreateFileW
MoveFileExW
GetTempFileNameW
IWIC*
IMF*
Windows error codes
MSVC-only convenience APIs as semantic dependencies
```

如果只是 plumbing，应移到 backend/foundation adapter。

## 7.2 Platform Backend

平台层负责：

```text
random-access file source/sink
streaming read/write
safe temp creation
atomic publish/replace
delete/remove
flush/durability where supported
filesystem capability
platform error mapping
```

当前只实现：

```text
WindowsPlatform / WindowsFilesystem
```

未来才可能增加：

```text
POSIX
Emscripten/browser
Apple platform
```

## 7.3 Media Backend

统一 capability contract，至少可表达：

```text
JPEG encode/decode/transform
HEIC encode/decode
video probe
video remux where generic backend is actually used
video decode/encode/transcode
audio handling
color transform
pixel scale/format conversion where required
```

协议 correctness 不读取“使用了哪个 backend”来决定结果。

# 8. Build 与 ABI 长期规则

## 8.1 CMake

P4 后：

```text
CMake = canonical Native build description
```

目标方向：

```text
MSVC       → LivePhotoBox.Native.dll
Emscripten → livephotobox.wasm
GCC/Clang  → liblivephotobox.so
AppleClang → liblivephotobox.dylib / static library
```

当前 `.vcxproj` 可以在迁移期保留，直到：

```text
CMake Windows build
+
tests
+
artifact parity
+
debug/developer workflow
```

证明无回归后再决定删除，不做大爆炸切换。

## 8.2 C ABI

C ABI 是长期 host boundary。

应保持：

```text
fixed-width types
explicit struct_size / ABI version
UTF-8 text at boundary
no C++ STL ABI leakage
no Windows HANDLE in public ABI
no COM objects in public ABI
```

优先提供：

```text
memory/span-oriented primitive
+
stream/random-access abstraction where large-file processing requires
```

这样 Windows file path、WASM ArrayBuffer 与未来 POSIX file 都可以复用同一核心。

# 9. 唯一阶段顺序

```text
P0   Rebuilt-only Runtime Closeout
 ↓
P1   Source Inspector Reliability
 ↓
P2   Extractor Reliability
 ↓
P3   Cleaner Reliability
 ↓
P4   Native Platform / Media Backend / Build Foundation
 ↓
P5   Converter Reliability
 ↓
P6   Neutral Pipeline Closeout
 ↓
P7   System Torture / Malformed / Regression Campaign
 ↓
P8   Split / Merge Product Foundation
 ↓
P9   Target Protocol Writers + Validators
 ↓
P10  Repair
```

各阶段对长期平台架构的职责：

| Phase | Long-term portability responsibility |
|---|---|
| P1 | Recognition/protocol truth 属 Portable Core |
| P2 | Exact extraction semantics 与文件 I/O 分离 |
| P3 | Cleaner mutation semantics 与 atomic publish 分离 |
| P4 | 正式建立 Platform/Media backend、CMake、dependency foundation |
| P5 | Converter 只依赖 backend contracts |
| P6 | NeutralMediaBundle 不携带 platform/backend-specific truth |
| P7 | 防止 backend/portability regression |
| P8 | Windows UI 可平台专用，但 product flow 不污染 Native truth |
| P9 | Writer/Validator 尽量为 Portable Core |
| P10 | Diagnosis/mutation portable；publish/backend 分离 |

# 10. Source-side / Target-side 闭环

Source：

```text
Source
↓
Inspector
↓
Extractor
↓
Cleaner
↓
Inspector post-clean verification
↓
Neutral eligibility
```

Target：

```text
NeutralMediaBundle
↓
OutputProfile
↓
Target Writer
↓
flush / close
↓
reopen final output
↓
Target Validator
↓
independent/reference/device evidence
↓
Publish
```

Source Inspector 与 Target Validator 可以共享可信只读低层 parser，不能共享最终 correctness 判定。

# 11. Neutral Contract

长期 Neutral 语义由：

```text
12-中性媒体契约.md
```

定义。

核心规则：

> **Target Writer 消费 NeutralMediaBundle + OutputProfile，不消费来源厂商私有状态。**

Neutral 还必须：

```text
platform-neutral
backend-neutral
truthful preservation
unambiguous auxiliary/HDR representation
```

```text
TargetProtocol

OutputProfile
```

其中：

OutputProfile

# 13. Production runtime 永久禁止项

禁止：

```text
legacy automatic fallback
hidden second protocol truth
ffmpeg.exe / ffprobe.exe production subprocess
ExifTool.exe production subprocess
jpegtran.exe production subprocess
heif-enc.exe / heif-dec.exe production subprocess
magick.exe production subprocess

silent HDR degradation
silent backend fallback that changes quality/preservation
```

外部 CLI 仍可用于：

```text
research
tests
independent validation
fixture generation
diagnostics in developer tooling
```

# 14. 全局执行硬规则

所有 P0–P10 文档共享以下规则，Phase 文档不再复制整套规则。

1. **先读当前 HEAD，再修改。** Roadmap 是 contract，不是当前实现快照。
2. **只执行当前阶段。** 不以“顺手”为理由提前实现后续 Phase。
3. **Compatibility / correctness 优先于体积和依赖数量。**
4. **协议/容器 truth 不外包给 generic codec/backend。**
5. **Production runtime 不恢复 external media CLI。**
6. **C# 是 Control Plane；Native 是 result-affecting Data Plane。**
7. **Portable Core 不无理由直接依赖平台 API。** 已存在的 Win32 plumbing 若不影响 correctness，可在 P4 收口，而不是为了形式主义回头重写 P1–P3。
8. **平台原生能力有明显优势时允许分流。** 分流必须位于 backend contract 后。
9. **同等条件优先 portable third-party solution。**
10. **不为“少一个库”牺牲兼容性；也不为一个小功能引入无必要的大框架。**
11. **所有 output-changing operation 默认事务安全。**
12. **源文件默认不原地覆盖。**
13. **所有 Done 必须由与风险匹配的证据宣布。**
14. **错误必须可定位到 Stage / Capability / Failure category。**
15. **用户可见文档除非用户明确要求，不随 Roadmap 重构自动修改。**

# 16. 最终判断

Live Photo Box 不追求“理论上所有代码都跨平台”。

它追求：

> **协议 truth 写一次；通用能力优先复用成熟 portable Native library；平台原生能力只有在明显更好时才分流；当前 Windows 做到最好，同时不把未来 Web/Linux/macOS 的门焊死。**

这条原则高于“依赖越少越好”“全部用 Windows API”“全部用 FFmpeg”“全部自己写”等任何单一技术偏好。
