# 中性媒体转换与来源协议清理路线

> **路线性质**：这是从现在开始采用的产品重构路线。旧的 `docs/LivePhotoBox-Native-Refactor/` 不再作为本路线的施工依据。
>
> **最终状态**：本路线完成时，新管线只负责正确读取来源、转换图片与视频格式、清除来源实况照片协议、保留重要媒体信息。它不生成、不注入任何 Google、OPPO、vivo、Samsung、Huawei、Honor 或 Apple 实况照片协议。

## 1. 为什么先停在这里

现在最需要证明的不是“又支持了一个协议”，而是以下基础事实：

- 软件能正确读出图片、视频、辅助图、轨道、方向和时间轴；
- 图片与视频能稳定转换成指定编码和容器；
- 来源文件中的实况照片标识、配对信息、视频指针和封面字段能被清干净；
- EXIF、ICC、HDR、GainMap、方向、旋转矩阵和其他重要信息不会被误删；
- 用户能够知道一次操作实际走了什么处理后端。

如果这些底层能力还不可靠，继续实现目标协议只会把读取、转码、清理和协议写入的问题叠在一起，出了错也无法判断是哪一层造成的。

## 2. 明确不做什么

本路线期间不做以下工作：

- 不新增目标厂商协议；
- 不修补目标协议注入以追求真机识别；
- 不把任何 Preview Native 协议提升为 Auto 或 Default；
- 不删除现有 Legacy 或 Native 协议实现；
- 不让新管线调用现有协议 writer；
- 不在产品里加入完整协议发布检测器；
- 不因为新管线不需要某段私有数据，就未经证明整段删除。

现有协议实现作为冻结参考保留。施工前为当前状态建立可恢复提交或备份分支，记录源码版本和现有测试结果。之后新管线与旧协议实现物理或依赖方向隔离。

## 3. 新管线的输入和输出

### 3.1 输入

允许输入：

- 已经包含实况协议的单文件照片；
- Apple、vivo 旧格式等双文件照片和视频；
- 普通图片和普通视频；
- JPEG、HEIC/HEIF、MP4、MOV，以及能力表明确支持的编码组合。

### 3.2 输出

输出是中性媒体，不是实况照片：

- 单文件来源拆为独立图片和独立视频；
- 双文件来源转换为用户选择的图片格式和视频格式；
- 普通媒体按需要只换容器、无损重封装或转码；
- 输出中不存在任何实况照片识别、配对、视频定位或封面编辑字段。

目标组合先限定为项目确实需要并能够验证的集合，例如：

| 图片 | 视频 | 典型用途 |
|---|---|---|
| JPEG | MP4 / H.264 | 通用兼容输出 |
| JPEG | MOV / H.264 或 HEVC | 保留 QuickTime 容器需求 |
| HEIC | MP4 / H.264 或 HEVC | HEIC 图片与独立视频 |
| HEIC | MOV / HEVC | Apple 媒体格式但不带 Live Photo 配对 |

能力表必须机器可读。尚未验证的组合标为不支持，不能只因为底层工具“可能能转”就显示给用户。

## 4. 产品职责划分

```text
GUI / CLI
  → 转换任务、批处理、命名、进度、取消
  → LivePhotoBox.Core 编排
  → 来源读取 / 协议清理 / 图片转换 / 视频转换
  → 中性图片 + 中性视频 + 操作结果
```

### C# 保留

- GUI、CLI 和用户选项；
- 任务编排、批处理、进度、取消和日志；
- Backend 路由和安全 fallback；
- 输出命名、冲突处理和错误展示；
- 转换计划与保留策略的业务决策。

### Native C++ 承担

- 边界安全的 JPEG、TIFF/EXIF、XMP、HEIF、ISOBMFF、MP4/MOV 解析；
- 厂商实况结构的精确定位和精确删除；
- offset、size、alignment 和 box/table 重建；
- 不能交给通用元数据工具的原始字节保留；
- 后续逐步承接标准媒体库的 decode、encode 和 remux。

### 外部媒体工具

基础阶段允许继续调用稳定的 ffmpeg、ffprobe、libheif 工具或现有项目工具，先把行为和测试固定。不要为了“全 Native”同时重写编码器、容器和协议清理。

外部工具路径统一由一个定位器决定；生产打包工具使用项目固定版本，开发诊断工具可从 PATH 查找。等功能清单稳定后，再决定是否把媒体 CLI 换成库或自编精简版本。

## 5. 中性媒体模型

建议建立以下职责对象，具体类名可在实现时按源码调整：

| 对象 | 责任 |
|---|---|
| `SourceMediaFacts` | 来源容器、编码、图片 item、视频轨、辅助图、方向、色彩和来源协议事实 |
| `MediaConversionRequest` | 用户选择的目标图片/视频格式与保留选项 |
| `MetadataPreservationPlan` | 每项元数据是保留、重算、删除、降级还是不支持 |
| `NeutralMediaBundle` | 中性静态图、视频、GainMap/辅助图和已完成的保留结果 |
| `SourceProtocolCleaner` | 只删除来源实况照片协议，不注入目标协议 |
| `ImageConversionService` | 图片解码、编码、方向、色彩和 HDR/GainMap 处理 |
| `VideoConversionService` | 视频容器、编码、音频、旋转和时间轴处理 |
| `ConversionExecutionRecord` | 请求后端、实际后端、fallback、工具版本和输出事实 |

新管线中不建立 `TargetProtocol`、`ProtocolPackager` 或目标厂商 writer 的依赖。以后是否恢复协议实现，由另一个后续决策决定，不属于本路线。

## 6. 正确读取是第一道门槛

每种输入都要先形成结构化事实，不能用“搜到一个字符串”代替完整读取：

- JPEG：段边界、EOI、EXIF APP1、XMP APP1、ICC 分片、SOS 后扫描数据；
- TIFF/EXIF：字节序、IFD 链、offset、MakerNote 原始范围、UserComment 原始编码；
- HEIC/HEIF：顶层 box、meta、iinf/infe、iloc、iref、iprp、主图、Exif/XMP item 和辅助图；
- MP4/MOV：ftyp、moov、mdat、轨道、sample table、edit list、旋转矩阵和 metadata；
- HDR/GainMap：Primary 与 GainMap 的真实资源范围和关联关系；
- 实况来源：图片、视频、尾部、Trailer、UUID 或 ContentIdentifier 的真实位置。

产品读取器必须能给出明确错误：不支持、结构损坏、引用越界、媒体缺失或存在多个冲突候选。不能自动选一个看起来最像的范围继续写。

## 7. 来源协议清理规则

清理目标是“中性化”，不是抹掉所有厂商信息。

### Google V1 / V2 与 Xiaomi

- 删除 `MicroVideo*`、`MotionPhoto*`；
- 删除 MotionPhoto Item 和它指向的视频范围；
- 如果 Container 仍用于 GainMap，保留 Primary/GainMap 并重算其结构；
- 保留非实况 XMP、EXIF、ICC、相机信息和真实 GainMap；
- 不把 Xiaomi 私有相机 APP 段当作实况协议整段删除。

### OPPO / OnePlus

- 删除 V2 实况字段和 MotionPhoto Item；
- 删除 `OpCamera` 中属于实况识别、视频长度和封面的字段；
- 删除实况用途的 `oplus_` UserComment；
- 精确切除视频和相关实况尾部；
- 保留与实况无关的相机信息、HDR、GainMap 和色彩数据。

### vivo X300 及以后

- 删除 GCamera/VCamera 实况字段和 MotionPhoto Item；
- 删除用于 vivo 实况识别的 UserComment；
- 保留真实存在的 Primary、GainMap、`hdrgm` 和非实况 EXIF；
- 输出中 GainMap item 必须继续指向真实资源。

### vivo X200 及以前

- 删除图片和视频两端的 `com.android.camera.livephoto` 配对值；
- 删除 `cameralbum!` 实况尾标和 MP4 `vivoMediaExtInfo` 中的实况字段；
- 删除 `imageTime/newCoverTime` 等只服务于实况封面的字段；
- 非实况 JSON 只有在能安全重建时保留，否则明确记录降级原因。

### Samsung JPEG / HEIC

- 删除 Google V2 实况部分；
- JPEG 删除 `MotionPhoto_Data`、`MotionPhoto_Version` 及视频载荷；
- HEIC 删除 mpvd/sefd 中的实况视频与指针；
- 需要保留其他 Samsung Tag 时，重新计算 SEF 项目数量、offset 和 size；
- 保留非实况 Samsung Tag、图片色彩和普通 EXIF。

### Huawei / Honor

- 根据容器结构定位并移除嵌入 MP4；
- 删除 `LIVE_` 尾标、`v6_fXX/v2_fXX` 和实况封面字段；
- 从视频中清除只服务于 Moving Photo 的 covertime 等信息；
- Honor 防抖扩展不因字符串命中而盲删，必须确认它是否落在被移除的视频尾部范围；
- 保留静态图片、EXIF、ICC、HDR 和不冲突的相机私有数据。

### Apple

- 图片端删除 Live Photo ContentIdentifier，不误删其他 MakerNote 数据；
- MOV 端删除配对 ContentIdentifier、Live Photo metadata 轨和相关标记；
- 保留视频、音频、普通 creation metadata、方向矩阵和色彩信息；
- 输出是独立 HEIC/JPEG 与 MOV/MP4，不应再被识别为一对 Live Photo。

## 8. 元数据保留策略

每类信息都要有显式政策，不能简单写“尽量保留”。

| 信息 | 默认政策 |
|---|---|
| EXIF 拍摄信息 | 容器支持时保留；offset 重建后回读 |
| MakerNote | 不理解时原始保留；只有已确认的实况条目精确删除 |
| UserComment | 非实况内容保留原始编码；实况识别内容精确删除 |
| ICC Profile | 分片完整保留并验证重组 hash |
| EXIF Orientation | 根据是否旋转像素决定保留或归一化 |
| QuickTime rotation matrix | remux 时保留；旋转像素时按策略归一化 |
| HDR / GainMap | 容器和编码支持时保留；不能保留时禁止静默降级 |
| 时间、GPS | 用户未要求清除时保留 |
| 缩略图 | 方向与主图一致时保留，否则重建或明确删除 |
| 未知厂商块 | 默认原样保留；移动前确认内部是否可能含 offset |

每次转换产生机器可读的 preservation report，列出保留、删除、重算、降级和失败项。它是操作记录，不是完整协议检测器。

## 9. Backend 设置先修清楚

当前设置会写入 `%LocalAppData%\LivePhotoBox\backend-settings.json`，但现有测试没有证明执行一次真实操作后设置仍保持，也没有统一记录实际后端。

重构第一阶段必须完成：

1. 用临时配置文件测试保存、重载、进程重启和一次转换后的值一致；
2. GUI 自动化测试选择 Backend、执行一次操作、返回设置仍保持；
3. 每次操作记录请求模式、每项能力的实际后端、fallback 与原因；
4. GUI/CLI 显示实际执行结果，不能根据设置值推测；
5. 任何转换、拆分或清理操作都不能修改用户设置；
6. 把“媒体转换后端”与旧的“厂商协议后端”分开，旧协议选择器在本路线中冻结或隐藏为实验项。

在这些测试完成前，不以设置页面显示值证明 Native 已被使用。

## 10. 测试体系

本路线自己的测试只证明产品基础能力，不承担所有厂商协议的发布认证。完整协议验证由另一份独立路线负责。

### 单元与契约测试

- parser 边界、截断、重复块、未知块和 32/64 位大小；
- 每个 cleaner 的最小合法结构和损坏结构；
- 保留策略的正向与负向 fixture；
- Native/Legacy 差分只用于已有等价能力，不把旧实现自动当真理。

### 真实样本转换测试

- `designs/各个机型测试` 只读，复制后处理；
- 覆盖每种来源协议、JPEG/HEIC、MP4/MOV、H.264/HEVC、音频、方向和 HDR/GainMap；
- 真实输出必须能被独立标准工具读取；
- 必须断言已知实况标识不存在；
- 必须对保留清单逐项比较，而不是只看命令退出码。

### 失败测试

- 视频长度错一位、box 截断、重复 XMP、多个 MakerNote、无 EOI；
- 只有协议标识但视频缺失；
- 引用越界或两个候选视频；
- 不支持的 HDR/编码组合；
- 取消、磁盘空间不足、输出冲突和外部工具失败。

## 11. 分阶段实施

### A. 冻结与盘点

- 建立恢复点；
- 列出所有协议 writer、cleaner、reader、转码入口和外部工具；
- 标出新管线禁止调用的目标协议入口。

完成条件：能够从调用图证明新旧边界。

### B. Backend 可观察性

- 修持久化测试；
- 增加实际执行记录；
- 将媒体后端和协议后端解耦。

完成条件：一次操作用了什么实现有机器可读证据。

### C. 来源事实模型

- 统一 JPEG/HEIC/MP4/MOV 读取结果；
- 建立 `SourceMediaFacts` 和错误模型；
- 先只读，不写文件。

完成条件：真实样本都能得到完整、无越界的结构事实，不能确认的内容明确报错。

### D. 图片转换

- JPEG/HEIC、方向、EXIF、ICC、HDR/GainMap；
- 区分原样复制、无损容器修改和重新编码。

完成条件：图片矩阵和 preservation report 全部通过。

### E. 视频转换

- MP4/MOV、H.264/HEVC、音频、旋转矩阵、时间轴；
- 区分 remux 和 transcode。

完成条件：首/中/末帧、轨道、时长和方向验证一致。

### F. 来源协议清理

- 按第 7 节逐个实现；
- 每个 cleaner 同时证明“实况信息消失”和“重要信息仍在”。

完成条件：所有来源样本能输出中性媒体，不再被相应厂商协议识别器判为实况照片。

### G. 完整中性转换矩阵

- capability matrix 生成全部声明支持组合；
- GUI 与 CLI 使用同一 Core 管线；
- 连续运行、批处理、失败恢复和取消全部覆盖。

完成条件：所有声明支持组合有真实产物和证据报告，没有目标协议注入路径被调用。

## 12. 本路线完成的定义

只有同时满足以下条件，才能称为完成：

- 新管线从任何声明支持的实况来源读出正确图片和视频；
- 转成声明支持的图片/视频格式后可正常读取和播放；
- 来源实况协议标识、配对、定位和封面信息全部清除；
- EXIF、ICC、HDR、GainMap、方向、音频和时间轴符合明确政策；
- 未知数据没有被无依据删除；
- GUI 与 CLI 输出一致；
- Backend 设置不会因一次操作重置，实际执行后端可追踪；
- 真实样本矩阵、损坏输入和回归测试全部通过；
- 重构后的新路径没有实现或调用任何目标实况照片协议。

完成本路线后先停下来评审。是否重新开始实现目标协议，需要新的明确决定，不由本文自动进入下一阶段。
