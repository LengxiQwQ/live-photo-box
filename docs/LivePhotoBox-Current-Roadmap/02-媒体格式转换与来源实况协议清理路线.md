# 媒体格式转换与来源实况协议清理路线

> **状态**：待执行 / 重构第二阶段  
> **审计基线**：`master @ 7e27c62297b6065bdfa82fdf16ae7e0fd2c2b6c0`  
> **前置条件**：`01-协议后端分流开关与路由审计路线.md` 的全局开关和 fail-fast 隔离全部通过；当前阶段不提前实现本路线。  
> **目标**：把当前散落在 Merge / Split / Protocol / ExifTool / FFmpeg / Native helper 中的图片转换、视频转换、元数据保留和来源实况协议清理拆成明确、可组合、可测试的基础能力  
> **核心原则**：先得到正确、干净、信息保留明确的中性媒体；本路线完成前不接入任何目标协议 writer，也不要把“解包、转码、清理、协议写入”混成一个函数
> **当前阶段范围**：先把 Backend、基础格式转换、协议清理、测试框架搭稳。HDR / GainMap 暂不作为完整保真发布门禁；基础路径允许降级为 SDR / 普通图片，但绝不能静默丢失：必须写入 Preservation Outcome 和 Execution Record，供 GUI、CLI、测试和发布报告读取。

---

## 1. 本路线解决什么

当前 Live Photo Box 已经能够完成大量实际操作，但媒体处理逻辑与协议逻辑互相穿插。

典型当前链路：

```text
LivePhotoMergeRunnerService
  → HEIC/JPEG 转换
  → SourceProtocolCleaner
  → EnsureMp4Async
  → MOV cleanup
  → protocol.PrepareImageAsync
  → WriteLivePhotoAsync
  → 再补 UserComment
  → 再清 Apple MakerNote
```

Split 侧又有另一套：

```text
LivePhotoSplitService
  → 找视频
  → 切图片
  → 切视频
  → 清部分标记
  → 图片转换
  → 视频转换
  → CopyMetadataToVideo
  → Apple/vivo 双文件协议写入
```

这使以下问题很难单独判断：

- 是源协议解析错了；
- 是视频切割错了；
- 是格式转换损失了数据；
- 是来源协议没清干净；
- 是目标协议 writer 写错了；
- 还是某个 helper 隐形走了 Native。

本路线的目标是把这些层彻底分开。

## 2. 最终处理管线

统一成：

```text
Source Files
   ↓
Source Inspection
   ↓
Source Protocol Read / Extract
   ↓
Canonical Media Facts
   ↓
Preservation Plan
   ↓
Source Protocol Cleaning
   ↓
Media Conversion Plan
   ↓
Image / Video Conversion
   ↓
Neutral Media Bundle
   ↓
（后续）Target Protocol Write
```

`Source Protocol Read / Extract` 必须在任何清理前完成并产出不可变的 `SourceMediaFacts`、真实媒体范围和 preservation inventory。Cleaner 只能处理 workspace 副本；它不能靠清理后的文件重新猜来源边界，也不能修改用户源文件。

### 2.1 本路线结束时必须能单独调用

```text
只提取，不转码
只转图片
只转视频
只清协议
清协议 + 保持原格式
清协议 + 转成指定中性格式
```

而不是必须进入：

```text
Merge / Split 某个 UI 页面
```

才能用。

## 3. 当前代码基线审计

### 3.1 Merge 侧当前格式索引

当前：

```text
LivePhotoMergeRunOptions.OutputFormatIndex
ProtocolFormatMatrix
```

使用裸整数。

大致：

```text
0 = JPG + MP4
1 = JPG + MOV
2 = HEIC + MP4
3 = HEIC + MOV
4 = HEIC + MP4 / H.265（Huawei）
```

### 3.2 Split 又有另一套整数含义

当前：

```text
SplitCommand.SplitFormatMap
```

是：

```text
0 = keep
1 = JPG + MOV / H.265
2 = HEIC + MOV / H.265
3 = JPG + MP4 / H.264
```

同一个数字在不同链路含义不同。

这必须消失。

### 3.3 HeicConverterService 已经承担很多职责

当前它同时处理：

- HEIC → JPEG；
- JPEG → HEIC；
- heif-dec / heif-enc；
- Magick.NET；
- ExifTool metadata copy；
- Orientation；
- Apple gain map；
- Standard HDR conversion。

问题不是功能少，而是能力没有形成统一 contract。

### 3.4 HDR / GainMap 本阶段不作为重构目标

当前阶段优先级固定为：

```text
协议 Backend 分流可信
→ 图片/视频基础格式转换可复用
→ 来源实况协议能正确拆除
→ 自动化测试基础设施完整
```

HDR / GainMap 现在只作为“来源结构里可能存在的附加数据”处理，不要求完整保真，也不为它增加新的用户交互或复杂 policy。

规则：

```text
现有路径能保留 → 保留
现有路径不能保留 / HDR 转换失败 → 可降级为普通 SDR / 普通图片，但必须记录
```

并且：

- 当前 GUI 不要求为每次降级弹窗；
- `PreservationOutcome` 必须记录 `preserved / normalized / downgraded / unsupported` 和证据；
- API 保留 `BestEffort` 与 `RequirePreservation` policy，当前普通 UI 请求可用 `BestEffort`；
- `RequirePreservation` 请求遇到无法保留时必须失败，不能擅自降级；
- 发布与测试报告必须显示 HDR/GainMap 是否保留，不能把降级写成“preserved”；
- 不把 HDR 保真列入本轮 Native/Legacy 重构门禁；
- `StandardHdrConversionService` 可以继续存在，但本阶段不扩展、不围绕它重构架构。

唯一必须做的是：如果 Motion Photo / HEIF 容器里存在 GainMap 或其他辅助 Item，解析器要能正确识别它不是实况视频，不能因此算错视频范围。这个属于**容器解析正确性**，不是 HDR 功能。

### 3.5 VideoTranscodeService 已经比较成熟

当前已经有：

- MP4/MOV；
- H.264/HEVC；
- FFmpeg；
- remux；
- hardware encoder chain；
- CPU fallback；
- Apple HEVC conformance window 处理；
- audio；
- faststart；
- Huawei 特殊 brand；
- ffprobe/exiftool 辅助。

这部分不应该为了“全部 C++”马上重写。

第一目标：

> 把它收口成稳定的 Media.Video capability。

后续再决定 FFmpeg CLI → libavformat/libavcodec 是否值得迁。

### 3.6 SourceProtocolCleaner 当前覆盖很窄

当前：

```text
LivePhotoBox.Core/Services/Protocols/SourceProtocolCleaner.cs
```

主要处理：

- Apple 图片 MakerNote；
- Apple MOV mdta / mebx；
- vivo legacy JPEG tail；
- vivo legacy MP4 uuid。

它不是完整的来源协议清理器。

Google V1/V2、OPPO、vivo X300、Samsung、Huawei/Honor 仍有大量清理逻辑散落在：

```text
LivePhotoSplitService
LivePhotoMergeRunnerService
Mp4MdtaKeyStripper
AppleMakerNoteWriter
协议类
```

### 3.7 Mp4MdtaKeyStripper 已经有可复用的结构化能力

当前能够：

- 删除 mdta keys；
- 删除 track；
- 删除 uuid；
- 重建 moov；
- 调整 stco/co64。

这类能力应成为：

```text
Media.Container.*
Protocol.Clean.*
```

底层能力，而不是被多个业务函数直接调用。

```text

```

例如：

```json

  "image": {
    "container": "jpeg"

  "video": {

  }
```


## 6. 图片格式转换能力

本阶段只把 JPEG / HEIC 的**基础转换接口与路由**搭稳。

HDR / GainMap 不作为本阶段的功能目标。

### 6.1 JPEG → JPEG

默认：

```text
不重编码像素
```

仅在确实需要时：

- 清理/重建协议 XMP；
- 修改指定 metadata；
- 修正 orientation；
- 保持文件结构有效。

如果源 JPEG 是 Ultra HDR，本阶段不要求重建或验证 GainMap。现有路径自然保留则保留，否则允许自动变成普通 JPEG。

### 6.2 HEIC → HEIC

优先：

```text
原字节 / 结构级处理
```

目标是避免为了协议清理无意义地 decode/re-encode。

本阶段重点验证：

- HEIF box/item 边界；
- Exif item 定位；
- 普通 metadata；
- 输出仍是合法 HEIC。

GainMap / HDR auxiliary item 只要求**不要干扰视频或 Exif 定位**。是否最终完整保留，不作为门禁。

### 6.3 HEIC → JPEG

本阶段目标：

```text
HEIC
→ decode
→ 普通 JPEG
→ 尽量复制普通 EXIF / ICC / Orientation
```

如果现有 HDR 转换路径成功，可以继续得到 Ultra HDR JPEG，并记录 preserved evidence。

如果 HDR 路径失败或未实现：

```text
自动走普通 SDR JPEG，并记录 downgrade 原因
```

普通 `BestEffort` 请求不必弹窗，也不把任务判失败；`RequirePreservation` 请求必须失败。

### 6.4 JPEG → HEIC

本阶段目标：

```text
JPEG
→ decode
→ HEIC encode
→ 尽量复制普通 EXIF / ICC / Orientation
```

如果来源包含 Ultra HDR GainMap，本阶段不要求把它转换成 HEIF auxiliary GainMap。

现有能力能保留则保留；不能则直接生成普通 HEIC 并记录 downgrade。

### 6.5 不做无意义重复转换

```text
JPEG → JPEG target
HEIC → HEIC target
```

如果目标容器与像素内容无需变化，默认不重新编码。

### 6.6 HDR 后续单独立项

以后真正做 HDR 时，再单独设计：

- GainMap 提取；
- Ultra HDR JPEG；
- Apple HEIC hdrgainmap；
- HEIF auxiliary image；
- HDR metadata 映射；
- HDR 保真测试；
- 用户可配置的保真/降级策略。

这些**不进入当前基础设施里程碑**。

## 7. 视频格式转换能力

### 7.1 Remux 优先于 Transcode

如果 codec 与目标兼容：

```text
MOV/HEVC → MP4/HEVC
```

优先：

```text
remux
```

而不是 re-encode。

同理：

```text
MP4/H264 → MOV/H264
```

优先 remux。

### 7.2 H.264 / HEVC 转码

需要转码时才进入：

```text
VideoTranscodeService
```

当前 hardware fallback：

```text
NVENC
→ AMF
→ QSV
→ VAAPI
→ libx264/libx265
```

可以继续保留。

这不是协议 Legacy/Native fallback。

### 7.3 必须记录实际 encoder

Conversion Execution Record：

```text
requestedCodec
selectedEncoder
hardwareFallbackOccurred
outputCodec
outputContainer
```

### 7.4 Apple 全 I 帧是目标协议要求，不是通用转换规则

当前 Split Apple：

```text
keyframeInterval = 1
```

应该移动到：

```text
Apple Target Media Profile
```

而不是写死在通用：

```text
VideoConversionService
```

### 7.5 Huawei 特殊 brand 也属于目标 profile

例如：

```text
mp42
iso2
openharmony6
```

这些是 Huawei 目标协议写入需求。

不能成为普通 MP4 conversion 默认行为。

## 8. 来源协议清理的总原则

“清除实况照片协议”不等于：

```text
删除所有厂商数据
```

而是：

> 删除使文件被识别、配对、定位或编辑为 Live/Motion Photo 的数据，普通 EXIF / ICC / 相机信息尽量保留；HDR / GainMap 本阶段不作为强制保留目标。

### 8.1 禁止只靠字符串命中删除

ASCII / UTF-8 scan 可以做：

```text
prefilter
```

不能直接做：

```text
看到 LIVE_
→ 截文件

看到 MotionPhoto
→ 删除整个 XMP

看到 VCamera
→ 删除全部 UserComment
```

必须先结构化定位。

# 9. Google MicroVideo V1 清理

来源结构：

```text
JPEG
+
appended MP4
```

主要实况字段：

```text
GCamera:MicroVideo
GCamera:MicroVideoVersion
GCamera:MicroVideoOffset
GCamera:MicroVideoPresentationTimestampUs
```

清理：

1. 通过 `MicroVideoOffset` 验证真实视频范围；
2. 提取视频；
3. 图片截到正确 JPEG 结束；
4. 从 XMP 只删除 V1 实况字段；
5. 保留：
   - 其他 XMP；
   - EXIF；
   - ICC；
   - MakerNote；
   - 相机信息；
6. 清理后重新解析 JPEG 结构。

不能：

```text
只把 MicroVideo=0
```

视频仍留在文件尾。

# 10. Google Motion Photo V2 / Xiaomi 清理

V2 不能按 V1 offset 处理。

必须解析：

```text
Container:Directory
```

规则：

- Primary 有且只有一个；
- MotionPhoto item 有且只有一个；
- 视频 item 必须映射真实字节；
- GainMap 与实况无关。

清理：

```text
删除 MotionPhoto Item
删除 MotionPhoto 视频范围
删除 GCamera:MotionPhoto
删除 MotionPhotoVersion
删除 PresentationTimestamp
```

如果存在：

```text
Primary
+
GainMap
+
MotionPhoto
```

清理后必须变成合法的非 Motion Photo 图片容器。

如果现有实现可以自然保留 GainMap，可以是：

```text
Primary
+
GainMap
```

如果不能，本阶段允许自动降级成：

```text
Primary
```

两者都不提示用户，也不作为失败。

无论是否保留 GainMap，都要正确重算：

- item order；
- Length；
- Padding；
- XMP Container。

### 10.1 Xiaomi 特别规则

小米现代实况就是 Google V2。

不要把：

```text
GainMap
```

当成小米私有实况数据删除。

# 11. OPPO / OnePlus 清理

```text
可选 OnePlus trailer
```

5. 非实况 EXIF / ICC 尽量保留；HDR / GainMap 能自然保留就保留，不能则自动降级。

不能：

```text
整段删掉所有 OPPO 相机私有元数据
```

# 12. vivo X300+ 清理

当前协议事实：

```text
GCamera
VCamera
可选 hdrgm
可选 GainMap
vivo UserComment
MotionPhoto
```

清理：

1. 删除 GCamera MotionPhoto 实况字段；
2. 删除 VCamera：
   - VMotionPhotoVersion；
   - VMotionPhotoSource；
   - VMediaKitVersion（若已确认仅服务此实况协议）；
3. 删除 MotionPhoto item + 视频；
4. 删除 vivo 实况识别 UserComment；
5. 保留：
   - Primary；
   - 非实况 EXIF；
   - ICC；
6. GainMap / hdrgm / HDR：
   - 能自然保留就保留；
   - 不能则自动降级为普通 Primary；
   - 不提示用户；
   - 不作为失败。

### 12.1 绝不能因为 VCamera 与 GainMap 同时存在就整段删除 XMP

vivo 真机的 Ultra HDR 与实况协议共存。

清理后 HDR 是否仍有效不作为本阶段门禁；但 GainMap 不能被误判成 MotionPhoto 视频。

# 15. HUAWEI / Honor 清理

Huawei/Honor 当前单文件是：

```text

+
Embedded MP4
+
60-byte LIVE_ tail
```

并可能包含：

```text

timed_metadata movingphoto track
covertime
v6_fXX / v2_fXX

```

清理：

2. 提取视频；
3. 删除 60B LIVE tail；
4. 删除只服务 Moving Photo 的 cover / pairing / timed metadata；
5. 输出独立视频时清：
   - `com.openharmony.*` live keys；
   - movingphoto timed metadata track；
   - covertime；
6. 保留：
   - 静态图片；
   - EXIF；
   - ICC；

## 21. Transaction

所有清理/转换：

```text
Source Read Only
→ Workspace
→ Temp Artifact
→ Validate
→ Commit
```

禁止直接在用户唯一源文件上 destructive edit。

### 21.1 双文件和多产物发布

所有产物先在同一 volume 的 staging bundle 内完成，逐个验证并写 `ArtifactManifest`，再执行 publication plan。Apple/vivo 等成对输出不能逐文件“边生成边覆盖”；任一成员或验证失败时，最终输出目录不得出现新旧混合的一对文件。无法保证 bundle 级原子可见时，至少以可恢复 journal 记录提交次序和 rollback 清理目标。

### 21.2 Idempotent

清理器必须满足：

```text
Clean(Clean(file)) == Clean(file)
```

至少在语义和结构上等价。

第二次清理不能继续删普通 metadata。
