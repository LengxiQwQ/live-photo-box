# 独立协议验证与发布测试路线

> **路线性质**：这是独立测试系统的建设路线，与产品中性转换重构并行进行。旧的 `docs/LivePhotoBox-Native-Refactor/` 不是本路线的施工依据。
>
> **最终状态**：建立一个不进入产品、不复用产品协议 reader/writer、只在开发和发布前运行的严格验证系统。它依据《实况照片协议完整分析报告》逐条检查真实产物，而不是只看标识符、CLI 退出码或 ExifTool 输出。

## 1. 与产品路线完全分开

本测试系统：

- 不链接 `LivePhotoBox.Native`；
- 不引用 `LivePhotoBox.Core` 的协议读取器或写入器；
- 不进入 GUI、CLI 或安装包；
- 不在用户每次制作文件后运行；
- 不修改被检测文件；
- 不把产品自己回读成功当成合格证据。

它可以与产品重构同时开发。产品路线负责“做出文件”，本路线负责“独立证明文件里每个结构都在正确位置”。两边可以共享协议报告和样本清单，但不能共享同一份协议解析实现。

## 2. 推荐形态

采用三层结构：

```text
Python 集成测试调度器
  ├─ 复制只读真实样本
  ├─ 调用当前源码 lpb.cmd 生成真实产物
  ├─ 调用独立 ProtocolVerifier 检查厂商协议
  ├─ 调用外部标准工具检查媒体和容器
  └─ 汇总 JSON、Markdown 和失败证据

独立 C++20 ProtocolVerifier
  ├─ 只读字节和容器解析
  ├─ 厂商协议规则与交叉引用
  └─ 稳定 JSON 输出

外部工具
  ├─ ffprobe
  ├─ heif-info / libheif 工具
  ├─ Bento4 mp4dump 或 GPAC MP4Box
  └─ ExifTool（仅辅助诊断）
```

### 为什么保留 Python

现有 `scripts/testing/run-cli-integration-test.py` 已经负责真实样本复制、merge/split/cover/repair、超时、产物收集和报告。这些是 Python 擅长的调度工作，应继续使用。

Python 不再无限扩展为所有二进制格式的最终解析器。协议结构判断逐步迁入独立 verifier，脚本只消费 verifier 的 JSON。

### 为什么单独使用 C++

C++ 适合精确读取大文件、控制整数宽度、检查边界并解析 JPEG/TIFF/ISOBMFF。项目已经具备 C++20 和 Visual Studio 构建环境。

独立 verifier 是新的测试项目，例如：

```text
tests/LivePhotoBox.ProtocolVerifier/
```

它必须拥有自己的 parser、规则和 fixture，不链接生产 Native。即使两边都用 C++，也要保持实现独立，避免同一错误同时出现在写入端和验证端。

## 3. 工具使用政策

### PATH 优先

开发机上的大工具默认从系统 PATH 查找。发布验证缺少必需工具时，预检必须失败并说明缺少什么，不能把检查静默标为 skipped 后仍给出绿色结果。

### 可以放进项目的工具

只有同时满足以下条件才考虑放入测试工具目录：

- 体积小；
- 许可证允许再分发；
- 版本差异会影响判定；
- PATH 安装明显不稳定；
- 已记录来源、版本、许可证和 SHA-256。

测试工具不能未经评审进入产品发布包。

### ffprobe 精简版

先用官方完整 ffprobe 固定所有需要的字段、demuxer、parser 和输出行为。之后再维护一个只供测试使用的精简构建配置。

精简版必须与官方完整版对同一批合法、损坏、截断和私有容器样本做差分。只要出现“完整版报错、精简版却通过”或关键字段缺失，就不能替代完整版成为门禁。

### ExifTool 的位置

ExifTool 可以显示兼容性视角、帮助人工诊断、与历史报告对照，但不能成为任何协议的唯一真值。所有关键 offset、length、box、Tag、轨道、配对和封面位置必须由 verifier 或另一个标准容器工具独立证明。

## 4. 验证结果的数据结构

每条规则必须有稳定 ID，并能追溯到协议报告：

```json
{
  "rule": "HUAWEI.TAIL.LIVE_SIZE",
  "status": "pass",
  "reportSection": "Huawei/60-byte-tail",
  "expected": "LIVE value equals embedded MP4 size plus 20",
  "actual": {
    "tailOffset": 8123456,
    "declared": 4512367,
    "videoSize": 4512347
  },
  "evidence": "byte-range"
}
```

每个结果至少包含：

- 文件 hash、大小和检测时间；
- verifier 和外部工具版本；
- 协议候选及判定依据；
- 规则 ID、报告章节、预期、实际、字节范围；
- pass、fail、not-applicable 或 manual-required；
- 提取资源的 hash；
- 失败时的最小上下文，不在报告中复制大段私有数据。

禁止使用模糊的 `metadata ok`。报告必须能回答“检查了什么、在什么位置、实际是多少、为什么通过”。

## 5. 协议报告覆盖账本

先把《实况照片协议完整分析报告》拆成机器可追踪的规则清单。报告中的每一项必须属于以下一种：

| 分类 | 含义 |
|---|---|
| Automated | 可以由 verifier 或外部工具自动检查 |
| Manual device | 只能由对应厂商真机/相册验证 |
| Informational | 与实况识别无关，仅记录不设门禁 |
| Unknown | 报告本身待确认，不能伪装成已验证 |
| Not applicable | 对当前格式组合明确不适用 |

规则覆盖报告必须显示所有未实现项。任何没有分类的报告条目都让“完整验证”状态失败。

## 6. 通用结构检查

所有协议先通过共同基础检查：

### 文件与范围

- 文件头、容器类型和扩展名关系；
- 所有读取和计算使用检查过的 64 位范围；
- box/segment/tag 不越界、不重叠、不循环引用；
- 不能有未解释的尾部垃圾或声明范围外字节；
- 需要位于 EOF 的资源确实结束于 EOF。

### 图片

- JPEG SOI、segment、SOS、扫描数据和 EOI；
- EXIF/TIFF 字节序、IFD、offset 和 MakerNote 位置；
- XMP XML 可解析、命名空间 URI 与属性对应；
- HEIF meta/iinf/iloc/iref/iprp/item 范围；
- ICC、HDR、GainMap 与资源一致。

### 视频

- ftyp、moov、mdat、轨道和 sample table 自洽；
- codec、profile、像素格式、分辨率、音频、时长、帧率；
- edit list、时间基、旋转矩阵和关键帧；
- 按协议提取出的确切字节范围可以被 ffprobe 读取；
- 不能对整个混合文件运行 ffprobe 成功就认为嵌入视频正确。

### 封面

- 从协议规定的字段、轨道或尾部读取封面位置；
- 时间戳、帧号、时间基和视频总时长范围正确；
- 第一帧、中间帧、最后一帧和可变帧率分别测试；
- 抽取协议指向的实际帧，与生成时预期画面比较。

## 7. 各协议必须检查的内容

以下是最低清单，最终以规则覆盖账本逐条展开。

### Google MicroVideo V1

- `MicroVideo=1`、版本和命名空间；
- `MicroVideoOffset` 为合法整数；
- `fileSize - offset` 得到真实视频起点；
- 视频范围结束于 EOF 且能被 ffprobe 读取；
- PresentationTimestampUs 在时长范围内；
- JPEG 图片范围到正确 EOI，不把 APP 内偶然 `FFD9` 当结束。

### Google MotionPhoto V2

- MotionPhoto 值只能按规范解释，不能仅因字段为 1 就通过；
- 有且仅有一个 Primary，且排第一；
- 有且仅有一个 MotionPhoto，且排在资源顺序正确的位置；
- MIME、Semantic、Length、Padding 的必需性和取值正确；
- 所有 Item 按文件实际顺序紧密映射；
- MotionPhoto 为末项时必须到 EOF；
- 不能错误使用残留 V1 offset 定位 V2 视频；
- GainMap/Original 存在时顺序、长度和真实资源对应；
- PresentationTimestampUs 缺失时记录规范默认中点规则。

### Xiaomi

- 先完整满足对应 Google V1/V2；
- MiCamera 字段只作来源辅助，不参与视频定位；
- GainMap 和私有 APP 段不能被误判成视频；
- 报告标为待确认的字段不设自动合格条件。

### OPPO / OnePlus

- 完整满足 V2；
- `MotionPhotoOwner`、版本、Enable 和双时间戳语义；
- `OpCamera:VideoLength` 与纯视频范围一致；
- `Item:Length` 在有 OnePlus 尾部时覆盖的范围符合样本规则；
- UserComment 具有正确前缀和可接受值；
- 当前封面和原始封面字段分别验证；
- 尾部存在时不能把尾部当视频码流交给 ffprobe。

### vivo X300 及以后

- GCamera、VCamera、hdrgm 命名空间和版本；
- Primary/GainMap/MotionPhoto 三项的数量、顺序和属性；
- GainMap 是完整 JPEG，Length 与真实范围完全一致；
- MotionPhoto Length 与真实视频一致并结束于 EOF；
- UserComment 原始字节编码、非空和报告规定的结构；
- 封面时间戳能定位有效视频帧；
- 无 HDR 输出不能伪造 GainMap/hdrgm。

### vivo X200 及以前

- JPEG 尾部 `vivo{JSON}cameralbum!` 边界和 JSON；
- MP4 `vivoMediaExtInfo` UUID box 只有一份且 size 正确；
- 两端 livephoto 配对 ID 完全一致；
- `imageTime` 是 0-based 原始帧号；
- `newCoverTime`、`bestTime`、version 的未编辑/已编辑状态组合；
- 第一帧、中间帧和最后一帧的特殊写法；
- 独立 JPG 实际对应当前封面画面。

### Huawei / Honor

- 从容器结构定位嵌入 MP4，不只做全文件字符串搜索；
- JPEG 在正确 EOI 后找到 ftyp；HEIC 使用正确的第二个 MP4 ftyp 候选；
- 末尾标准 60 字节字段位置、空格填充和前缀；
- `LIVE_ = 嵌入 MP4字节数 + 20`；
- 视频范围排除 60 字节尾部和 Honor 扩展；
- ftyp brand、H.264、音频轨等兼容条件；
- 新版 `com.openharmony.covertime` 与旧版帧号分别验证；
- PPP 字段只按报告定义检查，不错误换算为封面时间；
- Honor 防抖 JSON 只作结构观察，不作为实况识别必要条件。

### Samsung JPEG

- 同时满足 Google V2 兼容层和 Samsung Trailer 私有层；
- 7 个 Tag 的 marker、name、顺序和数据范围；
- `MotionPhoto_Data` 包含完整、可读 MP4；
- MotionPhoto version 为声明版本；
- SEFH/SEFT、version、field count 和总大小；
- 每个 SEF offset/size 精确指向对应 Tag；
- Tag 不重叠、不越界，后续 offset 随视频长度正确变化；
- V2 Item 范围与 Samsung 私有视频的实际关系符合实现目标。

### Samsung HEIC

- HEIF 基础结构有效；
- mpvd/sefd box 的父子边界和 size；
- mpvd 中视频真实范围可读；
- `MotionPhoto_Data = mpv2 + BE offset + BE size`；
- offset 基准、视频大小和 sefd 位置交叉一致；
- HEIC V2 XMP 的 Primary Padding 和 MotionPhoto Length 正确；
- SEF 条目与 sefd 内实际 Tag 一致。

### Apple

- 照片端 ExifIFD 中只有一条目标 MakerNote `0x927C`；
- MakerNote 中 ContentIdentifier 结构、字节序和 UUID；
- 照片和 MOV ContentIdentifier 完全一致；
- MOV 顶层 box 顺序、ftyp brand/compatible、单 mdat；
- moov/meta/keys/ilst 的位置、键顺序和 data type；
- Video、Audio、ContentDescribes、Cover 四轨最低结构；
- 每轨 handler、data handler、sample table 和引用关系；
- ContentDescribes meBx 结构和重复次数；
- Cover meBx、elst 空编辑、TrackDuration 与实际封面位置；
- PosterTime 不能被误当真实封面；
- hvc1/avc1、旋转矩阵、全 I 帧要求按目标兼容级别检查；
- 实际抽取封面帧与静态图画面对应。

## 8. 检测器自身必须被验证

ProtocolVerifier 也可能写错，因此它需要自己的质量门槛：

- 每条规则的最小合法 fixture；
- 每个长度、偏移、计数和时间戳的差一位 fixture；
- 截断、重复、乱序、未知 box、64 位 largesize；
- 整数溢出、极大长度、循环引用和深度限制；
- 真实样本的只读回归；
- AddressSanitizer、未定义行为检查和 fuzzing；
- 与 mp4dump/MP4Box/heif-info/ffprobe 的差分；
- 对验证器版本和规则表做快照，避免规则被无声放宽。

修复产品失败时不得顺便修改 verifier 让测试变绿。若协议事实需要改变，先更新报告证据和规则说明，再单独评审 verifier 变化。

## 9. 真实产物矩阵

测试必须生成真正文件，不使用 dry-run 代替。

### 输入维度

- 每种真实厂商来源；
- JPEG/HEIC、SDR/HDR/GainMap；
- MP4/MOV、H.264/HEVC、有无音频、旋转、VFR/CFR；
- 普通、重复元数据、经过编辑和边界损坏样本。

### 操作维度

- merge 的所有声明协议 × 格式；
- split 的所有输出格式；
- cover 的第一帧、中间帧、最后一帧；
- repair 前后；
- 协议转换往返；
- Legacy/Native 差分；
- 同一输入连续执行的稳定性。

### 结果维度

- 严格协议规则；
- 标准媒体可读性；
- 图片/HDR/色彩保留；
- 封面实际画面；
- 真机导入、播放、编辑和再次导出。

能力矩阵只生成声明支持的组合。每个未测试的声明支持组合都算覆盖缺口，不能因为其他组合通过而忽略。

## 10. 真机验证

自动工具不能代替厂商相册。每个协议进入稳定状态前，记录：

- 手机型号、系统版本、相册版本；
- 输入和输出文件 SHA-256；
- 能否导入、识别、播放、编辑封面、分享和再次导出；
- 实际显示的封面帧；
- 导出后协议结构是否变化；
- 失败视频或截图的本地证据路径。

没有真机记录的协议最多标为“自动结构验证通过”，不能标为完整兼容。

## 11. 发布门禁

最终发布验证顺序：

1. Native build/smoke；
2. `dotnet test`；
3. ProtocolVerifier 自身单元、fixture、fuzz 回归；
4. CLI 生成完整真实产物矩阵；
5. ProtocolVerifier 严格检查；
6. ffprobe/heif/ISOBMFF 外部交叉检查；
7. 生成 `release-verification.json` 和 Markdown 摘要；
8. 任何必需工具缺失、规则未覆盖、产物未生成或检查失败都阻断发布。

原厂样本审计与生成产物结果分开：原厂样本用于发现设备变体，不因历史样本不符合新规则直接掩盖产品结果；但不理解的变体必须进入待调查清单，不能静默忽略。

## 12. 分阶段实施

### T1. 规则账本和 JSON schema

- 把协议报告逐条编号；
- 定义 Automated/Manual/Informational/Unknown；
- 固定 verifier 输出 schema。

完成条件：报告没有未分类条目。

### T2. Verifier 基础工程

- 建立独立 C++20 项目；
- 文件映射/流式读取、checked arithmetic、JSON 输出；
- JPEG/TIFF/ISOBMFF 通用 parser；
- 不链接生产项目。

完成条件：基础损坏 fixture 全部正确拒绝，安全检查通过。

### T3. 外部工具适配

- PATH 发现、版本记录、超时和失败处理；
- ffprobe、heif-info、mp4dump/MP4Box；
- ExifTool 诊断通道与门禁结果分离。

完成条件：缺工具会明确失败，工具输出可以写入统一证据。

### T4. 协议规则实现

- 按报告逐个完成，但可由不同协议模块并行；
- 每条规则先写合法和损坏 fixture；
- 每完成一个协议更新覆盖账本。

完成条件：该协议所有 Automated 条目有证据，Manual/Unknown 明确列出。

### T5. Python 调度器改造

- 保留现有真实产物生成；
- 调用 verifier JSON；
- 移除重复的最终判定逻辑；
- 失败产物、命令、日志和工具版本统一归档。

完成条件：Python 不再依靠 ExifTool 或自己的简化 parser 单独判定协议通过。

### T6. 完整矩阵与发布接入

- capability matrix 驱动真实产物；
- 接入 `scripts/verify.ps1 -Scope Release`；
- 固定报告、保留周期和失败重跑方式。

完成条件：任何遗漏或失败都能稳定阻断发布，成功报告能追溯到每条协议规则。

## 13. 本路线完成的定义

只有同时满足以下条件，测试项目才算完成：

- 与产品代码实现独立；
- 协议报告每一项都有明确分类；
- 所有可自动化条目都有 Rule ID、fixture 和实际证据；
- 标识、位置、长度、顺序、交叉引用、媒体范围和封面都被检查；
- 外部工具各司其职，ExifTool 不是唯一门禁；
- verifier 自身通过 fuzz、安全和损坏输入测试；
- 真实产物矩阵覆盖所有声明支持组合；
- JSON/Markdown 报告可定位每个失败；
- 发布环境缺工具、缺产物、缺规则或有失败时绝不会给出绿色结果；
- 真机检查与自动结构检查清楚分开。

这套测试系统可以在产品只做中性转换的时期先建设完成，并用真实厂商原文件和现有历史产物校准。以后如果重新开始实现目标协议，它直接作为协议上线前的独立门禁使用。
