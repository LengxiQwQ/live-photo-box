# 02A - 来源媒体识别、提取与格式转换路线

> 面向 AI Agent 执行。先扫描当前仓库最新 HEAD，复用现有能力并以实际代码为准；不要按本文档中的类名、目录或旧基线机械实现。
>
> 前置条件：Phase 01 的全局 `Rebuilt / Legacy` 路由、fail-fast 和单一开关已经完成。
>
> 本阶段目标：在 `Rebuilt` 分支内建立可独立复用的 **来源识别 / 媒体定位 / 媒体提取 / 图片转换 / 视频转换** 基础能力。
>
> 本阶段不负责彻底清除来源实况协议，也不实现任何目标协议 Writer。

# 6. Source Inspector

Inspector 只读源文件。

职责：

```text
识别来源协议
识别图片 / 视频容器与 codec
定位 Primary Image
定位 Motion Video
定位 Auxiliary Images / GainMap
识别双文件 pairing
读取 cover / timestamp / 必要协议事实
生成 SourceMediaFacts
```

禁止：

```text
修改源文件
截断源文件
删除协议字段
转码
写目标协议
```

字符串扫描只可作为候选检测 / prefilter。真实媒体范围必须有结构化依据。

---

# 7. Source Extractor

Extractor 不重新识别协议，也不重新猜媒体边界。

只能使用 Inspector 已确认的事实，例如：

```text
ImageByteRange
VideoByteRange
HEIF Item Mapping
Container Directory
SEF Pointer
Pairing Identity
```

所有结果写入 workspace：

```text
ExtractedMediaBundle
├── PrimaryImage
├── MotionVideo
├── AuxiliaryArtifacts
└── SourceMediaFacts
```

用户源文件必须始终只读。

# 8. 02A 需要理解的来源协议结构

Converter 本身不能写 `if Apple / if vivo / if Huawei`。

但本 Agent 必须理解来源协议，因为 Inspector / Extractor 需要知道真实媒体在哪里。

## Google MicroVideo V1

理解：

```text
JPEG + appended MP4
GCamera:MicroVideoOffset
```

Inspector 验证 JPEG 与 MP4 范围；Extractor 输出 Primary JPEG 和 Motion MP4。

本阶段不删除 MicroVideo XMP。

## Google Motion Photo V2 / Xiaomi

理解：

```text
Container:Directory
Primary
MotionPhoto
可选 GainMap / Auxiliary Item
```

必须正确区分：

```text
Primary
GainMap
MotionVideo
```

GainMap 不能误识别为 Motion Video。

本阶段不重建/删除 V2 XMP Directory。

## OPPO / OnePlus

理解 Google V2 基础结构及：

```text
OpCamera
oplus_*
可选 trailer
```

只做媒体定位和协议事实记录，不删除 live metadata。

## vivo X300+

理解：

```text
GCamera
VCamera
MotionPhoto
可选 GainMap
可选 hdrgm
vivo UserComment
```

必须区分 Motion Video 与 GainMap。

## vivo legacy

通常为双文件：

```text
Image + Video
```

Inspector 负责 pairing / format / cover facts。

不删除 UUID / pairing / bestTime / UserComment。

## Samsung JPEG / HEIC

JPEG 重点：

```text
Google V2
Samsung SEF
MotionPhoto_Data
```

HEIC 重点：

```text
mpvd
sefd
SEF
MotionPhoto_Data pointer
HEIF items
```

必须结构化定位 Motion Video，不能字符串命中后直接截文件。

## Huawei / Honor

理解：

```text
Still Image
+
Embedded MP4
+
LIVE tail
```

及可能存在的 movingphoto metadata / timed track / cover facts。

02A 只定位和提取，不清 tail / movingphoto metadata。

## Apple Live Photo

双文件：

```text
Image + MOV
```

Inspector 负责 pairing、still-image-time、cover、图片/视频格式与必要协议事实。

本阶段不删除 Apple Live Photo metadata。

# 9. 图片转换

优先包装现有能力，不为“全 C++”重写成熟 codec。

统一 API：

```text
ImageConversionRequest
→ ImageConversionResult
```

至少支持：

```text
JPEG → JPEG
HEIC → HEIC
HEIC → JPEG
JPEG → HEIC
```

### JPEG → JPEG

默认不重新编码像素。若像素与容器无需变化，优先 copy / structure-level operation。

### HEIC → HEIC

目标仍是 HEIC 时优先 copy / structure-level operation，不默认 decode → encode。

### HEIC → JPEG

基础路径：

```text
HEIC → decode → JPEG
```

尽量处理：

```text
EXIF
ICC
Orientation
Color Information
```

HDR / GainMap：

```text
能保留 → preserved
BestEffort 不能保留 → downgrade + record
RequirePreservation 不能保留 → fail
```

本阶段不扩建完整 HDR pipeline。

### JPEG → HEIC

基础路径：

```text
JPEG → decode → HEIC
```

尽量处理普通 EXIF / ICC / Orientation / Color Information。

Ultra HDR → HEIF GainMap 不作为本阶段门禁。

# 10. 视频转换

收口现有 `VideoTranscodeService` 等能力。

统一 API：

```text
VideoConversionRequest
→ VideoConversionResult
```

明确拆开：

```text
Inspect
Remux
Transcode
Normalize
```

## Remux 优先

codec 可保留时：

```text
MOV / HEVC → MP4 / HEVC
MP4 / H264 → MOV / H264
```

优先 remux，不重编码。

## Transcode

只有 codec 不符合目标要求时转码。

现有 FFmpeg / NVENC / AMF / QSV / VAAPI / libx264 / libx265 可继续使用。

这是 encoder fallback，不是 Legacy/Rebuilt fallback。

# 11. 通用 Converter 禁止厂商目标逻辑

例如：

```text
Apple all-I-frame
Huawei mp42 / iso2 / openharmony6
```

属于未来 Target Media Profile。

通用 Converter 不应该出现目标厂商判断。

如果当前通用服务里混有 target-specific 逻辑，识别并建立清晰 seam；不要为了本阶段强行大改 Legacy。

# 20. 完成标准

全部满足：

- Inspector 可独立调用；
- Extractor 可独立调用；
- Image Converter 可独立调用；
- Video Converter 可独立调用；
- GUI / CLI / Future API 可共用 Core capability；
- 新代码不新增裸 format index；
- Converter 无目标厂商协议分支；
- 底层能力不读取 backend settings；
- Legacy 未污染；
- source 只读；
- 关键路径有自动测试；
- `scripts/verify.ps1 -Scope Full` 通过；
- 最新 CI 通过。

# 22. Agent 完成后的动作

完成实现后：

1. 全仓检查重复的新格式逻辑；
2. 检查是否污染 Legacy；
3. 检查 backend bypass / fallback；
4. review git diff；
5. 运行正式 Full Verify；
6. 修复代码层面的失败；
7. commit；
8. push 当前分支；
9. 检查最新 CI；
10. 输出简洁报告：
   - 实际架构
   - 新增/复用能力
   - Inspector 覆盖
   - 转码覆盖
   - 未做内容
   - tests / verify / CI
   - commit hash

> **核心原则：先可靠知道来源是什么、图片在哪、视频在哪，再把通用媒体转换能力做成可复用基础设施；不要让 Converter 重新变成协议业务层。**
