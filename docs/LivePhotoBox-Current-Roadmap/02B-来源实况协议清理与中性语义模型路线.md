## 1. 中性媒体模型（Neutral Media Bundle）的真实语义

### 1.1 纠正“全部清空”的误区
旧规划中存在一种倾向：误以为“中性媒体”就是把来源厂商的元数据全部抹杀干净。**这是错误的。**

**中性媒体（Neutral Media）的真正定义**是：
> **后续目标协议写入器（Target Writer）无需理解来源厂商的私有物理封装与专有结构，即可获得完成目标实况照片写入所需的纯净媒体流、准确时间戳和来源语义。**

中性媒体不仅包含音视频与图像，还包含可安全继承的摄影事实与相机元数据。

### 1.2 中性媒体包包含的内容
`NeutralMediaBundle` 作为不可变数据契约，包含：
1. **`PrimaryImage`**：静态主图切片（已剥离来源专有实况标记，保留通用 EXIF / ICC / 相机数据）；
2. **`MotionVideo`**：动态视频切片（已剥离来源专有实况 track / uuid / mdta，保留正常音视频流与通用 creation metadata）；
3. **`GainMap / AuxiliaryMedia`**：HDR GainMap 或辅助图像（若存在，不干扰主图和视频定位）；
4. **`TimingFacts`**：从源实况精确解析的封面微秒时间戳 (`CoverTimestampUs`) 或关键帧索引；
5. **`PairingIdentifier`**：来源实况配对标识（如 Apple UUID、vivo ID，用于追溯或转写）；
6. **`SourceProtocolFacts`**：来源协议类型与不可变事实快照；
7. **`PreservationReport`**：元数据保留真实性清单；
8. **`SourceProvenance`**：源文件 SHA256 与路径溯源信息；
9. **`OpaqueMetadata`**：经安全性评估可安全保留的底层非实况元数据。

### 1.3 非透明元数据（Opaque Metadata）三级保留策略
对于来源文件中的未知或厂商专有元数据，严禁无脑全量复制，必须遵循三级处理原则：

```text
       ┌─────────────────────────────────────────────────────────────┐
       │                 未知 / 厂商专有元数据分类处理规则              │
       └──────────────────────────────┬──────────────────────────────┘
                                      │
         ┌────────────────────────────┼────────────────────────────┐
         ▼                            ▼                            ▼
  【第一类：安全且位置无关】     【第二类：包含结构引用】       【第三类：无法证明安全】
  例如标准 EXIF/ICC/MakerNote   包含 offset/size/track ID/   存在未知二进制结构、破坏
  中与实况协议无关的相机标记    item ID 等容器内部索引引用    容器合法性或可能冲突
         │                            │                            │
         ▼                            ▼                            ▼
  ─── Raw 逐字节保留 ───       ── 必须 Parse/Rebuild ──      ── 严禁盲目迁移/复制 ──
                              或在原容器保持合法位置
```

> **黄金守则**：  
> **Parse what we understand, Preserve what we don't, Remove only what conflicts, Do not relocate unknown structural data blindly.**  
> （解析已知结构，保留无害未知，仅删除冲突协议，严禁盲目搬迁未知结构数据）

## 3. 逐厂商 Native 协议清理规范

所有清理操作均必须在 C++ Native 执行（`LivePhotoBox.Native/src/protocols/`），且基于**二进制结构化定位**，**严禁仅凭 ASCII 字符串搜索盲目截断文件**。

### 3.1 Google MicroVideo V1 清理
- **结构**：JPEG + 尾部拼接 MP4
- **清理逻辑**：
  1. 通过 `GCamera:MicroVideoOffset` 定位视频边界并提取视频；
  2. 图片精确截断至 JPEG EOI (`FF D9`)；
  3. 从 XMP 中移除 `GCamera:MicroVideo*` 实况字段；
  4. 完整保留普通 EXIF、ICC、MakerNote 及其他 XMP 描述项。

### 3.2 Google Motion Photo V2 / 小米 清理
- **结构**：JPEG + `Container:Directory` (Primary + [GainMap] + MotionPhoto)
- **清理逻辑**：
  1. 解析 XMP `Container:Directory`，定位并切除 `Item:Semantic="MotionPhoto"` 对应视频；
  2. 从 XMP 移除 `GCamera:MotionPhoto*` 及 MotionPhoto Item 条目；
  3. 重建合法的主图（如存在 GainMap 则保留 Primary + GainMap，并重新计算 Item Length 与 Padding）；
  4. 小米 Ultra HDR GainMap 属于图像内容，严禁将其误判为实况私有数据删除。

### 3.3 OPPO / OnePlus O-Live 清理
- **结构**：Google V2 + `OpCamera` 命名空间 + `UserComment: oplus_*` + 可选 OnePlus 尾挂
- **清理逻辑**：
  1. 移除 V2 MotionPhoto Item 与对应 MP4 视频；
  2. 移除 `OpCamera:MotionPhoto*`、`OpCamera:VideoLength`、`OpCamera:OLivePhotoVersion`；
  3. 精确切除只服务实况识别的 `oplus_*` UserComment 标记；
  4. 如存在 OnePlus 尾挂数据，按已验证结构切除；普通相机 EXIF 完整保留。

### 3.4 vivo X300+ 清理
- **结构**：3-Item HDR JPEG (Primary + GainMap + MotionPhoto) + `VCamera`
- **清理逻辑**：
  1. 移除 V2 MotionPhoto 视频载荷与对应 Item；
  2. 移除 `VCamera:VMotionPhotoVersion`、`VMotionPhotoSource` 等实况字段；
  3. 移除 vivo 实况 UserComment 签名；
  4. 严禁因存在 `VCamera` 而整段删除 XMP，确保 Primary 与 GainMap 容器合法性。

### 3.5 vivo ≤ X200 双文件清理
- **结构**：JPG (`vivoMediaExtInfo` JSON 尾部) + MP4 (顶级 `uuid` box)
- **清理逻辑**：
  1. 图片端：定位并精确剥离 `vivoMediaExtInfo` 实况 JSON 尾部，恢复标准 JPEG；
  2. 视频端：解析 MP4 ISO-BMFF box 树，删除 vivo 私有实况 `uuid` box，并重新计算 `stco`/`co64` 块偏移；
  3. 若 JSON 中包含非实况通用相机标记，能安全重建则保留，否则记录降级说明。

### 3.6 三星 JPEG / HEIC 清理
- **JPEG (SEF 结构)**：
  1. 解析 SEF 目录，切除 `MotionPhoto_Data` (Tag `0x0A30`) 视频载荷；
  2. 移除 `MotionPhoto_Version` 等实况 Tag；
  3. 若 SEF 中包含其他非实况 Tag，保留并重构 SEF 头部、Tag Count、Offset 及 SEFT 尾部。
- **HEIC (`mpvd` 结构)**：
  1. 从 ISO-BMFF 盒树中移除 `mpvd` 视频盒与 `sefd` 私有盒；
  2. 修正上级 box 长度，保持主 HEIC 图像项与元数据 item 合法可用。

### 3.7 华为 / 荣耀 Moving Photo 清理
- **结构**：静态图片 + 嵌入 MP4 + 60 字节 `LIVE_` 尾部
- **清理逻辑**：
  1. 结构化定位嵌入 MP4，将其分离提取为独立视频；
  2. 删除 60 字节 `LIVE_` 尾部与 Moving Photo 专有参数（如 covertime、版本号）；
  3. 独立视频中清除 `com.openharmony.*` 实况 mdta keys 与 timed_metadata 轨；
  4. 荣耀私有防抖/EIS 矩阵不可盲目依赖字符串匹配切除，须按结构边界处理。

### 3.8 Apple Live Photo 清理
- **结构**：图片 (ContentIdentifier MakerNote) + MOV (ContentIdentifier mdta, mebx track)
- **清理逻辑**：
  1. 图片端：通过 Native 原位清理 MakerNote 中的 Live Photo entries (如 `0x0011`)，重构合法 MakerNote 块；
  2. MOV 端：移除 `com.apple.quicktime.content.identifier` mdta、mebx `live-photo-info` 轨与 `still-image-time` 轨，重构合法 QuickTime 视频。

## 4. 清理器工程约束与事务安全

1. **幂等性要求 (Idempotency)**：
   ```text
   Clean(Clean(media)) == Clean(media)
   ```
   对已清理或非实况媒体执行二次清理，文件字节与元数据必须保持语义和结构完全等价，严禁二次清理误删普通元数据。
2. **源文件只读与不可变性**：
   所有清理均在 `IMediaWorkspace` 临时工作区副本上进行，源文件在提取前后计算 SHA256，断言源文件绝对不发生修改。
3. **多产物原子可见性**：
   Apple / vivo 等双文件输出必须在 workspace 中全部成功并校验后，才通过 Publication Plan 提交至目标目录，严禁出现仅输出半对文件的损坏状态。
