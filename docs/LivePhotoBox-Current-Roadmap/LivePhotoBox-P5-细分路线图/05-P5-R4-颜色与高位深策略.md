## 1. 目标与边界

本轮冻结并兑现 ordinary image conversion 的 ICC 字节携带、颜色 metadata 映射、真正像素色彩变换，以及高位深输入的不同语义。上位要求见 P5 主 Roadmap、P5 总览、R0/R2、Neutral Media Contract 和 P4 冻结的 Native/backend 归属。

本轮只处理静态 JPEG/HEIC。视频、R5 dispatch、video backend、全局阶段验收与 P5 完成状态均不在 R4 修改范围内。不得修改 P4-v1 manifest、样本身份或 P4 backend decision。不得改 public Contract/C ABI、增加目标色彩空间/目标位深 API，或新增生产色彩管理依赖；若完成 Roadmap 所要求能力必须改其中任一项，本地 Implementer 停止并报告用户。

## 2. 冻结语义

### 2.1 三种颜色操作彼此独立

1. **ICC byte carriage**：将源 JPEG 的完整 ICC_PROFILE APP2 sequence，或 HEIF primary item 关联的完整 `prof`/`rICC` payload，逐字节保留到目标容器的 primary image。独立解析器必须按 JPEG marker sequence 或 HEIF primary item 的合法 property association 取出字节；文件中任意位置的字符串命中不算证据。`ColorIcc=Preserved` 仅表示 profile bytes 完全相同，不表示发生过像素色彩变换，也不单独表示 rendered pixels 保真。
2. **Color metadata mapping**：ICC 与 NCLX/CICP 是不同表示。R4 不从一个表示猜造另一个表示；只有确实实现并独立验证了一对一 mapping 时才可宣称映射。本轮仅保留 ICC payload；未知/缺失色彩描述不得被贴成 sRGB、BT.709、Display P3 或其他 profile。若源的已知颜色 metadata 不能按该路径表示，必须 fail closed 或在既有 BestEffort outcome 中明确记为丢失，不能把它写成 preserved/mapped。
3. **Pixel color transform**：只有存在明确的、backend-neutral target profile/space intent 并执行 source-profile → pixel → target-profile 变换，才可报告 `ColorTransform`。当前 `ImageConversionRequest` 没有该 intent；R4 不新增 public request/ABI。因而 Display P3→sRGB、PQ/HLG→SDR 等实际 transform 在现有 API 下不受支持。不得只改标签，也不得以同 ICC 复制冒充 transform。只有用户批准相应 Contract 变更并重新规划后，才能重新打开此范围；不得为本轮加入 lcms2。

### 2.2 位深

- JPEG codec output 与当前 Native HEIC encoder 为 8-bit。R4 不宣称跨格式高位深转换、量化或 tone mapping。
- 大于 8-bit 的 HEIC→JPEG 在 `Strict` 下按既有跨容器 policy 拒绝，在 `BestEffort` 下返回真实 `Unsupported`；两者均须在目标发布前结束，不能留下 staged/final artifact。
- 大于 8-bit HEIC→同容器仅可走 passthrough，并要求输出 SHA-256 与输入完全一致。该操作证明 bytes 未改，不证明转换或颜色正确性。
- `HdrOutputPolicy.AllowSdrDegradation` 属于 R3 HDR/GainMap authority，不授予普通高位深量化、色彩转换或丢弃色彩 metadata 的权限。

### 2.3 没有 ICC 的输入

输入 JPEG 无 ICC 时，R4 不允许 Native encoder 为方便而固定写入 BT.709/sRGB/NCLX。未知即保持未知；目标不携带虚构的 ICC/NCLX 标签。若输入包含 R4 没有冻结 mapping 的其他颜色声明，则该路径 fail closed。实现和独立验证都必须覆盖“没有源 profile → 输出未新增 profile/label”。

## 4. 独立 validator 与预先冻结的 render comparison

Runner: `python tools/p5-r4-color-high-bit-depth-validation/validate.py --manifest tools/p5-r4-color-high-bit-depth-validation/profiles/P5-R4-v1/manifest.json --workspace .ai-tmp/workspace/P5-R4 --evidence .ai-tmp/evidence/P5-R4`。独立离线 provenance/cache 检查：`python tools/p5-r4-color-high-bit-depth-validation/source_lock.py --mode verify --manifest tools/p5-r4-color-high-bit-depth-validation/profiles/P5-R4-v1/manifest.json`。Runner 应保存完整实际 argv、exit code、tool versions、每个 route 的 input/output SHA、所有 assertion 和 stdout/stderr 摘要。原样本只读；只从 deterministic sample cache 读取，工作副本固定在 `.ai-tmp/workspace/P5-R4/`；正式快照只写 `.ai-tmp/evidence/P5-R4/`。

独立实现不得引用 LivePhotoBox 产品 Writer/Reader 或其 parser：

- 自行扫描 JPEG marker，按 APP2 ICC sequence number/count 检查重复、缺段、越界并精确重组 ICC bytes；不得扫任意 offset 字符串。
- 自行解析 HEIF `meta/pitm/iprp/ipco/ipma` 关联，按 primary item 身份解析 `colr`，验证 ICC/NCLX property 数量、关联与 payload。重复、shadow、malformed 或不能证明唯一主图关联时 fail。
- 以 ExifTool 13.55 交叉检查 profile description、维度和 orientation，以 FFmpeg/FFprobe 8.0.1 独立解码与读取 HEVC bit depth/pix_fmt；解码必须实际退出码 0。JPEG 必须只有一个 FFprobe image/video stream。HEIF color render 由 libheif 1.23.2 `heif-convert` 的 default primary-image 路径完成；R4 自有解析器独立解析 `pitm`、item type、尺寸与 ICC association，并要求解码 PNG 的 primary dimensions/profile bytes 与结构结果一致。对可映射的 FFprobe HEIF stream，只在 stream `id` 数值等于独立解析的 `pitm item_ID` 时额外用 FFmpeg 解码；不允许按顺序猜 primary；无映射时使用已固定的 libheif primary 路径。产品自身检视仅作附加证据。
- Apple/Huawei P3 carriage route source 和 output 的独立 render 流程在转换前冻结于 R4-v1 manifest：JPEG 由 FFmpeg 8.0.1 以 `-noautorotate`、唯一 stream index、`-frames:v 1`、`-pix_fmt rgb24 -f rawvideo` 解码；HEIF 由 libheif 1.23.2 default primary-image path 解码为 PNG，并核对 parser 解析的 primary item 尺寸与 ICC bytes。两种 decoder 只做 codec YCbCr→RGB，不应用 ICC CMS；Pillow 只读 PNG RGB bytes。不得加 `colorspace`/`zscale`/`tonemap` filter。HEIF `pitm`/`ispe`/`irot`/`imir` 与 JPEG IFD0 Orientation、ExifTool Orientation 必须共同证明 primary、尺寸一致且方向为 identity；否则阻止该路线，不作旋转或裁切。解码后只应用一次 Pillow 12.1.1 / LittleCMS 2.17 ICC→sRGB (`relative-colorimetric`, black-point compensation off)，不再次色彩管理；严格尺寸相同，不做 crop/registration；然后两图用 Pillow `Image.Resampling.LANCZOS` 按同一公式缩至长边最多 1024，再用 scikit-image 0.26.0 计算 Lab/CIEDE2000。冻结阈值：mean ΔE00 ≤ 2.0，P95 ≤ 5.0，P99 ≤ 9.0。不得观察正式输出后调阈值。该阈值只界定高质量 lossy reencode 的明显色彩偏差，不证明 lossless，也不证明执行过 transform。
- 预期独立验证工具：ExifTool 13.55、FFmpeg/FFprobe 8.0.1、libheif `heif-convert` 1.23.2；Python env 为 Pillow 12.1.1 / LittleCMS 2.17、NumPy 2.5.0、scikit-image 0.26.0。实现前确认 Windows x64 验证环境可复现这些 validator 依赖；不得把它们放入 production。
- Nikon 10-bit sample 的 ICC/NCLX readers 存在 interpretation 差异；它只可证明真实 10-bit decode、拒绝跨容器输出和 exact passthrough。不得据此作 SDR rendering/colorimetric correctness claim。

## 5. Implementation guardrails

- C# 仅负责现有 request/policy/result 编排；Native C++20 负责媒体/字节路径。沿用已有 C ABI，不引入 RGB/float managed round-trip。
- 不新增 public Contract、ABI、target profile/bit-depth request 字段；不接入生产 ExifTool/FFmpeg/Magick.NET/lcms2。
- 在 Native encoder 中去掉“无 ICC 即写固定 BT.709/sRGB/NCLX”的无依据 relabel；profile、color property 只从受信且完整的源 representation 按已冻结规则保留。
- 把 HEIC >8-bit/HDR 识别映射成 truthful `Unsupported`，并尽量在 managed control plane 的 output allocation 前基于现有 `DecodeHeicPrimaryAsync` 信息拒绝；保留 Native 最后一道 fail-closed 防线。`Strict` 仍按 strict policy 拒绝，`BestEffort` 不得将 backend generic error 伪装成成功。
- 改动后保持 R2 ICC、metadata、orientation、passthrough 与 strict no-publish regression。

## 7. R4 acceptance

1. ICC carriage、metadata mapping、pixel transform 语义可区分且无 relabel；
2. 10-bit cross-container conversion fail closed，10-bit passthrough byte-identical；
3. 所有 matrix route 都有 hash-locked RealSample、独立验证与真实 no-publish assertion；
4. render assumptions/阈值在正式转换前冻结，独立 parser/decode/render 通过；
5. R2 regression、R4 targeted builds/tests、R4 RealSample runner、doctor、diff check 全部成功且零 RealSample skip；
6. 无 P4-v1 manifest/identity 变化，无生产外部 CLI、managed pixel math 或新增公共 Contract/C ABI。
