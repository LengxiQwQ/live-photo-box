# P5-R5 — Video Converter Reliability

> 本文细化 P5 总路线与 R0/R1 的视频要求，不改变 Converter Contract、P4 backend freeze、样本身份、阶段顺序或验收标准。实现者只能在本轮 TASK 范围内施工；只有用户或外部 Chief Gate 可接受阶段。

## 1. Owner 与语义

继承 P4-R6 已冻结的 Hybrid，不重新选型：

| 请求能力 | 唯一 owner | 约束 |
|---|---|---|
| Copy / 同 codec 容器整理 | LivePhotoBox Native 的 project-owned ISO-BMFF remux | Codec packet payload 不得改变；外部 parser 独立复核容器、packet、audio 与 timing。 |
| 普通 SDR 跨 codec | Windows Media Foundation，software-forced | Native 预分派后只调用一次；不启用硬件转换，不因失败而换 backend。 |
| HDR、10-bit 或必须保留 color/HDR 的跨 codec | 已冻结 minimal-libav capability sidecar | 选择必须发生在转码前；必须独立验证输出精度、CICP、audio、rotation 与 timing。sidecar 不可用或不支持时 Unsupported/BackendUnavailable，无 MF 重试。 |

C# 只编排 backend-neutral request/result；视频 bit-depth、ISO-BMFF sample-entry/CICP 事实及 Native dispatch 留在 C++20。生产包只包含静态链接的窄化 sidecar，不包含 `ffmpeg.exe`、`ffprobe.exe`、网络或通用 FFmpeg runtime。

`VideoConversionRequest`、公开 Converter Contract、`livephotobox_native.h` 的函数签名与 POD 布局均不变。允许新增私有、版本化 Native-to-sidecar C ABI：只用固定宽度/POD、UTF-8/UTF-16 缓冲区或受控回调、明确结果码；不跨边界传 C++ 类型、异常、codec 对象或像素面。禁止增加公开 `VideoBackend` / C ABI enum 值。minimal-libav 的精确 backend 名称、版本、能力、profile 和 hardware mode 记录在已有 canonical `ConversionExecutionTruth` 字段中。若任何必需语义无法在这些边界内实现，停止并向用户报告，不自行扩展公开 Contract/ABI。

## 2. 固定操作与 policy 规则

- 按实际输入、目标和输出证据区分 `Passthrough`、`ContainerRemux`、`LossyReencode` 与 `Unsupported`。`Copy` 或 codec 相同本身不证明 passthrough；只有字节完全一致才可报告 passthrough。否则如确有 box 重排则报告 remux。
- 当前 CRF 转码按 lossy reencode 报告。不得仅因 decoder 能打开输出或产品 probe 读回成功声称无损/Preserved。
- 以 Native 对 ISO-BMFF sample entry、codec configuration、bit depth、`colr`/CICP、rotation 和相关 timing 的唯一且有效解析结果预分派。大于 8-bit 或显式 PQ/HLG 等 preservation-critical 信号选择 minimal-libav；明确普通 8-bit SDR 才选择 MF。未知、互相矛盾、重复、越界或解析不完整的 preservation-critical 事实必须 fail closed，不能猜作 SDR。
- HDR/10-bit 请求没有独立显式的 SDR degradation authority。BestEffort、Strict 或 `AllowDiscard` 均不得授权静默降到 SDR。不能满足目标 codec 的 bit-depth/color 语义时返回 truthful Unsupported 且无 artifact。
- `TargetFps > 0` 继续在创建输出前 Unsupported。所有 backend failure、取消、后验验证失败及 publish failure 必须清除本轮拥有的 staging object，不得留下 final 或半发布 artifact。
- `Strict` 对 request/format contract 要求保留的组件逐项校验；`BestEffort` 可报告实际发生的 `Reencoded`/`Lost`，但不得谎报保存或降级。用已有 truth 的 `Pixel`、`Metadata`、`Audio`、`Timing`、`Orientation`、`InputProfile`、`OutputProfile`、capability、backend/version 与 failure 字段表达结果，不扩展公开类型。video 的 CICP/bit-depth profile 不冒充 ICC 或 GainMap。

## 4. 独立验证与失败覆盖

独立 runner 使用冻结版本的非产品媒体 parser/decoder（例如正式 profile 指定的 FFprobe/FFmpeg）；这些工具仅限离线验证，不进入 production。验证假设和阈值先写入 manifest，运行后不可为绿灯改宽。至少独立检查：

- container、codec/profile/pixel format/bit depth、video sample entry 和 CICP primaries/transfer/matrix/range；
- packet timestamp/time base/duration/VFR、整体时长、rotation/display matrix；
- audio stream、codec、channel/rate/duration 与每条路线的 packet-copy 或 reencode 结果；
- 对 remux，分别提取 video 与 audio packet 并比较逐 packet SHA/顺序/timing；
- 对 reencode，执行独立 decode，并按冻结公式核验实际 profile、stream 数量、时序、音频及显示方向；
- output 文件是否存在、是否有意外 stream/metadata、失败后无 final/staging 残留。

另外覆盖 TargetFps Unsupported/no-output、实际缺少 sidecar 的 BackendUnavailable/no-MF-retry、Malformed/ambiguous sample-entry/CICP fail-closed/no-output、取消和 output validation/publish 失败清理。攻击性 synthetic/fault-state checks 只覆盖状态机，绝不替代必需 RealSample matrix 或独立 decoder evidence。

## 5. Runtime、legacy façade 与分发

- 从 P4-R6 frozen source/config 复现 FFmpeg `n9.0.1` minimal static feature set，固定源码 SHA-256 `195D54BEBE1A27F84D77F4B989D193466F305B355DA92292766A69F16880B18A`、x264/x265 来源与 vcpkg baseline；保留 `--disable-everything`、无 program/network/shared library 的约束。完整 source/build scripts 与对应 GPL notice 随仓库/包提供。license/patent/distribution 结论只按证据报告；P4-R6 标明尚未解决的 H.264/HEVC 专利义务不得写成已获法律批准。
- root x64 build 产出 sidecar 并让 Core/App package 将其放在 Native DLL 旁；runtime 只按已知 exact sibling path 加载，验证 ABI/version 与 hash/imports。sidecar 缺失时只有对应高位深 capability 不可用，不能全局切回 MF。
- sidecar 写入 Native 拥有的 staging transaction，由 Native 负责结构复读和 no-replace publish；具备 cancellation/cleanup，不能直接覆盖最终用户路径。
- 修复 `VideoTranscodeService`：`RemuxAsync` 明确请求 Copy，`"copy"` 不映射 H.264，`WasRemux`/`WasTranscoded` 源自 canonical execution truth，失败时为 false；`EnsureMp4Async` 和 caller-named output 的最终发布遵守 no-partial-output。保留既有 public signatures。

## 6. R5 closeout

只执行 R5 及实际受影响的 Native/Core/CLI 验证，不运行全项目 suite。至少要求：Native + sidecar Release x64 build；所有 `P5R5_` Core/CLI/Native runtime filters；`tools/p5-r5-video-validation` 完整 RealSample runner 0 skip；canonical Huawei extraction；package contents/imports 检查；missing-sidecar/no-retry/no-partial-output 检查；`.ai/doctor.ps1 -ActiveOnly`；`git diff --check`；检查 P4-v1 manifest/hash 未变化。每个逻辑单元真实记录 argv、exit code、文件与输出。

正式 evidence 只写 `.ai-tmp/evidence/P5-R5/`，至少绑定：manifest/profile/工具与阈值 hash、源/派生 identity、精确 HEAD 与 dirty diff identity、build/source/package/import hashes、每条 route 的 request/selected/actual capability/backend/version、独立 validator 原始结果、所有 skip/blocker 计数及失败清理结果。

Implementer 的完整本地 PASS 只可报告 `READY FOR FRESH EXTERNAL VERIFICATION`。不得把 R5/P5 标为 accepted/completed，不得进入 R6，直至本轮外部验证 Gate 按 authority 明确通过。R4 外部 transition verification 已 PASS；这不构成 P5 ACCEPT。
