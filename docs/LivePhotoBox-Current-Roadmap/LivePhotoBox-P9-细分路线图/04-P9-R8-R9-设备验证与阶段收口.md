# P9 R8–R9：设备验证与阶段收口

当前执行依据：[收尾计划入口](协议收尾执行计划/00-从这里开始.md)。2026-10-30 最新测试节奏统一见其 03：完整单元完成后实际 CLI 验证、失败局部重测、收口复用有效结果；本页不另加逐单元测试/审查。兼容档 A/B 取舍按其 01，下面“保留/编辑”要求按对应轮次适用，不把 B 轮要求提前阻塞 A 轮。历史正式结果不改写。

## R8

先完成 CLI 候选与公共服务，再依次完成小米/Google、OPPO、Apple、旧 vivo，然后商场组新版 vivo/Samsung/Huawei/Honor，最后 Fusion。具体顺序、缺设备处置与全部覆盖按[实施顺序](协议收尾执行计划/01-实施顺序与完成条件.md)。

每个目标的正式完成条件：全部真实来源及必需格式/版本实际转换；新结构化 Writer 与 fresh reopen Validator；独立媒体和保留证据；A 轮实况识别/完整流畅播放/声音/方向/封面及适用编辑；B 轮 HDR/色彩/辅助内容/普通 metadata；实际 CLI/GUI/结果与历史接入；无范围内 blocker；必需 fresh 独立复核通过。

A 轮可以在详细 HDR 验收前交付，但基本结构、完整媒体、源不变、已知数据损失回归不能延期；输入 HDR 等仍在完整来源/变体清单。A PASS 不能写 Production Ready。正式候选先接 CLI 与将来发布同一路径，不是临时脚本入口或校验旁路。

所有已准备成品在一个平铺目录，文件名标来源/目标协议和格式，每个当前目标完整交付；见[交付规范](协议收尾执行计划/02-真机交付与反馈.md)。机型/系统/相册/导入方式及文件身份随实际测试记录，不能因为未预先填表而拒绝交文件，也不能因此捏造设备证据。

缺设备保持待验收，尤其 X200 与 X300、Huawei 与 Honor、Google Photos 与厂商相册、Samsung mpv2/mpv3、JPEG/HEIC、不同编码不能互相代签。用户可到商场/手机店测试不表示每一型号已就绪。Fusion 按最终明确的设备/协议集合分别验证。

## 证据与失败

Unit/Mock/Synthetic、原始 RealSample、IndependentValidation、实际文件系统失败、CLI、GUI 和 RealDevice 分层记录。正常来源拒绝/无输出/缺覆盖均未完成，不是负例成功。脚本可调度 CLI 和独立检查，不可生成/补丁修改真机交付媒体。

最终候选身份须覆盖源码 dirty diff、实际 CLI/Core/Native、输入与输出成员及选项。共享能力变化后补测所有受影响目标；输出字节或行为变化后重新判断设备证据适用性。只复用有效旧证据，不能拼接不同版本的绿灯。流水与运行明细放 workspace，正式封存 create-only，不改历史失败。

## R8→R9

- R8 在全部范围完成转换、设备两轮及产品集成后，汇总最终结果并补失效/缺失检查；按 03 做最终 Review 与另一 Verify，前者审最终实现风险，后者核对候选身份、覆盖及未关闭事项，不重复跑全部测试或逐行审查。完成必要环境/规则检查并写回真实状态。
- R9 对最终候选逐条核对正式 P9、全部目标/来源/变体覆盖、缺样本与缺设备账本、设备适用性、旧写入入口退出、RELEASE-004 实际关闭条件及必需 Review/Verify。新变更影响证据时补受影响检查，不能仅抄 R8 结论，也不无理由重做全部历史测试。
- 按现有正式 R 交接要求由新主负责人接任 R9；不得由参与候选修改的上下文冒充独立验收。普通 S 单元不自动创建新聊天。
- 所有必需条件满足才更新 P9 complete。P10、无关编辑导出、其他发布问题和最终全产品总验收保留各自边界。本文不新增提交推送或发布授权。
