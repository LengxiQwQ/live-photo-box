# P9 R1：目标写入接口决策

2026-10-25。**PROPOSED / IMPLEMENTATION_PENDING_USER_DECISION**。用户已授权R1；本决策只请求完成R1所需的公开Native接口与独立Writer授权，不授权R2或后续厂商施工。Fusion仍延期，每R完成报告后须用户确认下一R。

## 为什么需要决定

当前C ABI版本为12。`lpb_jpeg_inject_xmp`、Apple MakerNote/MEBX、Samsung SEF builder等生产入口受`lpb_has_clean_authority`保护，只能在已核准的CleanupPlan执行中使用；相关TestHarness入口不属于生产能力。NeutralBundle已经结束来源清理，目标Writer不能重新借用来源clean token，更不能关闭检查。

当前Merge仍通过C#复制/模板写入，无法靠现有公共API把完整Neutral artifact身份、角色/关系、目标profile、允许的改动范围和单次执行授权传到Native真正写入位置。只加managed DTO或只修改内部parser不能完成R1的生产边界。

另有旧公开入口并非都已具备clean gate：Huawei的MP4/HEIC改写和vivo旧格式metadata rewrite仍是公开buffer mutation；部分managed Apple/vivo工具即使当前GUI/CLI不调用，也可经public方法改写任意路径。R1不能把“目前没有调用”当成安全关闭，亦不能擅改其对外行为。

项目AGENTS 0.2和本目录02明确要求公开Contract/ABI、安全边界变化先说明影响取得用户决定。因此本页是可审阅的接口方案，尚未修改production header、Native实现、managed互操作或测试，也没有构建/产品测试结果。

## 推荐方案：增加独立、版本化的目标写入入口

在现有Native库增加目标写入专用opaque plan；现有clean/extract API和POD布局保留，不给它们添加“通用跳过校验”开关。所有新增接口C ABI、POD/显式长度/结果码，无C++类、异常、COM或Windows HANDLE穿过公开边界。

拟议入口职责（最终声明/尺寸/枚举在获准后冻结并做布局与ABI测试）：

| 拟议v1入口 | 作用与约束 |
|---|---|
| `lpb_target_writer_prepare_v1` | 从Neutral artifact manifest和OutputProfile建立Native拥有的只读快照/lease、校验身份/媒体/关系，签发context-bound opaque plan；拒绝未知/冲突/重复角色、非法目标、身份不符和未经允许的损失 |
| `lpb_target_writer_stage_v1` | 单次执行plan；在真正mutation site前复核完整authority与输入/输出身份；只写该次创建的受控staging，不发布用户目标；未接通协议返回明确Unsupported，不生成虚假成功 |
| `lpb_target_writer_get_outputs_v1` | 查询实际创建的staging artifact身份/长度/哈希和语义结果，失败也能取得归属证据；不是从路径猜测，也不等于TargetValidator通过 |
| `lpb_target_writer_read_stage_v1` | 从Native持有的已封存stage分块读字节到显式buffer；C#只搬运到publisher自己创建持有的stage，并验证length/hash桥，不按路径接管陌生对象 |
| `lpb_target_writer_release_v1` | 释放plan、leases和仍由该plan拥有的临时对象；消费/失败/取消后的重放拒绝；不能清理源或foreign对象 |

API职责和上述名称是最小设计候选，不是已实现接口。prepare/stage/get_outputs/release的确切拆分若在实现前设计复核中需要合并或补充，只能在同一已批准职责范围内调整；改变授权、保留策略或公开兼容承诺则重新提交决定。

请求内容至少包括：

- `struct_size`/API版本、target/version、媒体格式要求、Strict/BestEffort策略；只传目标typed语义，不用UI index或SourceProvenance选布局。
- Artifact数组：角色、stable identity、长度/SHA256、容器/codec、owner/relationship、embedded/detached及同一asset映射、必要selector/semantic范围；文本UTF-8显式长度，有上限、深拷贝，不保留调用者临时指针。
- 可信Neutral时间、方向、颜色/HDR/GainMap/auxiliary及保留状态，未知保持未知；不能默认时间为0、不能看见GainMap文件就再次追加。
- 受控输入/输出I/O定位与事务范围。路径只是Windows适配信息，实际身份/leases通过P4平台原语建立；plan绑定context/generation/request fingerprint并由Native校验，调用者填写hash不能自行证明authority。

Native状态机：prepare成功→issued→单次claim（早于参数/取消/输出分配）→stage写入或受控失败→consumed→release。stale/replay、foreign context、替换、TOCTOU、回调重入、重复/shadow结构和partial action均fail closed。外部回调期间暂停mutation capability，不让回调借用授权。每个步骤有异常边界和资源退出证明。

只对当前profile允许的目标改动授权；来源Cleaner字段不能机械搬作目标owner。新增Writer scope不扩大旧clean token的作用域。非live metadata默认保留，无法表达的内容由Strict拒绝或按已批准的BestEffort语义报告，不能借新接口授予任意删除权限。

## 与现有发布机制及后续阶段的关系

Windows输出仍使用现有owned transaction/publish/rollback原语。Native只生成受控staging和实际归属证据，C#负责产品编排。优先通过read_stage分块搬运到publisher创建句柄持有的stage：两个文件对象可以不同，但完整length/hash与artifact角色必须一一绑定；writer视图关闭/flush后封存，保留guarding handle与后续R2验证位置，commit再次校验。不得关闭Native句柄后按路径猜测接管，也不得在尚未flush的writer callback里用假Validator过关。

R1搭好模型、authority与共享结构基础，并验证拒绝/资源/事务边界；R2才实现独立fresh TargetValidator门禁，各厂商Writer仍在R3/R4/R5/R7。没有厂商完整规则和后续验收前不得切换产品或宣称正式支持。R1不会通过新入口先发布未验证目标，也不会提前修RELEASE-004后冒称整个P9通过。

本次另请求批准旧mutation入口的有限安全收口：保留公开函数/方法签名，不删除公开符号；旧入口不获通用Writer开关，新的Writer只调用有完整scope验证的内部结构helper；不满足该旧入口适用原生授权的调用，在真正mutation前返回明确AuthorityViolation/NotSupported（managed为明确失败或NotSupportedException，具体原有返回形状适配，不伪装success）。范围包括未gate的Huawei/vivo公开Native字节改写和实际可自行改文件的旧Apple/vivo等managed utility；最终逐符号清单与产品调用影响在实施前冻结、fresh设计审查。只读parser/observer和现有合法plan-authorizedclean路径不受封闭。

兼容影响：外部直接调用这些旧写入工具会由原先可能成功变为明确拒绝；这属于行为变化，不能说完全兼容。若实际产品路径仍调用某入口，必须先完成合法迁移或保留显式旧adapter归属，不能一刀切导致未授权产品回退。用户若只批准新ABI而不批准本项，相关旧入口仍待决定，R1不能宣称已封闭全部旁路。

当前只读查得的具体候选清单：Native `lpb_huawei_patch_mp4`、`lpb_huawei_patch_heic_ftyp`、`lpb_vivo_rewrite_image_metadata`、`lpb_vivo_rewrite_video_metadata`；Core旧公开写入方法所属 `AppleMakerNoteWriter`、`AppleLivePhotoMebxWriter`、`AppleLivePhotoMovBuilderV2`、`VivoDualFileMetadataWriter`、`Mp4MdtaKeyStripper`。只封写方法，不封只读观察。另有internal `HeifAuxImageWriter`、`UltraHdrJpegWriter` 与TestHarness wrapper，不得成为新生产写入后门；移动/移除须确认测试与产品实际引用。本清单外发现新的公开兼容影响时先追加具体说明，不按“等”字无限扩大授权。

连续工程授权后的具体补充核查：`lpb_mp4_strip_uuid_box`、`lpb_mp4_strip_stsd_tracks`、`lpb_mp4_strip_mdta_keys`也是旧公开buffer mutation；当前未查到GUI/CLI生产调用，只有旧wrapper/测试链。纳入同类未授权入口校验，保留签名/合法Clean内部路径和Harness算法测试；若实际产品调用调查推翻该前提，先报告功能影响再决定，不直接切断。普通死入口安全收口不再逐项请求确认。

## R1与逐厂商替换的边界需要同步澄清

原细分02写R1完成即“无托管数据面旁路”，但正式P9 §10要求新Writer/Validator/样本/设备接受后才切换并移除对应旧Writer，R3起才施工厂商语义、R8才做设备/切换。因此R1不能提前将现有厂商Writer全部替换或禁用，也不能新增一套未接线foundation就宣布整个生产目标链已完成。

推荐明确R1完成条件为：新Native共享结构/独立authority/安全事务基础可被首个协议族调用，新增入口无旁路；旧公开任意mutation工具按批准清单封闭或受控迁移；现有厂商旧Writer只在明确existing-adapter中登记为后续待替换，无自动fallback或P9正确性声明。每个新目标实际生产接线与旧实现退出仍是对应厂商R及R8必需验收，R9必须确认全部范围内旧旁路清零。这修正的是细分计划的阶段分工冲突，不更改正式P9的完整生产验收。

只读设计审查也提出另一种分法：R1直接迁移现有Merge的共同字节拼接，再在R3+完善厂商语义。这会提前改变实际输出/拒绝行为，且必须同时处理已知duplicate-XMP与尚未实现的结构；不能为了兼容复制已知缺陷。主代理推荐前述“基础先就绪、逐家完整验证后切换”，与正式§10顺序一致；但这是细分计划完成条件的澄清，需当前用户明确同意，未决定前不自行修改02的完成条件、不宣称R1已完成。

用户批准此边界后同步02/05/TASK，保留旧文本的决策解释。若用户希望R1直接完成所有生产Writer迁移，将与逐厂商施工和逐R确认安排冲突，须重排后再实施，不能由代理暗自跨R。

## 影响、兼容与验证

推荐Native ABI **12→13**，同步本仓库C#互操作期望、Native header/导出清单、上下文版本检查和布局测试；旧POD不改。当前版本检查是精确匹配，因此新旧Core/Native混放会明确拒绝，必须成套重建/部署，不能称“旧二进制无需更新”。CLI/GUI用户操作、文件格式承诺和依赖集合不因接口增加而改变；不新增生产依赖或外部媒体CLI。

影响文件类别：Native公开header、foundation context/plan lifetime、target-writer内部实现与平台I/O接合、CMake source清单、Core NativeMethods/NativeContext及目标adapter接合、targeted ABI/authority/结构/事务测试。具体文件与调用链在R1执行清单冻结，未纳入新产品选项、Fusion、编辑器或后续R。

验证包括生产DLL的未授权/错context/错身份/重放/取消/回调重入拒绝，POD尺寸/版本/缓冲区上限/异常边界，合法结构的原始样本工作副本与非live保留，owned staging/foreign/source不变、真实适用share-lock/非可写失败、回滚/释放。Mock/injection单列，只验证状态机；不代替真实故障。实际命令/filter/数据行先discovery资格检查，再运行R1有界验证；fresh设计审查和实际候选独立复核都必须完成。

## 另一选择及建议
