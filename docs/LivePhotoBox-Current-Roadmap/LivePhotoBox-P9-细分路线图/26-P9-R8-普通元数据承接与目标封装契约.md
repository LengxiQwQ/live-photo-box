# P9-R8 普通元数据承接与目标封装契约

依据：当前用户已批准 [兼容承接接口](25-P9-R8-普通尾部数据承接决策.md)。本契约保持 N9 默认保留、来源清理权限及事务规则，不增加生产依赖，不授权丢数据、额外边车成品或原厂编辑功能承诺。实现和设备验收状态由 TODO 记录，本文件不是通过证明。

## 来源、Neutral 与所有权

来源侧只从已验证资源的 EOF 观察自相对目录，不搜索任意位置的 JSON 或 marker。末尾 LE32 长度包含目录 JSON、NUL、四字节目录标记及长度自身。目录记录闭合为 name/offset/length/version1，offset 从目录起点向前计；名称唯一、范围有界、整体无重叠和空洞。名称和 payload 不赋予文件访问或删除权限。来源布局另外核对完整视频与普通记录分界；跨末尾 `comm` 的记录必须整体承接，不能凭 VideoLength 截断。

Native `lpb_extract_media_with_plan_outputs_v3` 的新 descriptor 为24B，path 位于16，字段为 size/version1/carrier index/reserved0/path。它只绑定已有 Inspector-owned carrier，不接收调用方范围。实际输出角色 `MetadataCarrier=5`，与主图、视频和辅助媒体共用源租约、身份/hash、create-only 事务、创建回执和回滚。旧提取接口不得忽略未承接记录；旧 carrier facts 仍464B。

Neutral 普通元数据采用独立 `OrdinaryMetadata` manifest 角色与语义集合，不能混作 GainMap、Original 或其他辅助媒体。当前 codec 语义为 `OpaqueCameraRecords` / `self-relative-record-directory-v1`，owner 为 `primary:0`；实际 materialized artifact 必须具有可追踪的创建身份、完整长度/hash。语义图不保存路径、Windows identity/handle 或来源品牌。最终观察固定实际记录文件及祖先路径，核对全过程不允许写入、删除或换对象。

## 目标封装 v1

只有实际容器、普通元数据 codec、owner 和最终语义身份决定通用处理；来源协议、品牌、型号、路径和样本 hash 均不能选择目标分支。

namespace 为16字节 ASCII `LivePhotoBoxMDv1`。每个分块头为80B，整数为 big-endian：namespace[16]、version1@16、kind1@20、flags0@24、primary owner index0@28、完整 raw length u64@32、完整 raw SHA256[32]@40、chunk index u32@72、chunk count u32@76。单块总 payload 不超过65533B，最大 raw 32MiB；分块数量、顺序、每块长度、完整 hash 与内部记录模型必须一致。未知版本/flags/owner、重复/缺失/插入/重排或损坏均拒绝。

- JPEG：使用 primary 编码扫描之前连续的一组 APP15 marker。保留所有原主图、普通 metadata、辅助图与压缩扫描字节，只根据合法 MPF 所有权更新 primary 自身尺寸和布局。完整单图、无外部关系的既有 singleton stale-size 规则继续适用；不能把它扩给多图或未知 MPF。
- HEIF：使用 namespace 标识的单个合法顶层 UUID box；其 body 为 version1/count 及逐块 length/payload。原 item graph 与媒体 extents 不移动；存在最终普通 SEFD 时，UUID 位于它之前，完整 SEFD 原字节保持且仍为最后一个 box。Writer 必须先验证输入图和 owner，framing helper 本身不建立媒体有效性或写入权限。

不解读 raw payload 中的路径，不打开关联文件，不运行原厂编辑指令，不把其中的视频或字符串当成新的 live binding/append 权限。保留原始字节及自相对关系不等于其他品牌相册能使用原厂编辑功能；这一点必须如实区分。

## 兼容 Writer / Validator 接口

`lpb_target_writer_prepare_v4` 显式接收普通元数据 descriptor：size/version1/kind1/owner index0/flags0/reserved0、stable identity/owner/semantic/relationship 和实际 materialized artifact。Native 从实际租约核对物理身份/hash、完整记录模型、重复嵌入与所有者，把身份及语义纳入 fingerprint；真正 stage 前再次核对。旧 Writer v1–v3 的接口与 scope 不变，不作自动 fallback。

`lpb_target_validate_v4` 使用显式 kind/owner/length/hash 期望，重新观察成品中的合法 APP15/UUID owner，重建全部 raw records 并逐字节/hash核对，同时执行原有目标结构、媒体、时间、方向及辅助资产检查。新增 result v3 的普通元数据状态与实际 hash/长度/分块数/容器单独返回；只有全部检查成功才给出普通元数据 verified 状态。原 result v2 的全局 preservation/device 字段含义不变，不借普通字节通过宣布整协议或设备通过。

初始 v4 能力边界为一个 primary-owned 普通记录块、至多原有两个辅助媒体资产；Google V1/V2/OPPO 目标按实际适用容器验证。普通记录与 compound opaque primary 的组合、其他目标和更多 codec 未实现时必须明确失败，继续记为正向覆盖缺口。不得据此削减 P9 的全来源、全部适用变体和全部目标要求。

## 验收边界

需要原始来源 → Native 创建产物 → Neutral → 正式 CLI 成品的完整独立字节账； malformed/重复/别名/对象替换/重放/回滚及旧接口兼容验证；最终候选受影响聚合、fresh Review 和另一 fresh Verify。普通记录封装定向测试不代替完整 CLI 成品、GUI、播放/声音/方向/封面和 HDR 等设备 A/B 验收。运行细节和二进制仍放 R8 工作根，不能把源码文档当原始 evidence。
