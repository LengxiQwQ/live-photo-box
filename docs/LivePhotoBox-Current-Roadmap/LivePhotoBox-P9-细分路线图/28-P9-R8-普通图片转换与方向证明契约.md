# P9-R8 普通图片转换与方向证明契约

本契约落实[27 的当前用户决定](27-P9-R8-图片换格式与实际方向决策.md)。它定义兼容的新图片转换通道，不能追溯扩大旧接口、旧 HDR/XMP kind2/3 或旧运行结果的证明范围。阶段、真实设备和独立验收要求不变。

## 转换与结果含义

新 `lpb_convert_image_v2` 是绑定真实输入身份/hash 的单次转换事务。Native 保留来源文件及祖先目录的只读租约，核对实际结构与适用性，在私有内存中完成像素和 metadata 映射、实际输出重读及完整解码，再通过自有创建句柄完成 create-only、flush、无覆盖发布与结果绑定。失败不返回成功证明，不覆盖来源或既有目标；无法确认回滚须报清理失败。

初始有限能力是普通 JPEG→HEIC、8 位 RGB 表示。已知旋转/镜像按实际像素处理，输出不依赖有效旋转/镜像标记。Exif 根方向与适用尺寸、明确主图 subject 下的 XMP 方向/尺寸及单一 Primary 的 MIME 只允许按结构定位的窄范围映射；其他普通字段原字节承接。`rdf:about` 非空、匿名或嵌套资源上的相关字段不能凭数值相等当作主图。未清理的实况绑定、方向不明/冲突、HDR/GainMap、未支持的辅助图、CMYK/YCCK、扩展 XMP、未核对的缩略图方向及不能正确映射的活动坐标/编辑配方必须明确拒绝。

根方向正常时仍检查 Exif 缩略图的方向和实际 JPEG；根方向需要变换而缩略图尚无完整变换证据时拒绝。Exif SubjectArea/SubjectLocation、活动 Camera Raw 编辑配方需要独立几何映射，不能在旋转画面后原样保留旧坐标并签完全保留证明。此处的拒绝不是整协议完成条件，也不授权删掉这些数据。

当前用户批准的这条路径可以在全部必需、适用的保留组件有完整证据时生成成品。执行记录必须同时明确 `PixelReencoded=true`、实际 `LossyReencode`，不能把组件保留汇总解释成图片编码原字节未变。旧普通转换接口的恒定 partial/跨容器拒绝与旧有限 P5-R2 证据保留原义；本次演进不把其结果追溯升级。不能以该兼容通道为由降低其他保留/独立/设备门槛。

## 兼容 C ABI

入口为 `lpb_convert_image_v2(context,input_path,output_path,request,proof)`。跨边界仍仅使用 C ABI、POD、显式长度、结果码；不增加生产依赖或 C++ 类型/异常跨边界。

| 请求 `lpb_image_conversion_request_v2` | 偏移/规则 |
|---|---|
| `struct_size`, `api_version`, 来源容器、目标容器 | 0/4/8/12；精确96B、版本2 |
| quality、orientation_policy | 16/20；质量1–100，策略1为实际像素方向归正常 |
| expected_identity | 24，32B；卷、file ID、长度、单一 link |
| source_sha256 | 56，32B；实际来源全文件 |
| reserved0/reserved1 | 88/92，均0 |

| 证明 `lpb_image_conversion_proof_v1` | 偏移/规则 |
|---|---|
| size/version/kind/flags | 0/4/8/12；精确240B、版本1；kind1/flags1仅为完整支持的普通主图映射证明 |
| source/output SHA256 | 16/48；各32B，绑定实际来源和已发布的精确产物 |
| mapped_source/output metadata SHA256 | 80/112；各32B，必须相等；前者明确包含已授权方向/尺寸/容器映射，不能当作原始 TIFF 未改变 |
| source/output length | 144/152；各u64 |
| source/output orientation、operation | 160/164/168；来源1–8、输出1；operation1原样、2无损 DCT、3像素重编码，初始实现3 |
| metadata/ICC/orientation status | 172/176/180；1为适用且验证，2为证明不存在；方向必须1 |
| source/output width/height | 184/188/192/196；与实际编码/变换关系一致 |
| metadata_count/reserved | 200/204；当前最多4种 carrier，保留字段0 |
| output_identity | 208，32B；绑定实际创建句柄及发布对象 |

非空 proof 至少提供4B大小头。失败只清 `min(声明容量,240)` 的已声明范围；仅在容量足够时保留 size/version，不读写声明范围外字段。仅精确240B/版本1可成功。缺失新入口的旧运行库不能退回旧 API 后伪报这个证明。

Core 从 Native 创建记录取得实际产物身份/hash，验证全部证明头、状态、来源/产物、尺寸与 metadata 摘要关系，并将输出租约保留到结果交接完成；清理前释放本方租约。新增 `ImageOrdinaryConversionEvidence` 是独立契约，不占用旧 `ImageMetadataMappingEvidence` 的 kind2/3 含义。

## 普通 JPEG 附加记录

Exif、标准 XMP、完整 declared ICC 使用实际 HEIF owner 表示并逐字节重读。不能主动解释为当前 HEIF 结构的普通 APP/COM 记录，以及 ICC 分段超出 declared profile 的原始填充，保存在独立顶层 UUID `LivePhotoBoxIMv1` 中。它记录的是图片转换输入的 JPEG 上下文，不冒称是整份原厂实况文件。

UUID usertype16B 后为 BE version1/reserved0、JPEG length u64、JPEG SHA25632B、marker count u32/reserved0，共72B头。每项是原 JPEG offset u64、完整 marker length u32/reserved0、完整 marker 原字节。最多512项/32MiB，顺序、范围、重叠、marker framing、长度与唯一 namespace owner 均核对。摘要/hash/offset不成为当前文件、路径、HEIF item、实况绑定或删除权限。读取失败不能留下可误用的部分记录。

该记录与[26 的 `LivePhotoBoxMDv1` 相机记录](26-P9-R8-普通元数据承接与目标封装契约.md)不同，不能混用 kind1。metadata 摘要按 carrier1 Exif、2 XMP、3 declared ICC、4完整 IMv1 记录编码：`kind:u8 + length:u64LE + payload`，顺序固定，包含不存在项的零长度。原始 ICC segment/padding另有 IMv1 字节证据，不能把 declared ICC 相等说成原 APP2 分段未变。

这只证明相应数据确实携带，不证明其他品牌相册能继续使用原厂私有编辑功能。未支持 APP1、非默认 JFIF 或实际语义不可表示项仍需单独处理；不因名字像 debug 就自行删除未知记录。

## 验证与未完成边界

须核对 ABI 容量/版本/保留字段、替换/别名/身份/hash、真实文件锁与既有目标、取消、错误 subject/配对残留、活动缩略图、所有旋转镜像、Core 证明拒绝与租约释放。独立验证应覆盖实际 HEIF item/owner/property 图、完整 mapped TIFF/XML/ICC/原始 marker、完整解码与物理方向，以及既定 P5 画面/颜色误差门槛。

必须继续验证实际 CLI 成品与共享 Core GUI。接口正例、内部 Native 产物、派生方向样本或这份契约都不是整目标、HDR、完整格式覆盖、GUI、设备 A/B 或 R8 通过。实际运行与逐文件证据位于既定 R8 工作根 `documentation/s2-image-v2-*.md`、`cli-integration/`；失败记录保留。HEIC→JPEG、HDR/辅助图及其他格式的实际方向处理仍须逐项施工和验证。
