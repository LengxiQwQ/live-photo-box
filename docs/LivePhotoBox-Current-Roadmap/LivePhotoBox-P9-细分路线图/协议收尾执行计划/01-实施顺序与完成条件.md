# P9 剩余施工顺序与完成条件（实况优先版）

入口与授权见 [00-从这里开始](00-从这里开始.md)。本文件规定做什么、按什么顺序、做到什么算完成。

## 1. 两个输出档

| | 兼容档（A 轮默认） | 完整保留档（B 轮 / 用户显式选择） |
|---|---|---|
| 目标 | 目标手机上实况能用 | 尽量把所有内容原样带过去 |
| 对应契约 | 中性媒体契约 N9 的 BestEffort：如实报告损失后继续 | 现有 Strict 规则，带不过去就拒绝 |
| CLI/GUI | **默认** | 显式选项（沿用现有 Strict 语义） |
| 现状 | 阶段 0 新建 | 已有，R8 S2 已做的保留单元全部留在这里 |

### 1.1 兼容档必须做到（A 轮硬要求）

- **实况结构正确：** 目标协议要求的识别标记、XMP/私有字段、偏移/长度、双文件配对标识全部正确；写法以该目标品牌原生相机直出样本为准。
- **主图：** 像素完整，正常解码；方向在手机上显示正确。已经实现的物理转正继续使用；某个组合做不到物理转正时，可以用标准方向标签，只要手机显示正确（物理转正放 B 轮）。来源方向未写明（如 Orientation=0）时，兼容档默认按存储画面不旋转处理并记录，不再拒绝。
- **视频：** 只保留主视频轨 + 主音频轨。容器和编码用目标手机原生能接受的形态（以该品牌原生直出样本为准，例如 Google/小米类用 MP4）；来源编码目标能接受就直接复制（不重新编码），不能接受才转码。辅助视频轨、元数据轨（mebx/Mett 等）、私有 box 不带。
- **视频方向：** 需要转码时，按解析出的实际显示方向将像素真正转正（包括适用的镜像），成功后清除/归零 rotation 和实际承载方向的显示矩阵，保证只旋转一次。不能只删标签、也不能像素转正后继续带旧旋转矩阵。直接复制路径若方向可被目标正确表示且自检通过，可保留原方向表达；否则转码转正，不能把已转码视频的方向问题推到 B 轮。无旋转的输入不额外处理。苹果/三星是用户反馈的重点来源，其他来源目前反馈正常，不据此认定只有这两家会有问题。用户反馈旧版 2.2.1 会物理转正，可作对照线索，尚未在本次重新核验旧实现；新链不能调用旧运行时兜底。
- 上述“不带元数据轨”指不继承来源的非必需附加轨；目标协议自身要求的配对/封面轨仍由目标 Writer 正确生成，例如 Apple 必需的封面元数据，不能一律剥掉。
- **音频：** 来源有声音，成品必须有声音且同步；声道数不减少；目标容器不接受来源编码（如 LPCM 进 MP4）时转为 AAC。
- **封面：** 封面时间点落在视频范围内并对应正确画面。来源记录的封面时间超出视频长度时，取最接近的有效时间并记录，不再拒绝。
- **基本 EXIF 必带：** 拍摄时间（含时区偏移，如有）、厂商、型号、镜头、曝光时间、光圈、ISO、焦距、GPS（如有）。整块 Exif 能直接搬就整块搬。
- **HDR：** 现有路径能带增益图就带；带不过去输出 SDR 主图并记录 `DegradedToSdr`。
- **如实报告：** 每个成品的结果 JSON 有 `notCarried` 列表，逐项写没带过去的内容和原因（如 `auxVideoTrack x4`、`mebx x2`、`OPPO edit record`、`GainMap→SDR`），结果枚举用契约 N5 已有值，不能标 `Preserved`。
- **安全不变：** 来源只读、发布事务、双文件成套、失败不留半成品、无旧实现 fallback、无来源品牌特判。

### 1.2 兼容档不要求（A 轮不阻塞，列入 `notCarried` 和 B 待办）

来源的非必需辅助视频轨/元数据轨、厂商私有记录、编辑历史、水印/附图、HDR 精确数学一致性、原始音频编码、图片及未转码视频的统一物理转正（正确显示时）、XMP 中非识别相关字段、相册内封面编辑功能。已转码视频的物理转正与方向信息归零是 A 轮要求。

## 2. 阶段顺序

| 阶段 | 内容 | 完成条件 |
|---|---|---|
| **0 切换准备** | ① 实现兼容档（Core 共用，CLI/GUI 默认）② 结果 JSON 加 `notCarried` ③ 整包生成脚本 + 快速自检及交付阻断（见 02、03）④ 把 S2 未完成的保留类单元移入 B 待办 | 关联修改全部完成后按 03 统一编译/CLI 实测与必要边界检查，脚本能执行矩阵并阻止失败包交付；停下来报告，不要求手机诊断 |
| **1 Google（小米/Google Photos）A 轮** | Google V2：JPG+MP4、JPG+MOV、HEIC+MOV；Google V1：JPG+MP4、JPG+MOV | 见 §3 |
| **2 OPPO/一加 A 轮** | OPPO：JPG+MP4 | 见 §3 |
| **3 Apple A 轮** | JPG+MOV、HEIC+MOV 双文件：新建配对 Writer/Validator + 成套发布 | 见 §3；iPhone 按真实导入方式测 |
| **4 旧 vivo（X200 及更早）A 轮** | JPG+MP4 双文件：新建配对 Writer/Validator + 成套发布 | 见 §3 |
| **5 商场组 A 轮** | vivo X300 起 JPG+MP4；三星 mpv2/mpv3 的 JPG+MP4、HEIC+MP4；华为 v6、荣耀 v2 的 JPG+MP4、HEIC+MP4、HEIC+MP4-HEVC | 全部整包一次备好，用户一次出行集中测；缺机型的行保持未完成 |
| **6 Fusion A 轮** | JPG+MP4、JPG+MOV | 基础协议稳定后做；多协议冲突时带证据请用户决定 |
| **7 B 轮** | 按 1→6 同样顺序做保留增强（§5） | 每目标 B 待办清空或经用户确认接受 |
| **8 R8 收口 → R9** | 最终整包、一次 P9 相关回归、最终独立复核 + 另一 Verify | 交 R9，停在 P10 之前 |

**每段结束必须停下来报告：** 阶段 0 完成后停；每个目标电脑整包全部通过后停；收到手机反馈、完成该目标 A/B 轮收口后停。未通过则报告未完成和阻塞。停点不是新的复核节点，测试仍按 03。等用户“继续”后再推进下一段；如用户明确授权等待反馈期间准备下一个目标，可进行，但最多交叉两个目标，完成约定段仍须停。缺小米设备只延后小米真机验收，不改变电脑施工顺序或把手机未测写成通过。

格式变体以 `documentation/coverage.json` 的 targets 清单为准（当前计划为 14 组来源 × 22 个目标格式 = 308 行）。发现需要增减支持范围时先记录原因和建议，经用户决定后再改清单，不自行扩张或删减任务。

## 3. 一个目标的 A 轮流程

1. 用正式 CLI（兼容档）在内部工作目录生成该目标的**全部来源 × 全部既定格式变体**，自动跑快速自检，逐行记录结果。
2. 生成失败或自检失败先定位到来源提取、媒体转换、目标写入、重开校验/发布或检查器本身，按事实修复；检查器问题也不能通过跳过检查解决。按 §6 报告无进展的阻塞，失败行保留在内部开发清单，不交残缺包。
3. 全部行生成和自检通过后，才一次性发布平铺整包并给测试说明；停下来报告，用户按编号反馈。小米设备不可用时可先保存在内部待交付目录，说明“电脑通过、手机未测”。
4. 按反馈修复：先找共同原因（同一批文件都失败，一般是目标规则问题，不是逐文件问题），修完重新生成受影响的行，交完整更新包。
5. **A 轮通过条件：** 全部既定行电脑转换/自检通过，且该目标所有**原生格式变体**在对应手机上识别/播放/声音/方向/封面正常，基本 EXIF 正确；非原生变体（如 Google V2 + MOV、HEIC 在不支持 HEIC 的手机上）只记录“该手机支持/不支持”，不阻塞 A 轮，也不无限修。该设备不支持某格式不等于项目可以不生成该变体；不得把转换失败挪到 B 轮规避。确需改变支持范围时说明影响，须由用户另行明确决定。
6. 按 03 汇总相关验证，只补必要缺口；确认 GUI 实际接入，做一次 fresh 独立复核，然后按既有授权本地 commit，停下来报告。收口不意味着把已有有效检查重跑一遍；手机未测时不能提前称 A 轮收口。

## 4. 小米设备与诊断安排（暂缓手机诊断）

已知事实（`cross-source-fix/xiaomi-device-diagnostic-v1/comparison.json`）：小米能认的旧版文件内嵌 MP4（`isom`）、1 条 H.264 视频、无音频、XMP 属性写法、封面时间 0；不能认的新版内嵌 QuickTime MOV、主 HEVC + 4 条辅助 HEVC 轨、LPCM 音频、2 条 mebx 轨、XMP 元素写法。

设备目前在朋友处，先做好 Google 目标电脑端完整转换和自检，不生成/交付 X0–X5 零散诊断包作为阶段 0 前提。以下对照设计只留作后续确有需要且用户同意手机诊断时的参考，不是当前待办：

| 编号 | 内容 |
|---|---|
| X0 | 旧版 2.2.1 成功文件（只读原件复制，对照） |
| X1 | 10-28 已做的“只改 XMP 写法”文件（从未上机） |
| X2 | X1 的视频改为 MP4 容器，轨道不变 |
| X3 | X2 只留主视频 + 音频 |
| X4 | X3 音频 LPCM→AAC |
| X5 | X4 视频 HEVC→H.264 |
| N0 | 小米手机原生实况照片（用户从手机取，或用 `designs/` 中已有小米原生样本副本） |

若以后启用诊断，文件放 `cross-source-fix/xiaomi-device-diagnostic-v2/`，标“诊断-非成品”，不放取件目录。当前按 §1.1 实现兼容档，电脑端完成后报告；小米真机状态保持未测，不能凭旧版对照或电脑自检代签。

## 5. B 轮（保留增强）

在兼容档基础上逐项提升能带过去的内容，并让完整保留档能用：

- HDR 增益图全部带过去，手机上 HDR 显示正确；
- 图片及可正确显示的未转码视频进一步统一物理转正；A 轮转码视频的方向要求不能延后；
- 原始音频编码在目标支持时保留；辅助视频轨、元数据轨按目标支持情况保留；
- 厂商私有记录、编辑历史（OPPO/一加）、水印/附图（红米、华为、荣耀复合资产）；
- 完整 Exif/XMP、色彩/ICC；
- 相册内封面编辑功能。

已暂停的 S2 单元直接进入 B 待办：红米老款附图/水印（S01）、华为 JPG 附加图（S09）、华为 HEIC→JPG 信息（S10）、荣耀复合资产（S11）、图片及可正确显示的未转码视频同格式/反向转换物理转正、HDR/完整历史 Original 单元的最终复核、三星 HEIC 原封面时间精确保留。转码视频方向错误仍在 A 轮修复。

B 轮的修改如果改变了 A 轮成品，受影响的行需要用户手机快速复测 A 项。B 轮测试只增加 HDR 显示等电脑无法代替的项目。

**协议完成 = A 轮通过 + B 待办清空或经用户确认接受 + CLI/GUI 实测 + 收口复核通过。**

## 6. 防止死磕

- 按根规则 0.2 的两次无进展/约 30 分钟未缩小范围提醒线，停止该问题的继续试错并主动报告，不静默攒着、不自动加模型/代理。说明要做什么、失败在哪、已试什么、影响多少行、建议下一步。
- 生成/自检失败始终留在 A 轮开发清单并阻止该目标整包交付；可以做本阶段不受影响的独立项，但不越过阶段停点。修复优先找影响多行的共同原因。
- 来源被改、半成品发布、虚报保留：立即停止受影响的生成/交付并报告；几乎整包手机不识别时先查共同原因，不让用户逐个重复试。安全问题也不豁免无进展汇报。
- 普通问题自主解决；需要用户决定时提前问。用户不必提供技术解法，AI 应给清楚的选项、影响和建议。
