# 测试与复核规则（实况优先版）

依据 2026-10-30 最新用户决定：完整单元/小节的关联修改做完再统一验证；以正式 CLI 生成真实成品及实际检查为主。非必要、重复、低收益且没有明确风险依据的测试不运行。验证后发现问题，只修复和重测受影响区域；诊断可提前做最小检查。本文件是 P9 测试节奏的唯一位置，旧逐小改动测试、逐单元 Review+Verify+回执安排不再适用。不得删除失败测试、放松断言或漏掉必需验收换绿灯。

## 1. 什么时候跑什么

| 级别 | 内容 | 什么时候跑 | 什么时候**不**跑 |
|---|---|---|---|
| **L0 编译** | 编译当前完整单元涉及的项目 | 单元/小节全部关联修改完成后；局部修复后编译受影响部分 | 每次编辑、每个函数完成时；纯文档修改时 |
| **L1 必要边界检查** | 复用相关单测或最小实测，验证 CLI 正常成品覆盖不到的问题，如非法长度、取消、锁文件和成套发布失败 | 与该单元一起验证；只有明确风险或验收缺口才增加检查 | 不因改了业务代码就强制新增测试；不重复已有 CLI 成品已充分证明的事实；不按测试数量凑验收 |
| **单元 CLI 实测** | 正式程序处理受影响的真实样本，并自动检查输出 | 一个可运行单元完成后；失败定位修复后只重测相关案例 | 不每改一点就跑；不等整个 R8 写完才首次运行；不以 mock 或直接调用内部 Writer 代替产品入口 |
| **L2 整包 + 快速自检** | 正式 CLI 生成当前目标全部行，并自动自检（§2） | 准备交付整包时；处理完一批失败或一批手机反馈后 | 修一个小问题后不重跑整包，只重跑受影响的行；共用代码改变时，检查**已生成目标（含待设备的内部包）**的受影响行，未受影响且身份/适用性有效的成品和检查复用 |
| **L3 收口回归汇总** | 汇总当前目标相关 CLI/成品/边界结果，只补缺失或失效的必要检查；过滤器按实际影响选择，不按项目名全跑 | 每个目标 A/B 收口、R8 最终收口各汇总一次 | 平时小单元；收口时无理由再跑一遍已通过且有效的检查 |
| **L4 GUI 实际操作** | 确认目标选择、选项和 Core 接入实际可用；公共错误提示/取消仅在受影响或缺证据时补 | 每目标 A 收口核对该目标可用；B 改了界面/参数接入时补相关操作 | 平时；不重复 CLI 已证明的整包媒体结果，不为凑数固定转换 2–3 份；有效公共交互证据复用 |
| **L5 独立复核** | 一个 fresh 只读复核者（没参与修改），看该目标的改动和整包自检结果（§3） | 每个目标 A 轮收口、B 轮收口时各一次 | 平时任何小单元；不再要求“另一 fresh Verify”，只有 R8 最终收口才要第二个 |
| **手机测试** | 用户做 | 完整成品已通过电脑自检、设备可用时 | 有生成/自检失败的残缺包；小米设备暂不可用时 |

L3 发现失败：修复本次造成或本轮完成条件内的问题；已有严格档问题经证据确认与 A 轮无关时如实留在 B 待办，不删除或改松断言。兼容档用实际 CLI 或必要的专门测试验证，不能把严格档旧测试改成宽松档求绿。修完只补受影响检查，不重新启动全流程。

一个单元是计划中能交付实际行为的完整部分，不是每个 helper/函数。每项检查都应能说明“它要发现什么问题、当前已有结果为何不够”；不另写审查文件，短计划中一句即可。`scripts/verify.ps1` 的 Fast/Full 是宽范围入口，不用于日常小节验证；使用针对性构建/CLI 命令。

## 2. 快速自检（随整包自动运行）

每个成品一行结果，全部自动完成，不需要人工逐个看。用离线工具独立检查（ffprobe/exiftool/Python 等只作离线检查，不进入产品）：

1. 文件能被独立解析，实况识别标记/偏移/长度/双文件配对字段正确；
2. 主图完整解码；
3. 视频完整解码，时长 > 0；
4. 来源有音频时成品有音频，且声道数不少于来源；
5. 封面时间在视频范围内；
6. 基本 EXIF（时间、厂商、型号、曝光参数、GPS 如有）存在且与来源一致；
7. 来源文件 hash 前后不变；
8. 结果 JSON 的 `notCarried` 存在，且没有把损失写成 `Preserved`。
9. 视频发生转码时，检查忽略自动旋转后的实际解码画面方向与来源显示方向一致，且输出旋转信息/显示矩阵不再引发旋转；不能只看到 rotation=0 就判通过。检查主图、视频和封面方向一致；苹果/三星覆盖已有方向样本，按实际变换选择检查，不写品牌特判。

P9 临时调度/自检脚本复用 R8 工作根 `tools/` 或已有脚本，不进入产品运行和安装包。若确需长期维护为通用开发工具，按文档管理规范放 `scripts/`、`tools/` 或 `tests/`，不自动引入生产依赖。

## 3. 独立复核看什么（每个目标收口一次）

复核者只读，给出“通过 / 有阻断问题（列出）”，不写长报告：

- 没有按来源品牌/型号/文件名/hash 写的特判；
- 没有把没带过去的内容写成 `Preserved`；
- 来源只读、发布事务、双文件成套、失败不留半成品；
- 没有旧实现 fallback，没有绕过校验的开关；
- 全部既定行的整包自检结果与 coverage 记录一致，无被删除、隐藏或转 B 轮的转换失败；手机未测没有写成通过。

复核发现的问题修完后，复核者只复看修改部分和影响，不重新全量复核、不重跑已有有效成品检查。R8 最终另一 Verify 负责核对最终身份、完整覆盖和未关闭事项，不复制第一复核的逐行代码审查或全部命令；R9 复用有效证据，只补新缺口。

## 4. 模型和人手

- 跑测试、跑整包、收集结果是机械工作：主代理直接执行，不需要为此开子代理，更不用高推理模型。
- 写实现使用用户/会话选定的模型；能调推理强度时按工作复杂度选择，不默认最高档。若本会话不能调整，不宣称已切换；也不为机械执行另开模型。
- 两次无进展应先停下报告，不能自动提高推理强度继续耗。只有新的证据表明深入分析有明确价值且仍在授权范围内，才考虑调整。
- L5 独立复核才用一个 fresh 只读子代理（Codex 按专属偏好使用 gpt-6.1-sol / medium）；不开额外规划、跑测试或重复审查代理。
- 尽量一个号做完一个完整目标（或一个完整阶段）再换号；换号时只交接 `next-action.md` 那一页。

## 5. 不再做的事

- 每个小单元的 fresh Review + 另一 fresh Verify；
- 每个小单元的有界回归聚合、冒烟测试；
- 每个小单元的 hash 绑定回执、封存 run、新决策文档；
- 每次小修复后重跑整个 308 行矩阵；
- 为了证明“没改坏”而重复跑已经通过、且未受影响的测试；
- 用高推理模型执行测试命令。

正式封存证据（`.ai-tmp/evidence/P9/...run-N`）只在 R8 最终收口时做一次。

## 6. 防死磕

执行根规则 0.2 和 [01](01-实施顺序与完成条件.md) §6：无进展主动报告，停止该问题继续试错；转换/自检失败阻止整包交付，不推给用户测试。已有有效检查复用，仅补改动影响的部分。

阶段 0、每目标电脑整包就绪、每目标 A/B 收口均停止操作并报告，等用户继续。电脑整包报告不额外触发 L3–L5；它们仍只在对应目标 A/B 收口执行，R8 最终第二复核不变。执行中主动说明当前步骤、结果和卡点，不等用户追问，不为汇报生成长回执。
