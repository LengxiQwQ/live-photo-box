## 4. W0 — 先冻结施工合同与设计决定

- [x] plan 至少绑定：source file identity、完整 SHA/fingerprint、protocol、primary/video/auxiliary range、relationship、pairing、source index、plan version。
- [x] stale plan、替换 source、错 secondary、重放 plan 和篡改 relationship 均定义为 fail closed。

**W0.1 证据：** working-tree diff from base `372959514ab29a9a8faa4678e74fd39ea97d8ad2`；Native Release x64 与 Core Release x64 均 exit `0`；`ExtractorAuthorityTests` exit `0`，22/22 passed；证据位于 `.ai-tmp/workspace/p2-w1-repair/` 的 authority TRX、build/export/surface logs。真实 Apple dual-file source identity、wrong secondary、replaced primary、cross-context、generation、replay、diagnostic tamper 和 caller-facts fail-closed 均有测试覆盖。

### W0.2 Auxiliary / preservation taxonomy

- [ ] 🔴 区分以下三类，不用一个 `GainMap` 文件槽混为一谈：
  - semantic auxiliary descriptor（例如 embedded GainMap）；
  - materialized standalone auxiliary artifact；
  - 同容器 cleaning 所需的 opaque preservation fragment / cleanup source。
- [ ] 明确 embedded、detached、materialized 的 owner、relationship、stable identity 和 duplicate prevention。
- [ ] 明确 Samsung 非 motion SEF、OPPO Original 分别进入哪个正式模型；不得为了省事把非媒体 metadata 假称为 GainMap/Auxiliary image。
- [ ] 明确 P2 输出与后续 P3 Cleaner 的交接，不让 preservation 数据在 P2 边界消失。

**推荐方向：** `AuxiliaryMediaDescriptor` 表达语义资产；`MaterializedArtifact?` 只在确有独立有效文件时存在；另设 typed preservation carrier/cleanup source，服务同容器 N9 preservation。

### W0.3 HEIF compound auxiliary policy

- [x] 🔴 明确 HEIF `grid`/derived item 的默认表示是 Embedded，还是必须物化为独立有效容器。
- [ ] standalone materialization 必须包含合法 `ftyp/meta`、item properties、`iloc`、`iref`/`dimg` dependency graph 及所有 referenced tiles。
- [x] 尚不能正确物化的布局必须返回 `UnsupportedLayout`，不得输出裸 extent 并标成 `.heic`。

**推荐方向：** 第一阶段保留为 Embedded semantic asset，并绑定 Primary owner；只有完整重建并通过独立 HEIF validator 后，才增加 detached working representation。

### W0.4 ABI/兼容性批准

- [x] 记录 C ABI 版本策略、`struct_size` 兼容策略和旧入口处理策略。

## 13. 推荐提示词拆分

不使用一个让 Agent 同时发明 Contract、修改 ABI、实现全部功能并自我验收的无边界提示词。按以下顺序执行：

1. **P2-W0 设计冻结提示词**：只输出/落盘 TASK 和明确 contract decisions，不改 production。
2. **P2-W1 authority 实现提示词**：只处理 Inspector-issued plan 与所有 bypass。
3. **P2-W2/W3 auxiliary 实现提示词**：接通通用 Auxiliary/preservation，并处理 HEIF compound GainMap。
4. **P2-W4 transaction 实现提示词**：只处理 temp/publish identity 与 hash-verifiable publish。
5. **P2-W5/W6 验证修复提示词**：补测试、真实样本 gate 和可信脚本，不降低断言。
6. **P2 fresh audit 提示词**：review-only，独立从 production/RealSamples 反向取证。
7. **P2 verifier 提示词**：Auditor ACCEPT 后执行固定 P2 gate。

每个实现提示词最多允许一个 writer；主 Agent检查真实 diff 后才能进入下一工作包。单个工作包最多进行 3 轮 repair→audit，仍失败则停止并请求重新设计。

第六轮 Gate 复验：B2（ClaimKnownOutputTarget 按路径认领）、B3（BUFFER_TOO_SMALL → delete(path)）、B4（HEIF 固定 temp 预删）均已真实闭环；MP4/SEF/HEIF 发布后再打开 destination 登记也已删除。剩余唯一 blocker：

- **MP4 / Samsung SEF JPEG / Samsung HEIC 三条 sink 的 ownership 仍不是从「写文件的 handle」连续到登记**：原实现是 ofstream 写入 → close() → CreateFileW(temp) 重新按 temp pathname 打开 → MoveFileExW 发布 → 从重开 handle 捕获 identity。窗口：自己写的 A → close → temp pathname 被换成 foreign B → CreateFileW(temp) 打开 B → 发布并登记 B 的 File ID。这正是「pathname 不能创造 ownership」在 temporary pathname 上的残留。

### 19.2 修复内容

三条 sink 统一改为连续 handle 链，任何一步都不再按 pathname 重新建立 ownership：

`
CreateFileW(temp, GENERIC_READ|GENERIC_WRITE|DELETE)   ← 创建/写 handle
  → WriteFile 循环写完整 payload（32MB 分块）
  → FlushFileBuffers（同一 handle）
  → MoveFileExW(temp, dest, MOVEFILE_WRITE_THROUGH)     ← no-overwrite 发布（同一 handle 保持）
  → GetFileInformationByHandle（同一 handle 捕获 identity）
  → record_cleaner_staged_output（registry）
  → CloseHandle
`

- **MP4（mp4_strip.cpp）**：publish_owned_temp 重构为 open_temp_output_handle + write_all_to_handle + publish_and_register_cleaner_output；直接拷贝路径与流式（多 box 拼接）路径都通过同一 handle 写与发布。失败清理通过同一 handle 的 FileDispositionInfo（绝不裸 pathname 删除）。
- **Samsung SEF JPEG（samsung_sef_cleaner.cpp）**：ofstream 写改为创建 handle + WriteFile 循环 + 同一 handle 发布/捕获。
- **Samsung HEIC（heif_cleaner.cpp）**：write_atomic 同样改为创建 handle 写 + 同一 handle 发布/捕获。

### 19.5 独立反向审计

从 destructive mutation 点向上：三条 sink 的发布均为「创建 handle → 同 handle 写 → 同 handle 发布 → 同 handle 捕获 identity → registry」，不存在任何按 pathname（temp 或 destination）重新打开建立 ownership 的步骤；失败清理全部通过 handle 的 FileDispositionInfo。BUFFER_TOO_SMALL 失败路径保留输出与 registry（由 transaction rollback 决定）。未发现 DTO/pathname/SHA/raw-facts 自授权或 direct mutation bypass。

## 20. 第七轮最终收口：Cleaner temp 起点统一为 CREATE_NEW first-creation handle（2026-09-12）

### 20.1 外部 Chief Gate 复验结论

第七轮 Gate 确认第六轮三条 sink 的 handle 连续链正确，但指出更前端仍有一个原子性缺口：所有 Cleaner temp 输出都先调 `GetTempFileNameW(..., 0, ...)`——Windows 文档明确该调用会**自己创建空文件并关闭 handle 后返回 pathname**，随后代码再 `CreateFileW(path, OPEN_EXISTING)` 打开"现在处在这个 path 的对象"。窗口：GetTempFileNameW 返回的 A 被移走 → foreign B 占据同一 temp path → CreateFileW(OPEN_EXISTING) 打开 B → 后续写/发布/登记全部把 B 当作 transaction-owned。`write_file_binary()` 也存在同样问题（此前误判为正确先例，本轮纠正）。

### 20.2 修复内容

新增共享 primitive `lpb_create_unique_temp_file`（`internal.h`）：

```
随机候选名（std::random_device + PID + TickCount）
  → CreateFileW(..., CREATE_NEW, GENERIC_READ|GENERIC_WRITE|DELETE)
  → 成功 = 内核原子地证明该对象是本次 CreateFile 调用首次创建
  → 返回 first-creation handle（ownership 从对象存在第一刻成立）
  → 冲突（ERROR_FILE_EXISTS / ERROR_ALREADY_EXISTS）= 换随机名重试（最多 16 次）
```

所有 Cleaner 自有 temp 输出统一改走该 primitive，`GetTempFileNameW(0) → OPEN_EXISTING` 从 Cleaner-owned temp 创建链中全部清除：

| 位置 | 前缀 | 用途 |
|---|---|---|
| `media_cleaner.cpp` write_file_binary | `lpb` | 通用 JPEG（OPPO 等） |
| `mp4_strip.cpp` stream_clean_mp4_bytes | `lpbv` | MP4 video sink（直接拷贝与流式两路径，handle 提前创建并贯穿中间计算） |
| `samsung_sef_cleaner.cpp` | `lpbj` | Samsung SEF JPEG sink |
| `heif_cleaner.cpp` write_atomic | `lpbh` | Samsung HEIC sink |

伴随修改：`internal.h` 前置 `NOMINMAX` + `<windows.h>`（消除 min/max 宏污染，`std::min` 恢复正常）。剩余唯一 `CreateFileW(OPEN_EXISTING)` 是 input exact-object 验证（读取已存在的输入，正确）。

### 20.3 验证证据

| 项目 | 结果 |
|---|---|
| Debug 全套 10-filter | ✅ 129/129，4m8s，无崩溃弹窗（`_NO_DEBUG_HEAP=1`） |
| Release 全套 10-filter | ✅ 129/129，26s |

### 20.4 独立反向审计

从 destructive mutation 点向上：temp 对象在**首次创建瞬间**由本线程持有的 CREATE_NEW handle 锚定，随后写 / Flush / no-overwrite 发布 / identity 捕获 / registry 登记全程使用同一 handle；失败清理使用同一 handle 的 FileDispositionInfo。不存在任何 `GetTempFileNameW → OPEN_EXISTING` 式的 pathname 重开起点，也不存在按 pathname（temp 或 destination）重新建立 ownership 的步骤。未发现 DTO/pathname/SHA/raw-facts 自授权或 direct mutation bypass。

## 21. 第八轮最终收口：Cleaner publish 全链只认 HANDLE（2026-09-12）

### 21.1 外部 Chief Gate 复验结论

第八轮 Gate 确认第七轮 CREATE_NEW first-creation 起点正确，但指出 publish 本身仍是最后一段 pathname-bound：三个 dedicated sink（MP4 / Samsung SEF / Samsung HEIC）在正确的 `CREATE_NEW → HANDLE A → WriteFile(A) → FlushFileBuffers(A)` 之后仍用 `MoveFileExW(tempPath, destinationPath, MOVEFILE_WRITE_THROUGH)`。由于 temp handle 以 `FILE_SHARE_DELETE` 打开，持有 HANDLE A 并不能保证 tempPath 仍指向 A：外部进程可把 A rename 走、再在 tempPath 创建 foreign B，此时 MoveFileExW 移动的是 B（destination 变成 B），而 registry 登记的却是 A（GetFileInformationByHandle(A)）——foreign 对象被擅自移动，身份错位。任务书冻结标准：publish 的 source object 必须由 handle 决定，绝不能由 source pathname 决定。此外指出 `write_file_binary()` failure 路径残留 `CloseHandle → fs::remove(temp)`（可删 foreign B），以及 `lpb_create_unique_temp_file` 声明 noexcept 但内部含可能抛异常的 STL 操作（random_device / wstring / to_wstring / filesystem）会 `std::terminate` 违反 fail-closed。

### 21.2 修复内容

**A. 统一 handle-based publish primitive（`internal.h`）**

新增内联 `lpb_publish_cleaner_output_handle(context, artifact_role, handle, temp_source, dest, dest_path)`：

```
（harness 下可选 race seam：先按 handle 把原对象 rename 到 temp+".lpb-race-side"，
  再 CREATE_NEW 一个含 "LPB-FOREIGN-RACE-MARKER" 的 foreign 文件占原 temp path）
  → SetFileInformationByHandle(FileRenameInfo, ReplaceIfExists = FALSE)   // no-overwrite
  → GetFileInformationByHandle                                           // 同一 handle
  → record_cleaner_staged_output(identity)                               // registry
  → 全 try/catch → false（异常不穿过，不 terminate）
```

生产 build 中 `temp_source` 仅作参数消隐（`static_cast<void>`），seam 代码只在 `LPB_NATIVE_TEST_HARNESS` 编译；`lpb_cleaner_test_hook` 结构体与 `context.cleaner_hook` 字段在所有 build 布局一致（跨 production/harness DLL 传递 context 时字段偏移稳定，避免越界写）。设置导出 `lpb_test_set_cleaner_publish_fault(context, int32)` 仅 harness 编译。

**B. 三个 dedicated sink + 通用 write_file_binary 全部切换**

| Sink | 文件 | 原 publish | 现 publish | 失败清理 |
|---|---|---|---|---|
| 通用 JPEG / 字节输出 | `media_cleaner.cpp` write_file_binary | MoveFileExW + fs::remove(temp) | primitive | FileDispositionInfo(handle) |
| MP4 video | `mp4_strip.cpp` publish_and_register_cleaner_output | MoveFileExW(temp→dest) | primitive | FileDispositionInfo(handle) |
| Samsung SEF JPEG | `samsung_sef_cleaner.cpp` | MoveFileExW(temp→dest) | primitive | FileDispositionInfo(handle) |
| Samsung HEIC | `heif_cleaner.cpp` write_atomic | MoveFileExW(temp→dest) | primitive | FileDispositionInfo(handle) |

`write_file_binary` 失败分支删除 `fs::remove(temp, ec)`，改为 `SetFileInformationByHandle(FileDispositionInfo)` + `CloseHandle`，并补诊断消息（temp 创建失败 / 写入失败可区分）。

**C. `lpb_create_unique_temp_file` 异常安全**

整体包 `try { ... } catch (...) { return INVALID_HANDLE_VALUE; }`，任何分配 / random / 转换异常都返回明确失败，不再 `std::terminate`。

**D. test-only publish-race seam**

`lpb_cleaner_test_hook.swap_temp_source_before_publish`（一次性）：publish 前把 owned 对象按 handle rename 走、在原 temp path 创建 foreign 文件（marker 内容）。handle-based publish 必须仍移动原对象、foreign 必须原样保留。`lpb_test_set_cleaner_publish_fault` 导出仅 harness 编译。

