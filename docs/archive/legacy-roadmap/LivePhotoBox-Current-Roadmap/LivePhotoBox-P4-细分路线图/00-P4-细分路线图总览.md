# Live Photo Box — P4 细分执行路线图总览

> **定位：** 本文件是 `P4 — Native Platform / Media Backend / Build Foundation` 的二级执行路线图。  
> **适用对象：** 本地 AI Agent / 项目维护者 / 独立审计者。  
> **当前正式交付平台：** Windows x64。  
> **未来平台原则：** WebAssembly / Linux / macOS 只保留最小、稳定的接入缝，不在 P4 实现产品或预先实现 backend。  
> **上位规范：** 当前用户明确指令 > `docs/LivePhotoBox-Current-Roadmap/` > 当前 P4 子任务。本文只能细化 P4，不能降低总纲、P4、Neutral Media Contract 或 AI Bootstrap 的约束。

---

## 1. P4 在整个项目里的位置

正式媒体主线：

```text
P1 Source Inspector
        ↓
P2 Source Extractor
        ↓
P3 Source Protocol Cleaner
        ↓
P4 Native Platform / Media Backend / Build Foundation
        ↓
P5 Media Converter
        ↓
P6 Neutral Pipeline
        ↓
P7–P10
```

P4 的任务不是重新逆向协议，也不是提前完成 P5 Converter。

P4 要完成的是：

```text
Portable protocol/container truth
        ↓
small Media Backend contracts
        ↓
approved codec/video implementations

Portable mutation semantics
        ↓
small Platform Backend contract
        ↓
Windows filesystem / transaction / publish implementation

Native sources
        ↓
CMake canonical build
        ↓
reproducible dependency identity
        ↓
runtime capability identity
```

**P4 成功的最终定义：P5 不需要重新发明 build、platform、codec、video backend 架构，只需要把 Converter 正确接上已经冻结的基础设施。**

---

## 2. 基于当前源码快照确认的起点

本轮规划基于用户提供的当前源码快照，而不是旧报告。

当前可见事实包括：

- Native 约 2.6 万行 C/C++；
- `LivePhotoBox.Native.vcxproj` 仍是当前 Native 构建入口，尚未建立 canonical CMake；
- 当前未见正式 `vcpkg.json` / `vcpkg-configuration.json`；
- Native 图像转换仍直接包含 WIC；
- Native 视频转换仍直接包含 Media Foundation；
- Inspector / Extractor / Cleaner / converter / foundation 中仍存在多处 Win32 filesystem / handle / publish plumbing；
- P1–P3 已形成较严格的 authority、identity、transaction、publish、preservation 逻辑，P4 必须迁移 plumbing，而不是破坏这些 correctness 语义；
- public C ABI 已经存在，P4 应保护 ABI 边界，不让 `HANDLE`、COM、C++ STL 等平台类型泄漏到公共边界；
- 已有真实样本与 P1–P3 的大量 targeted / RealSample / adversarial tests，可作为 P4 重构回归基础。

这意味着 P4 是一次**受约束的基础设施收口**，不是“大重写”。

## 3. P4 的永久架构原则

### 3.1 Windows 是当前产品平台，但不是协议真相

允许 Windows-specific：

```text
Win32 filesystem semantics
atomic publish / replace
Media Foundation（若最终证据支持）
WIC（仅当某 result-affecting 能力确有证明优势）
```

不允许平台 API 无理由进入：

```text
protocol parser
container truth
source recognition authority
neutral semantics
target writer correctness
target validator correctness
```

### 3.2 未来平台只留接口缝，不预做产品

P4 不做：

```text
Linux GUI/CLI
macOS GUI/CLI
Web 产品
完整 WASM backend
POSIX backend 产品化
跨平台 C# Core 重构
```

P4 只要求：

> 本可平台无关的协议/容器/媒体语义不要被 Windows 类型和调用方式锁死；Windows-only 能力位于小而清晰的 backend 边界之后。

### 3.3 C# / C++ 边界保持不变

```text
C# = Control Plane / orchestration / product contract
C++20 Native = result-affecting media & byte Data Plane
```

跨边界继续使用：

```text
stable C ABI
fixed-width/POD
opaque handle
explicit buffers
result codes
UTF-8 text
```

### 3.4 不恢复 production external media CLI

production runtime 禁止重新依赖：

```text
ffmpeg.exe / ffprobe.exe
ExifTool.exe
jpegtran.exe
heif-enc / heif-dec
magick.exe
```

这些工具可继续用于研究、测试、独立验证或 fixture 生成，但不能偷偷变回正式写入路径。

### 3.5 P1–P3 correctness 优先保护

对 correctness-critical 的 Win32 实现：

```text
先建立 contract
→ 旧正确实现放到 adapter/backend 后
→ 回归验证
→ 再逐步整理内部
```

禁止：

```text
为了“跨平台更漂亮”
→ 大爆炸重写
→ authority / identity / transaction / preservation 退化
```

## 4. P4 推荐执行顺序

| 轮次 | 主题 | 核心结果 |
|---|---|---|
| R1 | 能力盘点与基线 | 搞清当前真实 architecture / dependency / runtime / contamination |
| R2 | PlatformFilesystem + Portable I/O | filesystem、transaction、publish 与 portable core 分离 |
| R3 | CMake + vcpkg | canonical build 与可复现依赖基础 |
| R4 | JPEG Foundation | libjpeg-turbo 成为正式 JPEG codec/lossless transform foundation |
| R5 | HEIF/HEIC + HDR Foundation | libheif/libde265/x265、aux/HDR 基础、WIC/lcms 决策 |
| R6 | Video Backend Differential | MF vs minimal libav* vs hybrid，用证据冻结 Windows 视频 backend |
| R7 | P4 Closure | capability identity、依赖收口、portable-core proof、package/runtime 收口 |
| Audit | Fresh Independent Audit | 从 Roadmap → production → data flow → tests 反向审计 |
| Verify | Fresh Verification | clean build、真实测试、样本、package、portable proof，准备外部门禁 |

**Implementer 共 7 个施工回合。Audit 与 Verify 必须是 fresh、独立上下文。**

如果 R5 或 R6 因实际工程量过大，可以在不改变目标的前提下内部拆成 A/B 两个施工上下文；不能因此降低该轮 gate。

## 5. 子轮次的通用执行规则

每一轮开始前：

1. 读取当前 HEAD，而不是沿用旧报告；
2. 按 AI Bootstrap 执行 reconcile；
3. 读取本轮文档、P4 总路线图、总纲、Neutral Media Contract，以及本轮直接依赖的前置规范；
4. 只执行本轮范围，不“顺手”提前做后续 P4 子轮或 P5；
5. 保留用户工作区改动；
6. build/test 只覆盖本轮和受影响的前置能力，不在 P4 跑全项目最终 suite。

每一轮结束时，Agent 至少应给出：

- 实际修改范围；
- 架构变化与数据流；
- build/test/RealSample/独立验证证据；
- 本轮 acceptance matrix；
- 所有未解决项及严重性；
- 是否 **READY FOR NEXT P4 SUB-ROUND**。

这里的 `READY` 只表示本轮内部 gate 清晰，不表示 P4 ACCEPT。

## 6. 通用“不算通过”规则

以下任一情况存在，本轮不得以“基本完成”“大部分完成”继续掩盖：

- 通过删除/跳过/缩小测试范围制造绿灯；
- Roadmap 要求 RealSamples，但样本缺失、skip 或 filter 没跑到；
- result-affecting 路径仍存在未说明的 legacy/external CLI fallback；
- 使用 mock/stub 代替要求的真实 filesystem / codec / sample 证据；
- correctness-critical 语义发生变化却没有回归证据；
- 新增 Windows-specific 类型进入 portable protocol/container truth；
- 新增第三方库却没有版本、feature、license/runtime 用途记录；
- fallback 改变质量/HDR/preservation，却仍报告为 preserved/success；
- 仅产品自身 Reader 验证自身 Writer，就声称独立正确；
- 当前轮还有 blocker，却自动开始下一轮；
- Implementer 自行宣布整个 P4 completed。

## 7. 整个 P4 的最终 Exit Gate

R7、Audit、Verify 完成后，仍必须逐项映射回 P4 原始 17 项 Exit Gate：

1. Platform / Media backend contracts 清楚；
2. scattered Win32 filesystem/publish logic 已收口或有明确、可接受的剩余清单；
3. CMake Windows build canonical 且 production parity；
4. dependency manifest 可复现；
5. libjpeg-turbo foundation 可用；
6. libheif foundation 可用；
7. libde265/x265 HEIC default path 有真实样本与分发记录；
8. HDR/GainMap Native foundation 足以支撑 P5；
9. video backend comparison 完成且 Windows P5 backend 冻结；
10. lcms2 是否需要已有证据结论；
11. WIC result-affecting policy 明确；
12. duplicate codec/runtime report 完成；
13. runtime binaries/features 都有用途说明；
14. portable-core build proof 通过，或存在由外部 Gate 明确认可的 blocker；
15. production runtime 无 external media CLI；
16. package footprint 有 baseline，但未为了体积牺牲兼容/正确；
17. P5 不需要重新设计 build/backend architecture。

只有 Fresh Auditor 与 Fresh Verifier 都无 blocker，才进入：

```text
READY FOR EXTERNAL CHIEF GATE
```

**只有当前用户 / External Chief Gate 明确 ACCEPT，P4 才算完成。**
