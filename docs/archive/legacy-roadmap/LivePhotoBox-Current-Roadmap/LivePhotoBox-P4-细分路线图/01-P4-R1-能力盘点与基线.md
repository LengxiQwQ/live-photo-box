# P4-R1 — Capability Inventory / Architecture Baseline

> **性质：** 调查与基线轮。  
> **默认原则：** 本轮不进行 production architecture 重构；先把当前真实状态看清楚。  
> **目标：** 为 R2–R7 建立可信、可追踪、不会靠旧报告猜测的 P4 baseline。

---

## 1. 本轮要解决的问题

P4 后续会同时触及 platform I/O、build、JPEG、HEIC/HDR、video backend 和 package。

在真正修改之前，必须回答：

```text
现在每一种能力是谁负责？
真实 production data flow 经过哪里？
哪些是 C#，哪些是 Native？
哪些依赖 Windows？
哪些依赖第三方 runtime？
哪些能力重复？
哪些路径会改变最终产物？
哪些旧能力只是 UI/preview？
P1–P3 哪些实现属于 correctness-critical，不能被随便改写？
```

本轮输出的是**事实地图**，不是理想架构图。

每项至少给出：

## 3. Windows Contamination Map

系统扫描 Native 中：

```text
Windows.h
HANDLE
Win32 file API
Move/Delete/Temp/Stat
Windows error codes
WIC / COM image API
Media Foundation
MSVC-only helpers
其他 platform-only API
```

每一处按三类处理：

### A. 合法 Windows backend

本来就应该由 Windows 实现，例如 filesystem publish 或最终胜出的 Windows media backend。

### B. 意外平台污染

协议/容器/哈希/Inspector 等本可平台无关逻辑只是因为实现方便而直接拿了 Win32 类型或 API。

### C. correctness-critical legacy plumbing

当前实现可能不漂亮，但已经承担 P1–P3 的安全语义。后续只能“包住后迁移”，不能直接重写。

## 4. Dependency / Runtime Graph

建立当前真实 dependency graph，至少看清：

```text
Native linked system libraries
NuGet / managed image dependencies
production packaged binaries
legacy/external tool remnants
codec/runtime duplication
UI-only vs result-affecting usage
```

对所有名字中出现的 FFmpeg、ExifTool、jpegtran、heif tools、Magick.NET 等，不能只看注释或 About 页面。

必须追到真实 production call path，判断：

```text
仍在 production runtime？
只剩 dead/legacy wrapper？
只用于 UI preview？
只用于 test/independent validation？
```

## 6. Test / RealSample Baseline

在不改 production code 的前提下，确认：

- P1 Inspector targeted tests 当前状态；
- P2 Extractor targeted / transaction / RealSample tests 当前状态；
- P3 Cleaner authority / transaction / preservation / RealSample tests 当前状态；
- 当前 Native media converter tests 的真实覆盖；
- 当前真实样本 corpus 能覆盖哪些 JPEG / HEIC / video 类型；
- R4–R6 还缺哪些真实样本或独立验证条件。

本轮的目的不是跑全项目 suite，而是知道后面重构不能破坏什么。

## 7. 本轮必须产生的长期结果

至少形成以下可进入仓库正规文档位置的 P4 baseline 资料：

1. Capability Inventory；
2. Windows contamination map；
3. dependency/runtime graph；
4. build/ABI/package baseline；

具体文件组织由执行 Agent 按现有项目文档结构决定，不要求机械照搬文件名。

---

## 8. 验收标准

本轮只有在以下全部满足时才可进入 R2：

- P4 所列主要 capability 没有“owner/backend 不明”的空白项；
- 所有 result-affecting production path 都能从 C#/C ABI 追到 Native/backend 或明确 legacy path；
- Windows-specific 使用已完成 A/B/C 分类，而不是只给 grep 数量；
- P1–P3 correctness-critical Win32 plumbing 已被明确标记；
- external media CLI 是否仍参与 production 已有代码级结论；
- 当前 Native build、ABI、runtime/package 有可比较基线；
- 真实样本与后续 benchmark 缺口已明确；
- 当前 targeted baseline build/test 没有未解释失败；
- 后续 R2–R7 的范围可以从该 inventory 推导，而不是继续猜。

---

## 9. 以下情况不得通过

任一出现即 `R1 BLOCKED`：

- 只列库名，没有追真实调用链；
- 把注释、README、旧报告当成 production evidence；
- 未区分 UI-only 与 result-affecting；
- 看到 `Windows.h` 就一律认定为错误；
- 没找出 P1–P3 transaction/publish correctness-critical 区域；
- 不知道测试实际加载了哪一个 Native DLL；
- Roadmap 要求的真实样本后续明显缺失，却没有列为 blocker；
- baseline 本身存在失败，却以“反正后面会修”跳过；
- 本轮提前开始大规模重构。

---

## 10. 验证方式

本轮验证以**静态追踪 + 当前 baseline 构建/测试 + 样本可用性确认**为主：

```text
source/code graph tracing
build graph inspection
dependency/package inspection
public ABI/export inspection
targeted current tests
selected existing RealSample tests
current package/runtime inventory
```

结论必须能让下一轮知道：

> 哪些东西可以迁、哪些只能包、哪些必须留在 Windows backend、哪些根本不是 P4 production path。
