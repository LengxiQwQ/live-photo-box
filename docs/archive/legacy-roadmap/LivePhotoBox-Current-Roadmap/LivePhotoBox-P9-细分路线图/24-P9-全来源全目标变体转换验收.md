# 协议互转的完整验收要求

> **2026-11-01 现行规则：** 保留等级以 [中性媒体契约 A/B/C](../12-中性媒体契约.md) 为准；执行见 [协议收尾计划](协议收尾执行计划/00-从这里开始.md)。取消强制 B 轮与 C 完整保留，允许完整有效样本先试机，未覆盖/失败/未真机验证继续记录。

**互转必须是来源 → Neutral → 通用媒体转换 → 目标的可复用能力。** 既有来源×目标×格式清单保留；只有声明范围实际走通并有适用验收，才能称该范围完成，局部样本通过不代表全部互转完成。

这条要求适用于所有协议，也适用于以后增加的协议。具体参与本轮验收的协议、格式、变体和样本列在测试清单中，不在本规则里逐个特批。任何延期或排除都必须有用户的明确决定，不能因为某个组合转不出来就自行移出清单。

## 转换功能必须是通用的

**来源负责拆干净，目标负责写正确，中间不按手机品牌分路。** 来源协议的差异在检查、提取和清理时处理完；进入目标转换器后，输入就是中性媒体，不再是“某品牌拍的文件”。目标只根据用户选择的目标协议，以及图片、视频、时间、方向、色彩和辅助资产等实际内容决定怎么生成。

识别并清理不同来源协议，需要各自的解析规则；生成不同目标协议，也需要各自的写入规则。这两端可以有协议差异，但不能在中间增加“来源A转目标B”的专用组合。以后支持新来源，只补它的解析和清理，不应挨个修改所有目标；以后支持新目标，只补它的写入和验证，不应挨个修改所有来源。

图片格式、视频编码、合法容器结构和辅助资产不同，可以调用相应的通用处理能力。判断依据必须是实际结构和中性语义，不能是品牌名、机型、文件名、来源协议或样本hash。来源记录只用于诊断和追踪，不得决定目标布局、放行条件或保留待遇。也不能把品牌判断藏进另一层helper、转换服务或白名单。

“拆干净”只表示来源绑定移除，不授权盲删正常媒体。A 语义必须正确提取/处理，B 用现成可靠能力保留，C 不要求跨协议承接。未知字段先按实际功能判断，不凭名称删，也不因未知就强制补观察接口/特殊封装/全字节证明。若私有字段承载封面时间、颜色解释或播放等 A 功能，应提取其通用语义，不完整搬运厂商记录。

## 发现互转失败时先查哪里

先确认来源解耦、主图/视频/有效音频及 A 语义是否正确，中性模型是否表达必要内容。属于 A 的实际通用缺口才局部修解析/清理/转换/写入；复用 P5/P6，不重开媒体工程，也不把原来源偷偷交目标重猜。

如果中性媒体已经合格，再查通用媒体准备或目标写入缺少哪项能力。修复应对所有具有同类结构和语义的输入生效。某个样本发现的问题可以用它复现，但最终修复不能只认识这个样本或这个品牌。

再问是否影响 A、是否通用缺陷、是否确需改架构、现有编解码/容器能力能否解决。A 无法保证则对应范围未完成；B 无法可靠保留可如实降级（HDR→正常 SDR），C 无需跨协议保留，均不自动派新任务。不能用“不认识来源”作为理由，或把已知损失宣称保留。

验收必须补查通用性：相同中性内容和相同目标选择，不应因来源标签不同而得到不同的目标布局、不同的允许条件或不同的保留结果。要用不同来源但同类结构的真实文件交叉验证，检查实际目标调用链没有来源品牌分支。完整互转矩阵验证的是同一套通用能力，而不是证明一堆专用转换分支碰巧能跑通。

## 测试怎么做

收齐各来源协议的真实文件，先逐份完成检查、提取和清理，生成中性媒体，再分别转换成每一个目标协议及其支持的全部格式和变体。成对文件作为一组处理，A 内容不能漏；B/C 按等级记录，不要求所有辅助资产迁移。

测试表按“来源文件 × 目标协议 × 目标格式及变体”展开。每一个宣称通过的合法组合都须实际执行并有成品；未覆盖组合继续记录，局部开发不每次全跑。跨协议转换是必测项，同协议拆开后再合成也可以测，但不能代替跨协议测试。缺少某个来源或变体的真实样本，就明确记为缺覆盖，不能用别的样本代签。

转换始终走“来源 → 中性媒体 → 目标”的生产流程。中性媒体承载实际内容和语义，不要求所有来源先压成一种固定图片、视频格式；目标也不能根据来源品牌走另一条临时拼接或绕过检查的路线。

清单要同时保留成功、失败和未执行的组合，并记录来源、目标、格式、变体及实际成品。不能预设成功数字凑数；可先交已检查成功样本，但同时说明完整清单中的失败/未执行范围，不冒称全范围通过。

## 什么才算通过

转换完成后，要关闭并重新打开最终文件，检查目标协议结构，并通过独立的图片、视频和音频检查。仅有程序返回成功、文件存在或软件自己能读回来，都不够。

每份成品核对 A 级画面、封面对应、方向/镜像、完整时长、声音/同步、基础颜色、目标结构与安全。B 级按现成能力和已知结果记录，HDR 未保留可正确降 SDR，不能宣称保留；C 不新增字节清点或承接证明。允许重新编码、容器变化及合理位深转换，不要求原字段、轨道、字节一致；现有精确证明只在其真实范围使用。

**正常真实文件转不出来，对应组合仍未完成。** 报“不支持”、无输出或未执行都不能算转换通过；但不因 B/C 缺少完整保留就要求扩建，先重新分类。确认影响 A 的通用缺陷才局部修复并定向重测；本次不修代码。正确拒绝损坏输入属于另一类测试，不能拿它充当互转成功；也不能仅凭软件报错就断言原文件损坏。

需要设备接受声明的成品要在对应目标真实设备或应用中测试，确认能导入、识别、显示和播放，并核对声音、方向、封面及其他适用行为。一个来源、一个格式或一个设备上的通过，不能替其他未测文件盖章。缺设备或缺结果就保留未完成，不能用电脑解码成功代替目标设备接受。

## 什么时候做

复用已接通的正式 CLI/共用 Core 和 P5/P6 基础，优先主要目标 Writer/Validator。已通过电脑检查的完整有效样本可先试机，不等该目标其他来源组合或所有协议齐备。优先身边设备，再商场组；阶段收口按实际风险补必要全面验证，308 行不是每次局部修改的门槛。只按 A 基础功能与真实设备/入口验收收口，B 不自动立项、不补专项矩阵，C 退出，不再强制第二保留轮。R9 核对最终声明范围和真实缺口，未覆盖/失败/未测不能虚报通过。

实际产品入口也必须能生成和使用这些合格结果，不能出现内部服务通过、用户实际操作却失败的情况。代码或输出发生变化后，补测受影响的转换和设备行为。有效旧证据可以复用，但必须确实适用于最终版本。

最后的独立审查既要查文件和结果是否真实，也要查是否漏了来源、目标、格式或变体。声明范围的 A/安全及真实设备必需条件未满足时不能称该范围完成；不能靠局部通过、删行或推给 P10 掩盖缺口。B/C 不作为新增阻断，也不转成未来强制任务。

## 怎么交付测试文件

直接提供一个平铺文件夹，所有已准备的目标协议、格式和变体都放在其中，禁止创建子文件夹。文件名标清来源协议/格式、目标协议/版本/格式和稳定编号，双文件同basename；附完整清单和实际结果。允许按明确覆盖范围分批提供已检查的完整有效样本；双文件成套，失败样本不交付，其他未覆盖或失败范围如实说明。由正式CLI生成成品，脚本不能代做转换/修改交付媒体。用户能直接取文件测试，不必先填写设备资料；整理正式兼容结论时补齐测试条件和文件身份。详细规则见[真机交付与反馈](协议收尾执行计划/02-真机交付与反馈.md)。

具体样本数量、各协议选项、当前失败项、执行命令和运行记录放在对应测试任务中维护。这篇规则只规定所有协议共同遵守的验收方法，不把某一次测试进度写成长期要求。
