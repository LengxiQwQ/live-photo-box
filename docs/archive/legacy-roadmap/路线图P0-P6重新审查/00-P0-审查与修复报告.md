## 1. P0 当前真实状态与总体判断

P0 的核心契约是 **Rebuilt-only 运行时固化**：彻底移除对外部 FFmpeg/ExifTool 等命令行媒体子进程的生产依赖，由 C++20 Native（`LivePhotoBox.Native.dll`）负责底层媒体与容器操作，C# 负责工作流调度与业务契约编排；生产运行时禁止回退到 Legacy 模式，输入非法或缺失时必须 Fail-Closed。

### 核心结论：是否值得信任以支撑 P8、P9、P10？
**结论：有条件值得信任（Conditional Trust）。**
- **底层与运行时架构（Native ABI / Rebuilt 管道 / C# 编排）**：已建立严格的边界与防御性架构，无外部 CLI 生产进程依赖，且架构看门狗测试有效阻断 Legacy 符号回流。
- **已修复缺陷**：本轮已定位并修复 2 项测试断言与服务边界缺陷，并清除了生成过时 FFmpeg 参数的死代码；针对 P0 的 45 项单元测试已实现 **100% 通过（45 Passed, 0 Failed）**。
- **阻碍无条件信任的关键未决项（需移交高级模型 GPT-6.1 Sol 裁决）**：
  1. GUI 编辑导出链路（`EditExportService`）存在捕获并静默吞掉 ExifTool 不可用异常的“假成功”隐患；
  2. Native 层的结构化日志回调在 C# 宿主端未实际接通（传指针 `0`），导致原生诊断日志丢失；
  3. `LivePhotoSplitService` 内部残留约 1000 行旧版正则与字节嗅探技术债，且有 GUI 缩略图调用绕过 `SourceInspector` 管道。

## 2. 已确认可靠的部分

1. **Rebuilt 架构防线严密**：
   - `ArchitectureGuard_NoLegacyRuntimeOrRequireLegacySymbols` 等架构测试确保 Core 程序集中不存在 `ProcessingPipelineMode` 开关，也不存在唤醒 Legacy 运行时的旁路。
   - `ProcessingPipelineRouter.RunRebuiltAsync` 统一控制核心服务入口（`merge`、`split`、`cover`、`repair`），对于尚未就绪的管道统一抛出 `RebuiltPipelineNotReadyException`。
2. **Native C ABI 规范严密**：
   - 跨语言边界仅通过 C ABI 传递 POD 结构体和不透明句柄（`NativeContextOptions`、`NativeSourceMediaFacts`、`NativeResult`），结构体带 `StructSize` 和 `AbiVersion`，在 ABI 错配时严格 Fail-Closed。
3. **真实运行时探针（NativeRuntime.Probe）**：
   - 能够真实反映底层原生库（`libjpeg-turbo 3.2.0`、`libheif 1.23.4`、`project-isobmff`、`minimal-libav 9.0.1`）的加载与能力状态。

## 5. 移交给高级模型（GPT-6.1 Sol）的审查与裁决清单

以下问题复杂度较高，涉及跨模块协同、用户数据元数据保护或 Native 线程安全，需由高级模型审查并裁定实施方案：

### 问题 1 (L2)：`EditExportService` 的 EXIF 复制降级与假成功处理
- **定位**: `LivePhotoBox\Services\EditExportService.cs:832`
- **现象**:
  ```csharp
  // EditExportService.CopyExifForExportAsync:
  await LivePhotoRepairService.RunExifToolAsync(token, "-TagsFromFile", ...);
  ```
  而在 Rebuilt 运行时中：
  ```csharp
  // LivePhotoRepairService:
  throw new NotSupportedException("ExifTool has been removed from LivePhotoBox.");
  ```
  外层 `CopyExifForExportAsync` 使用空 `catch (Exception ex)` 记录 Warning 后继续执行，最终向用户弹窗“导出成功”。
- **风险**: 用户编辑实况照片后导出的图片丢失原始相机的拍摄时间、地点、机型、镜头参数，构成破坏性静默故障。
- **建议 GPT-6.1 Sol 裁决**:
  1. 方案 A：在 P6/P8 体系中引入基于 Native / ExifLib 的纯内存/无进程 EXIF 复制机制。
  2. 方案 B：若编辑导出不在当前 Phase 交付范围内，必须明确提示用户“当前版本暂未支持无损元数据复制”，或 Fail-Closed 阻止假成功发布。

### 问题 2 (L3)：Native 日志回调接通与线程生命周期
- **定位**: `LivePhotoBox.Core\Interop\NativeContext.cs:44`
- **现象**:
  ```csharp
  var options = new NativeContextOptions
  {
      StructSize = checked((uint)sizeof(NativeContextOptions)),
      AbiVersion = NativeMethods.ExpectedAbiVersion,
      LogCallback = nint.Zero, // <-- 未接通！
      LogUserContext = nint.Zero
  };
  ```
  Native 内部大量使用 `lpb_log(context, ...)` 记录 ISOBMFF box 解析异常、MFT 编码器选择理由及 Libheif 警告，但由于 C# 传入空指针，所有日志直接丢失。
- **建议 GPT-6.1 Sol 裁决**:
  1. 在 C# 端实现持久化委托（防止 GC 回收被 Native 调用的委托函数指针），挂接到 `LivePhotoBox.Services.LogService`。
  2. 审查跨线程回调的安全性（Native 线程调用 C# 托管委托时的线程上下文绑定与异常安全）。

### 问题 3 (L2)：`LivePhotoSplitService` 巨石代码剥离与 GUI 契约收敛
- **定位**: `LivePhotoBox.Core\Services\LivePhotoSplitService.cs`
- **现象**: 该类中除了规范的 `SplitRebuiltAsync` 外，还堆积了 1000 多行早期旧版解析逻辑（如 `GetHuaweiEmbeddedVideoRange`、`ExtractMiMetadata` 等）。GUI 的 `LightboxItemSource.cs` 和 `MagickHeicThumbnailProvider.cs` 依然绕过规范架构，直接调用这些静态旧方法。
- **建议 GPT-6.1 Sol 裁决**:
  1. 将缩略图探测逻辑统一迁移至 `SourceInspector`。
  2. 评估是否在 P0/P1 重构收尾中彻底删除这些未受保护的旧解析方法，将文件精简至仅保留发布协调逻辑。
