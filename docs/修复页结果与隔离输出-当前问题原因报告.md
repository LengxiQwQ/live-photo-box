# 修复页结果与隔离输出：当前问题现状、原因及证据

日期：2026-11-06。性质：只读调查与现状报告，不是修复完成证明。本次调查没有修改产品代码、测试或既有媒体成品。

## 1. 结论

当前问题不只是一个错误用词，而是修复结果没有被完整传递到界面：**做了哪些修复、哪些没有完成、为什么没有完成、是否实际生成文件、文件在哪里**，没有成为一份统一的逐项结果。

已经确认以下缺陷：

1. `warning` 既能表示“部分修复并已输出隔离副本”，也能表示“没有实际修复，也没有输出”。界面却把二者统一显示成“部分处理，已隔离”。后者属于明确的事实性错误。
2. 单个文件的状态、文件对的整体状态和输出是否隔离没有独立表达。可能出现照片动作完成、视频原样复制、整组隔离，但汇总没有准确反映整组的未完成原因。
3. 界面详情以拼接文字为主，没有稳定的“已修复／未完成／原因／输出”结构。部分 Native 原因还是英文，不能要求用户从长段技术信息中自行判断是否修好。
4. 修复选项数量主要按文件类型和 `NeedsRebuild` 统计，遗漏了单文件内嵌视频与 `Limited` 项。可能出现内嵌视频实际会被检查，但界面计数为零、选项灰色而内部仍保留默认选中的情况。
5. 输出按钮使用配置的输出根目录，不使用逐项实际发布路径；点击处理函数还包含创建不存在目录的逻辑。打开了一个目录本身不能证明有成品。
6. 完成日志只记录 repaired／skipped／failed 总数，没有记录每个文件的动作、黄色原因与最终路径。通知也没有携带黄色结果的完整分类。关闭应用后不能可靠恢复那次逐项结果。

上一轮新增华为处理时，我让“可读但尚未完成、无输出”返回了 `warning`，却没有同步修正现有界面、统计和日志语义，这是本轮引入并遗漏处理的问题。既有其他协议的隔离分支也需要一起对齐，不能只改华为一处文案。

## 4. 黄色与隔离实际因为什么出现

“隔离”在本项目中的含义是：把已生成但仍有明确未完成项或相关不确定性的副本，放在普通输出之外的 `_isolated` 子目录。不是把来源文件当病毒，也不是移动原件。

| 当前触发情况 | 实际已做／未做 | 当前结果与问题 |
|---|---|---|
| 华为照片无修复动作，但选中了尚未执行的内嵌视频方向规范化 | 照片检查完成；视频保持原字节；没有完成视频画面转正 | 返回 `warning`，默认无文件；界面却说“已隔离”，属于错误 |
| 华为有照片动作完成，但内嵌视频方向仍未规范化 | 已完成所能安全处理的照片动作；视频不改 | 实际生成 `_isolated` 副本；只能称部分完成 |
| 用户明确选择复制正常文件，同时存在未完成项 | 复制原字节，没有把未完成修复变成完成 | 可以生成隔离的原样副本；必须标明“原样复制，未修复”，现有文字没有充分区分 |
| 普通复合 JPEG 的方向无法安全变换，但能清理独立缩略图 | 缩略图处理完成，原方向或附加媒体保留 | 已生成副本时隔离；若任何动作都没完成，部分既有分支返回失败，与华为无输出黄色的表达不一致 |
| 旧 vivo 配对视频方向尚无安全重建路径 | 可以清理照片缩略图，视频与配对信息原样保留 | 有可用修复时隔离；不能说整个文件对已全部修复 |
| Apple 配对 MOV／照片未找到，或已选检查不能确认 | 只处理已确认的部分，不猜配 | 可用副本隔离；详情必须说明缺的是哪一份、影响什么 |
| 视频已经转码，但来源元数据保留未获完整验证 | 画面方向动作可能已完成，相关元数据仍有不确定性 | 隔离不等于视频完全失败，也不能无条件算全部成功 |
| 三星照片部分修复做不了，但主视频或自动播放视频已完成可验证动作 | 保留原照片，保留已完成的视频处理 | Native 返回部分结果，副本隔离；应说清具体是哪一部分未完成 |

这些是从当前分支读出的原因分类，**不能仅凭“已隔离”四个字判断用户点开的那一项属于哪一行。** 用户那次日志缺少逐文件记录，尚不能把所有黄色项逐一归因。

其中两份 Mate80 原图在已有定向记录中均带 90° 视频显示矩阵。显示矩阵告诉播放器怎样显示画面，本身不等于视频损坏。当前实现把“用户选中了视频方向烘焙，但华为专用入口没有执行它”记为未完成。它与延期的 HDR Vivid→H.264 导出是不同问题，本次没有恢复后者。

## 5. 为什么界面没有把原因讲清楚

### 5.1 结果模型信息不足

`LivePhotoRepairService.cs:20` 的 `RepairResult` 主要只有 `Status`、自由文字 `Message` 和可空的 `Image`／`Video` 路径，另有图片／视频成员状态。没有统一的已选动作、动作完成结果、未完成原因和输出发布类型。

`LivePhotoRepairService.cs:354` 明确能返回 `warning` 且不带任何输出路径。因此，从代码中已经可以确定：**warning 不必然等于已导出，更不必然等于已隔离。**

### 5.2 显示只看状态字符串

`RepairTask.cs:205` 把结果状态映射到 `Repair_Outcome_*`，`RepairTask.cs:234` 再用该状态选显示文字。`Resources.resw` 中 `Repair_Outcome_warning` 固定为“部分处理，已隔离；未完成动作与实际输出位置见详情”。这个分支没有核对是否真的存在已发布输出。

详情虽然追加了 `result.Image`、`result.Video`，但它们为空时只是不显示，没有“本次未生成文件”这一明确事实。用户看到前面的“已隔离”，自然会去找不存在的文件。

### 5.3 动作完成与整组隔离混在一起

普通配对分支可返回整组 `warning`，同时把照片成员标为 `success`、视频成员标为 `copied`。这可能忠实表示“照片动作完成、视频原样复制”，但没有独立保留“这两份实际输出均因整组限制而放入隔离目录”的界面事实。

按成员 `ExecutionStatus` 汇总时，整组的黄色也可能没有进入相应计数。不能通过把所有成员强制改成同一种文字解决，应分别显示成员动作和整组输出限制。

### 5.4 选项计数与执行不一致

`RepairViewModel.cs:1571` 的对话框先跳过 `!entry.NeedsRepair` 项，再主要根据 `ar.IsVideo` 和文件扩展名统计动作。单文件动态照片的内嵌视频不是独立视频条目，`Limited` 项也可能被排除。

因此，只有单文件内嵌视频时可能显示视频动作数量为 0、复选框禁用，但底层默认选项仍为 true，并在执行时检查视频方向，最终产生用户不容易理解的未完成结果。此问题由代码确认；不能据此断言用户那次混批对话框必然处于该状态。

### 5.5 输出入口与实际结果没有绑定

`RepairViewModel.cs:1957` 按设置返回输出根目录；`OpenRepairOutputFolder` 不按当前选中项的发布路径定位 `_isolated`。方法还包含创建不存在目录的代码，虽然命令可执行性通常会先检查目录存在，仍不应把“打开配置目录”当成“定位本次成品”。

### 5.6 汇总和日志丢失关键事实

界面汇总把所有 `warning` 算成“隔离”；完成日志 `RepairViewModel.cs:615` 只记修复、跳过、失败三类，通知也只传递成功／失败等有限字段。

项目已有持久终态历史机制，但 `ProductOperationKind` 当前只包含 Split／Merge，现有有效性规则也假定 warning 带隔离输出。Repair 没有接入逐项结果持久化，不能直接生搬该格式来容纳无输出的未完成结果。

## 7. 影响与责任边界

- 用户无法根据完成提示判断“检查过”还是“修过”，也无法判断“部分完成”还是“完全没做”。
- 用户可能寻找不存在的隔离目录，也可能把原样副本误认为修复成品。
- 文件对中某个成员的动作成功，可能掩盖整组仍有未完成项；只有总数的日志无法事后解释。
- 当前没有证据表明这句“隔离”表示移动、删除或感染了原件，也没有证据表明该显示缺陷本身改变了媒体字节。正常修复发布路径是生成新副本。
- 本次没有重新逐一核验用户那次 17 份输入的历史指纹，不能据此对整批来源的历史状态作额外保证。此前两份 Mate80 的已记录指纹和定向原件保护证据，仍仅按其范围使用。
- 上一轮主要验证了媒体处理和 CLI，没有把“无输出时不能显示已隔离”纳入界面结果验收。我此前用“本轮已修好”概括交付，范围表达过宽；准确结论应为“华为有界照片处理能力已接通并有定向证据，结果说明和输出定位仍存在未完成缺陷”。
