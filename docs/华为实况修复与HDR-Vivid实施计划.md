# 华为实况修复与 HDR Vivid 实施计划

制定日期：2026-11-06。状态：M1／M2 实现与定向电脑检查完成；M3 公开获取条件核实完成，授权代码待提供；M4 未实现，GUI／设备与完整 HDR 显色未验。

本计划依据用户本次决定：以实际媒体修复为主线，先完成保留原 HDR 的华为实况修复；同步明确 HDR Vivid 专用算法、工具与依赖的可行性；结果说明和输出定位必须随实际功能一起完成，不能代替媒体能力。

## 1. 交付目标与固定边界

### 1.1 第一轮要真正交付什么

对现有 `华为Mate80.heic` 和 `华为-Mate80.jpg`：

1. 按华为实际结构识别照片、完整内嵌 MP4 和 60 字节尾标。
2. 对需要的视频方向／镜像执行实际画面转正，输出仍为 HEVC 10 位 HLG，并保留对应显示时间的 HDR Vivid 数据。
3. 保留原 AAC 声音、原数据轨和封面信息，重组为完整华为单文件实况副本。
4. 按实际结果告诉用户：检查了什么、修了什么、未完成什么、为什么、是否输出以及真实成品位置。
5. 形成有界电脑验证结果和供用户真机检查的成品清单。

这不是“所有华为设备已经兼容”的承诺。完整成品的手机相册识别、播放、HDR 显示和封面行为仍须设备验证。

### 1.2 已确定的产品与工程边界

- 默认仍只处理 Apple／Samsung。Huawei 在关闭设备限制或 CLI 使用 `--all-devices` 后处理。
- 生产保持 Rebuilt-only、Source → Neutral → Target 的既有总原则；Repair 的协议重组只限其源实况结构，不借机另造转换主线。
- C# 负责编排和结果，C++ Native 负责媒体字节。生产不调用外部 FFmpeg／ExifTool 等命令行；离线独立检查可以使用工具。
- 普通未知私有信息尽量原样保留，不因不认识就全部拒绝；承担主图、方向、声音、时间、封面或正确显示等基础功能的字段不能忽略。其余私有数据不扩建跨品牌全保留系统。
- 不修改原件、不覆盖已有文件；逐项处理，单个外部文件问题不造成闪退、未处理异常或整批停止。
- 视频转正需要重编码，沿用当前修复 CRF 18。不能称视频像素无损，也不能用保留 HDR 标记代替画面质量验证。
- 用户此前暂停的两项 HDR Vivid→H.264 导出不在第一轮恢复；SDR 转 Vivid、重新调色、所有格式／所有机型支持均不是本轮交付。
- 不提交、推送、打包、发布；不擅自接管桌面、创建外部账号、申请会员或发送联系邮件。

## 4. M1：补齐真实华为修复后端

主要落点是 `LivePhotoBox.Native/src/media/huawei_repair.cpp`，复用现有 Inspector、视频方向后端、主视频替换和发布能力。

### 4.1 有界结构与照片动作

- Inspector 确认主图、视频、尾标及包装的范围与来源身份；支持原厂裸拼和现有显式定长 `free` 包装。
- 沿用主图缩略图／预览清理、HEIC 显示变换与 EXIF 对齐、符合条件的 JPEG 完美无损变换。
- 各照片动作独立尝试。一个动作受限时不丢弃其他安全动作；未知普通内容保留。受影响的主图／辅助图关系必须按已确认结构处理，不能把 HDR 辅助图当缩略图删除。
- 不根据文件名、机型或样本指纹选择媒体算法；样本名称和指纹仅用于测试身份。

### 4.2 实际执行内嵌视频转正

采用已经验证过的固定路径，不增加生产旁路：

```text
确认的原始 MP4 → 现有视频修复后端 → 转正后的中间 MP4
确认的原始 MP4 + 中间 MP4 → 只替换主视频 → 保留其他内容的完整 MP4
```

- 根据实际旋转／镜像决定是否编码；没有方向动作需求时直接保留原视频。
- 调用当前 `repair_orientation` 路径，保持原 codec／container；两份现有样本继续使用 HEVC Main10、BT.2020 HLG。
- 不借用三星专属颜色纠正，不进入 HLG→SDR 兼容转换。将 Vivid 信息绑定到原对应的显示帧，不按编码包顺序直接对应。
- 使用原始 MP4 作保留基础，以现有主视频替换函数承接新主视频。编码器输出丢掉的音轨、数据轨或普通元数据不能随之丢掉。
- 不进行去噪、调色、亮度调整、裁切或缩放，不在此阶段重新生成 Vivid 动态参数。
- 中间文件只是暂存结果，不能直接暴露为已经完成的华为实况成品。

### 4.3 接口、暂存文件和动作位

- 保持 `lpb_repair_huawei_v1` 现有签名、请求选项和 POD 布局；使用已经保留的位 8 表达视频方向动作。
- 空输出诊断只进行结构／能力预检，不实际重编码。诊断中的待执行动作与执行后的已完成动作分开，不能让 dry-run 成为修复成功。
- 执行时以现有托管 `MediaWorkspace` 分配的输出路径父目录作为工作目录，Native 只在该工作目录中建立有明确角色的暂存文件，不使用用户来源目录作为临时工作区。
- 补齐托管输出凭据捕获：不能继续假设 Native 只注册一个文件；按本工作目录内允许的中间角色与最终暂存角色校验并登记拥有权。失败／取消时也收集已创建对象的凭据，安全清理，不能按路径猜删。
- 实际完成视频动作并形成验证结果后设置动作位；清除已解决的 pending。保留未完成动作及原因，不把内部错误伪装成源文件不支持。
- 复用现有身份、指纹、取消、受控错误和不覆盖发布规则；不让新 helper 形成不受保护的裸写入口。

### 4.4 重组完整华为文件

- 按已确认的主图／间隔或包装／新 MP4／尾标组装，保留不需要修改的照片与普通间隔数据。
- `LIVE_` 更新为新 MP4 长度＋20，检查十进制字段容量、整数溢出与实际文件范围。
- 有 `free` 包装时更新显式包装长度；无包装时保留原厂裸拼布局，不无理由换壳。
- 优先保持电影级封面元数据的原所有者、类型和值，不套用目标协议制作器重写其外观。
- 保留尾部历史字段；只有显示时间／对应帧关系确实变化时才按协议作有证据的映射。若验证显示时间不变，旧封面帧关系也应保持。
- 不顺带压缩原 MP4 中已经不再引用的旧视频存储，避免增加清理权限和偏移重写范围；成品体积可能增加，明确报告视频重编码与实际大小。

### 4.5 改为与实际动作相符的验证

| 未执行视频动作 | 已执行视频动作 |
|---|---|
| 保留视频字节指纹一致要求 | 不再要求新旧视频长度或全部字节一致 |
| 保留原音视频时间与尾标关系 | 核对转正后的实际画面、尺寸、无旧旋转／镜像矩阵 |
| 以照片动作的实际变化验主图 | 核对帧数、显示时间、声音、同步及封面对应关系 |
| 不制造视频变化 | 核对原 AAC 和应保留的数据轨样本／时间、电影级元数据及有关颜色标记 |
| 未改动的 HDR 信息保持原样 | 核对 10 位、HLG、Vivid 载荷及逐显示时间绑定，不只检查一个 HDR 标签 |

Native 验证须形成针对实际变换的 before／after 证据。不能直接移除旧校验后宣布绿色，也不能继续用“普通转码的全量元数据指纹不同”否定已经通过有界映射验证的正确修复。

## 7. M3：HDR Vivid 专用算法与工具评估

### 7.1 候选优先级

| 候选 | 用途与选择理由 | 需要核实的部分 |
|---|---|---|
| UWA 解码侧 C++ CPU 参考实现 | 首选算法评估来源；官方文档说明使用动态参数进行映射，并有 HLG＋Vivid 处理说明 | 能否取得、对应标准与版本、实际接口、样本输出、构建和分发条件 |
| UWA Windows Direct3D 参考实现 | 作为 Windows 显示／预览和后续加速参考 | 是否覆盖本项目输入、GPU 与驱动要求、是否确有性能必要 |
| UWA 编码侧／编码转码参考代码 | 了解参数生成、保留转码及更广的处理能力 | 不把能生成参数等同能保持原厂调色，也不自动纳入本轮 |
| FFmpeg 的 Vivid 元数据能力 | 复用解析和帧关联，不重写已经可靠的编码解码基础 | 解析与实际色调映射必须分开证明；当前精简库没有开启 avfilter |
| libplacebo | 通用色彩和 GPU 处理候选 | 本次未确认开箱即用消费 Vivid 专属曲线的完整接口，不作为已经解决 Vivid 的依据 |
| HarmonyOS／OpenHarmony VPE | 系统实现与算法接线参考 | 存在系统组件依赖，不能把 HarmonyOS PC 支持当作 Windows DLL 支持；不作当前 Windows 主线首选 |

### 7.2 评估动作及交付

1. 记录可公开获取的文档、源码和工具，以及需要会员、申请、合作授权的部分；没有取得的内容标为未验证。
2. 对可合法获取的算法在独立开发目录做最小 C++ 调用试验，不先加入生产依赖。
3. 用现有 HLG＋Vivid 样本及官方可获得测试码流核对参数解析、映射输出、异常数据、精度、性能和资源消耗；PQ 与其他版本单列覆盖。
4. 优先用 UWA 元数据检查工具、专用 ffprobe、参考码流／渲染结果作独立对照。普通播放器能打开或一般 HLG 转换看起来正常，不算 Vivid 映射正确。
5. 输出一份明确结论：推荐实现、实际已通过能力、未覆盖类型、授权／打包影响、是否需要 GPU、预计影响的现有路径、M4 的具体输入和输出合同。

没有 UWA 代码／工具或授权条件不确定时，记录缺口，不虚构可用 SDK，不替用户申请或联系第三方。可继续 M1／M2 及不依赖它的公开资料验证；需要用户身份、费用或分发决定时，带着具体材料说明，而不是让整个已有修复工作停摆。

## 8. M4：完整 Vivid 色彩处理的条件阶段

M3 推荐通过、具体生产依赖与输出目标得到决定后，才开始该阶段。不能在尚未取得源码时承诺某个 SDK 能解决全部输入。

默认技术方向是：**现有解码 → 独立 C++ Vivid 帧处理 → 现有编码／重组**。算法隐藏在 Native 内部，通过项目已有 C ABI／POD 边界提供能力；首选 CPU 正确性闭环，GPU 加速只有实际性能证据需要时再加。

该阶段的能力清单由 M3 按实际评估锁定，至少分清：

- 保持原 HDR 的转码与几何处理：优先保留现有参数及正确关联，不无理由重新生成。
- Vivid 颜色映射：真正使用有关动态参数，核对目标亮度、色域、位深和输出标记；不能只换标签或丢掉参数。
- 输出 SDR：只有用户明确选择相应转换时才进行，明确其 HDR 降级；不能代替用户要求的保留 HDR。
- 输出其他 HDR：逐目标核对语义和承载，不能承诺任意格式无损保持同一种效果。
- 重新调色／参数生成：不是简单方向修复的必需项，不默认扩成创作系统。

此前暂停的两项 H.264 导出保持为独立待恢复事项。即使 M3 找到方案，也须明确更新其范围和验收后再施工，不能顺带把它们记为通过。

实现还解决了两个成品校验中的实际问题：

- 替换视频轨时，从编码器高精度时间尺度换回原电影尺度，按最近值取整会裁掉末帧不足一毫秒的覆盖范围。主视频替换现使用向上覆盖的时长换算，完整末帧得以保留。
- HEVC 的 hvc1／hev1 都属于同一编码；静态 HDR 信息可以从 hvcC 配置移到首个访问单元并持续生效。新增核验按这些实际语义比较，仍逐显示帧核对 Vivid；编码器增加的替代传递函数 SEI 只在与独立读到的 CICP 相符时接受。没有放宽来源配对、文件身份或边界校验。
