# 原生引擎重构规划（Native Media Engine Refactor Plan）

> 本文档是 **Live Photo Box 下一代媒体核心** 的长期执行规划。
> 目标读者是后续接手开发的 AI 或人类开发者。
> 如果你第一次进入这个项目，请按顺序先读下面的“上手阅读顺序”，再读本文档。

---

## 0. 文档目的

当前项目大部分功能可用，但存在以下核心问题：

- 元数据写入依赖 ExifTool 命令行；
- 视频、HEIC、JPEG 处理依赖外部 exe；
- 协议实现和外部工具调用散落在 Core、GUI、CLI 多处；
- 部分场景 HDR 丢失；
- 原始实况照片标记剥离不干净；
- XMP / 操作历史写入路径不统一，可能产生双 XMP 或文件错乱。

本规划的目标是把项目逐步迁移到：

```text
C# 负责流程、UI、CLI、历史记录
C++ native engine 负责文件解析、协议适配、容器写入
libheif / FFmpeg libav* / libjpeg-turbo 负责真正需要的编解码
```

最终不再依赖：

```text
exiftool.exe
ffmpeg.exe
ffprobe.exe
heif-enc.exe
heif-dec.exe
jpegtran.exe
```

这些工具只允许在开发期作为“旧实现参照物”保留。

## 2. 当前状态摘要

### 2.1 项目结构

- `LivePhotoBox.Core`：协议、合成、拆分、修复、元数据服务；
- `LivePhotoBox`：WinUI 3 GUI；
- `LivePhotoBox.CLI`：命令行工具；
- `LivePhotoBox/Tools/`：外部工具二进制，约 45.6 MB，其中 ExifTool 运行目录约 33.4 MB。

### 2.2 当前协议与格式

合并目标协议：

```text
Google Micro Video V1
Google Motion Photo V2
OPPO O-Live Photo
vivo Live Photo
Samsung Motion Photo
HUAWEI Moving Photo
```

合并输出格式：

```text
JPEG + MP4
JPEG + MOV
HEIC + MP4
HEIC + MOV
HEIC + MP4 H.265
```

拆分目标协议：

```text
None
Apple
vivo
```

拆分输出格式：

```text
Keep
JPG + MOV
HEIC + MOV
JPG + MP4
```

协议矩阵以 `LivePhotoBox.Core/Services/ProtocolFormatMatrix.cs` 为合并侧唯一事实源；拆分侧目前仍有一部分矩阵写在 GUI 代码中，重构时应统一。

### 2.3 当前协议实现位置

主要位于：

```text
LivePhotoBox.Core/Services/Protocols/
```

当前已有不少字节级实现，不能直接丢弃，应作为 native engine 的参考实现：

```text

AppleLivePhotoMetadata.cs
AppleLivePhotoMovBuilderV2.cs
AppleLivePhotoMebxWriter.cs
AppleMakerNoteWriter.cs
UltraHdrJpegWriter.cs
HeifAuxImageWriter.cs
HdrGainMapCodec.cs
SamsungMotionPhotoProtocol.cs
HuaweiMovingPhotoProtocol.cs
VivoLivePhotoProtocol.cs
OppoLivePhotoProtocol.cs
MotionPhotoV2Protocol.cs
MicroVideoV1Protocol.cs
```

### 2.4 当前外部工具调用

最典型的问题不是“没有字节级代码”，而是：

- Core 内部直接启动 exiftool / ffmpeg；
- GUI 的 `EditViewModel.cs` 等也直接启动 exiftool / ffmpeg / heif；
- 元数据写入路径分散；
- 同一个文件可能被 exiftool、ffmpeg、自写字节逻辑先后修改。

重构时必须把这些入口收口。

## 3. 核心设计原则

任何阶段都必须遵守以下原则：

### 3.1 只有一个写入口

每种输出文件只允许一个 writer 落盘。

禁止：

```text
先 exiftool 写一次，再 C++ 写一次，再 ffmpeg 写一次。
```

允许：

```text
C# 生成完整 XMP 模型
    → C++ 把 XMP 放到正确容器位置
    → 只写一次临时文件
    → 校验通过后原子替换
```

### 3.2 不认识的字节原样搬

C++ parser 的核心模型不是“值”，而是“区间”。

每个区间至少保存：

```text
offset
length
type
known / unknown
raw bytes
```

写入规则：

```text
已认识的字段：可以修改
不认识的字段：不解释，原样写回
修改后长度变化：只重算必须更新的偏移/长度
```

### 3.3 临时文件 + 校验 + 原子替换

禁止原地改用户源文件。

标准输出流程：

```text
写入临时文件
    → 独立 reader 读回
    → 校验容器结构
    → 校验协议标记
    → 校验媒体可解码
    → 校验 HDR / EXIF / 时间 / 历史
    → 通过后替换目标文件
```

### 3.4 编解码库只在真正需要时使用

默认走无损拆装。

只有用户明确要求转格式 / 转编码时才调用：

```text
libheif
FFmpeg libav*
libjpeg-turbo
```

### 3.5 不做长期用户可见的双引擎开关

可以保留开发期开关：

```text
Legacy
Native
Auto
```

但不要把它作为普通用户长期可选的正式功能。

默认值在重构期间应为 `Legacy` 或 `Auto`，等 native 稳定后再把默认切到 `Native`，最终删除 legacy。

## 4. 目标架构

```text
┌──────────────────────────────────────────────────────┐
│ GUI / CLI                                             │
│ 输入输出、协议选择、格式选择、进度、历史记录、错误处理      │
└───────────────────────────┬──────────────────────────┘
                            │
                            v
┌──────────────────────────────────────────────────────┐
│ C# Media Engine Facade                                 │
│ ILivePhotoEngine                                      │
│ ├─ LegacyEngine  → 旧 C# 服务 + 外部工具                 │
│ └─ NativeEngine  → P/Invoke 调用 C++ native DLL         │
└───────────────────────────┬──────────────────────────┘
                            │
                            v
┌──────────────────────────────────────────────────────┐
│ C++ Native Media Engine                               │
│ ├─ FileMap / Container Parser                          │
│ ├─ JPEG / EXIF / XMP / ICC parser & writer             │
│ ├─ ISOBMFF / QuickTime parser & writer                 │
│ ├─ Protocol Adapters                                   │
│ ├─ Media Reader / Validator                            │
│ └─ codec wrappers                                      │
└───────────┬───────────────────┬───────────────────────┘
            │                   │
            v                   v
     libheif / libav*     libjpeg-turbo
```

### 4.1 语言分工

| 层 | 语言 | 职责 |
|---|---|---|
| 流程、UI、CLI | C# | 用户交互、调度、历史、设置 |
| 协议格式矩阵 | C# | 唯一数据源，GUI/CLI 共用 |
| 文件解析与写入 | C++ | 容器、段、box、协议私有结构 |
| XMP 模型生成 | C# | LPB namespace、dc:subject 历史 |
| XMP 容器写入 | C++ | 把完整 XMP 放进目标文件 |
| 编解码 | C++ 包装库 | libheif / libav* / libjpeg-turbo |
| 读回校验 | C++ 独立 reader | 不能与 writer 共用同一套判断 |

### 4.2 不建议使用 C++/CLI

建议使用：

```text
C++ native DLL + 稳定 C ABI + C# P/Invoke
```

理由：

- 边界清晰；
- C++ 和 C# 构建解耦；
- 方便测试和替换；
- 不会把 UI 和 native 代码耦合在一起。

## 5. 分支与发布策略

### 5.1 建议分支策略

```text
当前稳定版本
    → backup/stable-before-native-refactor
    → refactor/native-media-engine
```

规则：

- 新 native engine 在独立分支开发；
- 主分支开始新优化前，先给当前稳定代码打 tag 或备份分支；
- 重构期间不发布普通用户版本，除非修复严重安全/崩溃问题；
- native 未通过验收前，不合并主分支，不删除 legacy 代码。

### 5.2 开发期引擎开关

```text
Legacy  → 默认
Native  → 仅开发测试
Auto    → native 优先，不支持回退 legacy
```

入口：

```text
CLI: --engine legacy|native|auto
GUI: 隐藏的开发者设置，或暂不提供用户设置
```

新引擎不支持的操作必须自动回退，不能直接报错。

## 6. 阶段规划

下面按“先打地基，再读，再拆，再写，再切”的顺序执行。

---

### 阶段 0：建立稳定基线与测试语料

**目标：**

让后续每一步都有可对比的“正确答案”。

**要做：**

1. 备份当前稳定分支 / 打 tag；
2. 从 `designs/各个机型测试` 建立测试语料索引；
3. 为每个代表性样本记录：
   - 协议；
   - 容器；
   - 是否 HDR；
   - 视频编码；
   - 原始文件 hash；
   - 关键元数据摘要；
4. 写一个测试语料清单文件，建议放：

```text
tests/native-engine-corpus/
```

5. 不要修改 `designs/` 下任何原始样本。

**验收标准：**

- 原始样本 hash 全部可重复计算；
- 每个主要协议至少有 1 个样本；
- HDR 样本被单独标出；
- 当前 `dotnet build` 和 `dotnet test` 通过。

---

### 阶段 1：搭建 Native 项目与 C# 互操作骨架

**目标：**

建立可编译、可调用、可替换的 C++ native 项目。

**要做：**

1. 创建独立目录：

```text
native/
  lpb-media-core/
  lpb-native-interop/
```

2. 定义 C ABI，最初只放少量函数：

```text
LPB_GetVersion
LPB_OpenFile
LPB_CloseFile
LPB_GetLastError
```

3. 写 C# P/Invoke 包装；
4. 用 x64 优先构建；
5. 做一个最小 native smoke test。

**验收标准：**

- native DLL 可被 C# 加载；
- 返回版本号和错误信息正常；
- 不依赖 ExifTool / FFmpeg CLI；
- x64 下无 `BadImageFormatException`。

**注意：**

GUI 当前支持 x86/x64/ARM64，但 native engine 先只做 x64，其他架构显示不支持或回退 legacy。

---

### 阶段 2：实现 FileMap / 容器解析器

**目标：**

这是整个重构的地基。

**要做：**

1. JPEG parser：

```text
SOI
APPn
EXIF
XMP
ICC
SOS
EOI
EOI 之后的所有尾部数据
```

2. ISOBMFF / QuickTime parser：

```text
ftyp
moov
meta
mdat
uuid
free
mpvd
sefd
mebx
```

3. 每个节点保存：

```text
offset
length
type
known/unknown
raw bytes
```

4. 实现“原样 round-trip”：

```text
parse → write → parse
```

**验收标准：**

- 对普通 JPEG、HEIC、MP4、MOV 能 round-trip；
- 未知区间的原始字节完全一致；
- 对华为异常布局、Apple MOV、Samsung HEIC 至少能定位关键结构；
- 解析失败时不崩溃，标记为 opaque region。

---

### 阶段 3：接入 libheif / FFmpeg / libjpeg-turbo

**目标：**

让 native engine 拥有真正的编解码能力，但只在需要时调用。

**要做：**

1. 先按当前 `外部工具定制编译指南.md` 的最小化思路编译静态库，不直接使用完整发行包；
2. 封装：

```text
HEIC 解码 / 编码
视频探测 / remux / 转码
JPEG 解码 / 编码 / 无损旋转
```

3. 所有媒体操作走库 API，不走命令行；
4. 为 HDR 保留单独做输入输出参数。

**验收标准：**

- 能解码 HEIC；
- 能编码 HEIC；
- 能 remux 视频；
- 能提取帧；
- 能无损旋转 JPEG；
- 不再调用外部 exe。

---

### 阶段 4：实现 native 检测与元数据读取

**目标：**

替换 ExifTool 的“读取/查看”职责。

**要做：**

1. 实现协议检测：

```text
Google V1 / V2
OPPO
vivo
Samsung
HUAWEI / Honor
Apple
```

2. 实现元数据读取：

```text
宽高
日期
EXIF
XMP
旋转
时长
音频视频编码
ContentIdentifier
封面时间
```

3. 输出统一的 C# DTO。

**验收标准：**

- native 读取结果与当前 legacy/exiftool 结果一致；
- 能读取 HDR 标志；
- 能读取 Apple / vivo 配对信息；
- 能读取 HUAWEI `LIVE_` / `covertime`。

---

### 阶段 5：实现 native 无损拆分与源标记剥离

**目标：**

把当前拆分和 SourceProtocolCleaner 的能力下沉到 C++。

**要做：**

1. 拆分：

```text
单文件 JPEG + 嵌入视频
单文件 HEIC + 嵌入视频
Samsung Trailer
HUAWEI LIVE_
```

2. 剥离源文件标记：

```text
Apple ContentIdentifier
Apple live-photo keys
Apple mebx track
vivo JPEG 尾标
vivo MP4 uuid
OPPO UserComment
vivo UserComment
```

3. 剥离时必须保留：

```text
HDR
EXIF
ICC
厂商私有数据
```

**验收标准：**

- 拆出的照片可正常打开；
- 拆出的视频可正常播放；
- 不再残留“我是实况照片”的旧标记；
- 未知私有字节不被误删。

---

### 阶段 6：实现 XMP 与操作历史统一写入

**目标：**

解决当前最严重的 XMP / 历史错乱问题。

**要做：**

1. C# 生成完整 XMP 模型：

```text
LPB namespace
Version
Timestamp
File ID
dc:subject 历史
```

2. C++ 负责容器放置：

```text
JPEG APP1
HEIC meta
MP4 / MOV uuid
```

3. 同一文件只写一次；
4. 不重复添加双 XMP；
5. 读回时优先解析本工具最新 XMP。

**验收标准：**

- 输出文件只有一份最新 XMP；
- 历史记录可读；
- 旧记录迁移正确；
- 华为 HEIC 等特殊布局可用；
- 校验器能识别单份 XMP。

---

### 阶段 7：逐个迁移协议 Adapter

**目标：**

把协议生成能力从 C# 迁到 C++。

**建议顺序：**

```text
Google V1
Google V2
OPPO
vivo
Samsung
HUAWEI
Apple
```

理由：

- V1/V2 公开标准最多，最容易验证架构；
- OPPO / vivo 主要是 XMP 扩展；
- Samsung / HUAWEI 私有二进制较多；
- Apple 的 MOV / mebx 结构最复杂，放最后。

**每个协议要做：**

1. 定义协议描述；
2. 实现解析；
3. 实现生成；
4. 实现校验；
5. 跑真机样本对比。

**验收标准：**

- 合成文件能被对应设备 / 相册识别；
- 与 legacy 输出在可观测字段上一致；
- HDR 不丢失；
- 失败时不会产出半损坏文件。

---

### 阶段 8：最终校验与原子输出

**目标：**

把校验变成强制门禁，而不是“尽力而为”。

**要做：**

1. 独立 reader；
2. 结构校验；
3. 协议标记校验；
4. 媒体解码校验；
5. HDR / EXIF / 封面时间校验；
6. 历史记录校验；
7. 未知字节对比；
8. 原子替换。

**验收标准：**

- 任何校验失败都能拒绝输出；
- 原文件不受影响；
- 错误信息可定位到具体阶段。

---

### 阶段 9：接入 GUI / CLI，启用开发期开关

**目标：**

让新引擎真正进入应用，但默认仍安全。

**要做：**

1. 创建 `ILivePhotoEngine`；
2. `LegacyEngine` 包装旧服务；
3. `NativeEngine` 包装 native DLL；
4. 默认 `Legacy`；
5. CLI 增加 `--engine`；
6. native 不支持时回退。

**验收标准：**

- 旧功能默认不受影响；
- `--engine native` 可测试；
- 不支持组合自动回退；
- 不再有 ViewModel 直接 `Process.Start` 新引擎相关命令。

---

### 阶段 10：全面切换与删除旧工具链

**目标：**

把 native 变成默认，删除旧外部工具和旧代码。

**要做：**

1. native 通过全量语料测试；
2. 默认改为 `Native`；
3. 删除：

```text
exiftool.exe
exiftool_files/
ffmpeg.exe
ffprobe.exe
heif-enc.exe
heif-dec.exe
jpegtran.exe
```

4. 删除 legacy 调用点；
5. 更新文档和发布流程。

**验收标准：**

- 不依赖外部工具；
- 测试、构建、打包全通过；
- 项目总览同步更新；
- 发布包体积合理。

## 9. 关键决策

| 决策 | 结论 |
|---|---|
| 全部 C++ 还是混合 | 混合：C# 流程 + C++ native engine |
| 是否长期双引擎 | 否，只保留开发期开关 |
| C++/CLI 还是 C ABI | C ABI + P/Invoke |
| 是否先支持 x86/ARM64 | 否，先 x64 |
| 是否继续用 ExifTool | 否，最终删除 |
| 是否直接用完整 FFmpeg/libheif | 否，沿用最小化定制编译思路 |
| 是否原样保留未知字节 | 是，这是最高原则 |

---

## 10. 风险

| 风险 | 应对 |
|---|---|
| native 输出与 legacy 不一致 | 黄金样本对比 + 阶段门禁 |
| HDR 在转码中丢失 | 默认无损，转码单独路径 |
| 私有协议没有公开文档 | 以现有字节级代码和真实样本为准 |
| C++ 项目与 C# 构建耦合 | 独立目录 + 独立构建 + P/Invoke |
| native DLL 体积变大 | 沿用最小化编译、静态链接、strip |
| GUI/CLI 直接调用点难清理 | 先做 Engine Facade，逐步替换 |
| x86/ARM64 不兼容 | x64 先做，其他自动回退 legacy |

---

## 11. 立即开始的第一批任务

任何接手者第一轮只需要做：

1. 确认当前分支和稳定备份；
2. 阅读 `项目总览.md`、协议报告、本文档；
3. 跑一次完整构建和测试；
4. 建立测试语料清单；
5. 创建 `native/lpb-media-core/`；
6. 写最小 C ABI；
7. 写最小 C# P/Invoke smoke test；
8. 不修改 `designs/` 原始样本；
9. 不在旧 Core 里直接加 `if (native)` 散逻辑。

---

## 12. 禁止事项

- 禁止删除旧实现，直到新引擎通过对应阶段验收；
- 禁止原地修改 `designs/` 样本；
- 禁止在新 native 代码中调用 ExifTool / ffmpeg CLI；
- 禁止把新 C++ 源码混入现有 GUI/Core 目录；
- 禁止在多个服务里各自维护协议/格式矩阵；
- 禁止让 C++ 和 C# 同时写同一个 XMP；
- 禁止在没有校验的情况下覆盖用户文件。
