# Live Photo Box 发布流程

## 一句话流程

```
改代码 → 写更新日志 → 提交 → 打标签 → 推送 → 去 GitHub 点发布
```

---

## 详细步骤

### 第一步：准备发布

```bash
cd "D:\Projects\live-photo-box"
```

更新版本号（如果版本变了）：

| 文件 | 位置 |
|------|------|
| `Package.appxmanifest` | `<Identity Version="1.14.11.0" />` |
| `Live Photo Box.csproj` | `<Version>1.14.11.0</Version>` 和 `<FileVersion>1.14.11.0</FileVersion>` |

> 版本号格式：`主版本.次版本.修订.0`（4 段）
> 标签和文件名会自动去掉末尾的 `.0`，显示为 `v1.14.11`

### 第二步：写更新日志

每次发版需要更新两个文件：

#### 1. `changelogs/release-vX.X.X.md`（发布说明）

在 `changelogs/` 目录下新建文件，**直接用正式文件名**，不用写草稿：

```
changelogs/release-v2.0.1.md    ← 发布说明（直接写正式名，提交推送即可）
```

> ⚠️ 文件名中的 `v` 不可省略，必须与 Git 标签一致。Workflow 通过 `release-v{版本号}.md` 匹配此文件作为 Release 正文。没有草稿/改名流程，写完这个文件直接提交、打标签、推送即可。

#### 2. `changelogs/CHANGELOG.zh-CN.md` + `CHANGELOG.md`（版本历史汇总）

在文件顶部版本号改成新版本，然后在当前大版本段落下加一行。格式参照已有的 v1.14.x 写法：

```markdown
> **v2.0.1** (2026-07-21) **[性能]** 编辑页面性能大幅提升 — 点击文件即时响应、快速切换不再闪退、HEIC 缩略图加载提速、时间线显存骤降；刷新/清空按钮自动切换
```

- 一个版本**一行**，分号分隔不同模块
- 标签用 `**[性能]**` `**[修复]**` `**[新增]**` `**[重构]**` `**[发布]**` 等
- 几十个字讲完，不要展开技术细节
- 中英文各更新一份

发布说明单独看可能合理，但 CHANGELOG 是日后所有版本的汇总——写长了没人翻得动。

更新日志按以下格式填写。

### 章节顺序（三明治结构）

```
## ⚠️ 缺陷警告（仅严重缺陷需要，可选）
## ✨ 新增功能 / New Features
## ⚡ 优化 / Optimizations（可选）
## 🐛 修复 / Bug Fixes（可选）
---
## 📥 下载 / Download
```

> ⚡ 和 🐛 可以省略其中一个，但不能互换顺序。如果既有优化又有修复，优化在前修复在后。

### 每条的写法

每条功能/修复都是**中英双语**结构，中文描述功能，`>` 英文翻译一行：

```markdown
- **🖼️ 功能标题** — 一句话中文说明，讲清楚做了什么
  > English description: one sentence explaining the feature.

- **🔗 另一个功能** — 功能说明
  > Another feature description in English.
```

注意事项：
- **每条必须有 Emoji**，从下方参考表选取最匹配的
- 中文放外面，`> 英文` 缩进在下一行
- 英文行首字母大写，句末加句点，**长度和风格与中文一致**——中文写多长英文就多长，不要中文简洁英文啰嗦
- 每条之间用一个空行分隔
- **标题只说结果，不写技术实现**：说"资源浏览重新设计 — 更加紧凑，统计信息更加详细"，不说"把 ComboBox 换成 Button，把 Grid 改成 StackPanel"
- **同类小改动合并到一条**：如果一条能说清楚就不要拆成三条。开头放最重要的改动，末尾用 **"其他细节优化"** 把零碎小修整合到一起，如 `选项卡根据文件类型自动切换默认视图；修复 150% DPI 缩放下白边；默认排序改为按日期`

### 写作原则

> ⚠️ 更新日志是给普通用户看的，不是开发者文档。

- **站在用户角度描述**：说"修复了切换语言后界面没反应"，不说"修复了 PrimaryLanguageOverride 在非打包下抛 InvalidOperationException"
- **简短**：一句话讲清楚即可，不要展开技术细节。内容不是越多越好，用户只关心核心变化
- **说人话**：用户只关心"什么东西变了"，不关心底层原因。**描述用户能感知到的结果**（"更加紧凑"），**不描述代码怎么改的**（"把 ComboBox 换成了 Button"）
- **轻重分明**：重要的改动单独列一条，放在前面；细碎的修补合并成"其他细节优化"放在末尾，一行带过
- **只对比上一个正式版**：更新日志是 v2.0.1 vs v2.0.0，不是 v2.0.1 开发过程中的所有试错记录。开发中途改坏又修回来的东西，上个版本根本没这问题，不需要写
- **没有就没有**：没修 bug 就不要硬写 🐛 章节；没新功能就不要硬写 ✨ 章节。一条能说清楚的事不要拆成三条

### Download 区块（固定格式）

```markdown
## 📥 下载 / Download

**x64** 架构（Windows 11 / 10 64 位）

### 📦 便携版 / Portable
[⬇️ **Live-Photo-Box-v{版本号}-x64-portable.zip**](https://github.com/LengxiQwQ/live-photo-box/releases/download/v{版本号}/Live-Photo-Box-v{版本号}-x64-portable.zip)

### ⚙️ 安装版 / Installer
[⬇️ **Live-Photo-Box-v{版本号}-x64-setup.exe**](https://github.com/LengxiQwQ/live-photo-box/releases/download/v{版本号}/Live-Photo-Box-v{版本号}-x64-setup.exe)

> 🐛 反馈问题 → [Issues](https://github.com/lengxiqwq/live-photo-box/issues)  
> ⭐ 如果喜欢这个项目，欢迎点个 Star！
```

下载链接中的 `{版本号}` 替换为 3 段版本号（不含末尾 .0），如 `v2.0.0`。

这个文件的内容会自动成为 GitHub Release 页面正文。

### 第三步：提交代码

```bash
git add .
git commit -m "Version 1.14.11 Released"
```

> 提交信息写 `Version x.x.x Released`，便于查看历史。版本号以 Git 标签为准，提交信息中的版本号仅作标识，不参与自动构建触发。

### 第四步：打标签并推送

```bash
git tag v1.14.11
git push --tags
```

---

## 推送后 GitHub 自动做的事

```
你推送标签 v1.14.11
       ↓
① 拉取代码
② 安装 .NET 9 SDK
③ dotnet publish 编译（Release x64 自包含）
④ 打包便携版 → Live-Photo-Box-v1.14.11-x64-portable.zip
⑤ 安装 Inno Setup
⑥ 打安装包 → Live-Photo-Box-v1.14.11-x64-setup.exe
⑦ 创建 GitHub Release（草稿状态）
⑧ 把 zip 和 exe 上传到 Release 附件
⑨ 从 changelogs/release-v1.14.11.md 读取发布说明
       ↓
```

全程不需要你手动操作任何东西。

---

### 第五步：检查并发布

1. 打开 https://github.com/LengxiQwQ/live-photo-box/releases
2. 会看到一个 **Draft**（草稿）状态的 Release
3. 点进去检查：
   - ✅ 标题是否正确
   - ✅ 发布说明是否完整
   - ✅ zip 和 exe 是否已上传
   - ✅ 想加东西可以直接编辑
4. 确认无误 → 点击 **Publish release**

发布后的 Release 会出现在首页，用户就能看到了。

## 示例：一次完整的发版

```bash
# 假设从 v1.14.10 发到 v1.14.11

cd "D:\Projects\live-photo-box"

# 1. 改版本号
#    编辑 Package.appxmanifest 和 LivePhotoBox.csproj

# 2. 写更新日志
echo "..." > changelogs/release-v1.14.11.md

# 3. 提交 + 标签 + 推送
git add .
git commit -m "Version 1.14.11 Released"
git tag v1.14.11
git push --tags
# ↑ 到这步就可以关电脑了，GitHub 会搞定剩下的

# 4. 去 GitHub 点发布
#    浏览器打开 https://github.com/LengxiQwQ/live-photo-box/releases
```

## 本地打包（可选）

不需要每次都在本地打包，GitHub 会自动做。但如果想在本地测试：

```powershell
# 用 PowerShell 运行
.\scripts\build-release.ps1
```

产物在 `publish/` 目录下。
注意本地打包需要安装 Inno Setup（`C:\Program Files (x86)\Inno Setup 6\ISCC.exe`）。

## 常见问题

**Q: Actions 构建失败了怎么办？**
A: 去 https://github.com/LengxiQwQ/live-photo-box/actions 点开失败的记录，看是哪个步骤红了，点进去看日志排查。

**Q: 草稿 Release 可以编辑吗？**
A: 可以。在发布之前可以随意修改标题、正文、甚至替换附件。

**Q: 打错标签了怎么办？**
A: 
```bash
git tag -d v1.14.11              # 删除本地标签
git push origin :refs/tags/v1.14.11  # 删除远程标签
```

**Q: 支持哪些架构？**
A: 目前仅 x64。如需 x86 / ARM64 需在 workflow 中添加对应的编译步骤。
