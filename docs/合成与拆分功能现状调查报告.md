## 1. 执行摘要与总体结论

经对整个解决方案的源代码（C# Core/GUI/CLI + C++ Native）及实际运行行为的完整穿透追踪，核心结论如下：

1. **拆分（Split）现状：单向“提取去协议”已完整接通，但“导出为手机双文件”完全不可用**
   - **已完整接通**：将单文件实况照片（Google V1/V2、小米、OPPO、vivo X300+新格式、三星、华为/荣耀）拆分为**无协议的中性图片与视频**（`protocol: none`，支持保留原样、JPG+MOV、HEIC+MOV、JPG+MP4 转换）。
   - **完全不可用/虚假接口**：GUI 下拉框与 CLI 参数中的“Apple 实况照片”与“vivo 实况照片”拆分目标，运行时直接抛出 `NotSupportedException` 或报错退出（底层写入器为 Stub，Native 未实现）。
   - **限制**：拆分**不接受双文件作为输入**（Apple 双文件与 vivo 旧双文件无法通过拖拽或扫描进入拆分）。

2. **合成（Merge）现状：单组单配对已完整接通，但批量按文件名配对彻底瘫痪**
   - **已完整接通**：单组（单个图片 + 单个视频）合成为单文件实况照片（支持 Google V1、Google V2、OPPO、vivo X300+ 新格式、三星、华为/荣耀 6 种协议目标及多种容器格式），已完整接通中性媒体提取、转码/重封装、Native 目标封装与事务发布校验。
   - **彻底瘫痪的核心故障**：**批量合成无法按文件名配对普通图片和视频**。无论 GUI 选择“按文件名匹配”还是 CLI 默认 `--pairing name`，扫描层均强制要求两文件必须已具备 Apple ContentIdentifier 或 vivo 相机私有 ID。普通拍摄的一组同名 `photo.jpg` 与 `photo.mp4` 扫描后配对数为 0，批量合成直接报“未找到配对”结束。
   - **缺失目标**：合成目标中**完全没有 Apple 实况照片**（Apple 双文件不可作为合成目标）。

3. **vivo 新旧格式断层与 Apple 协议定位混乱**
   - vivo 新格式（X300+ 单文件，UserComment + XMP）已作为合成目标接入（协议 4）；vivo 旧格式（≤X200 双文件，私有 JSON + `cameralbum!` + MP4 uuid box）仅能作为输入被解析，**无写入能力**（写入器为抛异常 Stub）。
   - Apple 双文件在产品设计中被孤立为“拆分目标（未完成）”，在合成中被拒绝作为目标协议；但 Apple 双文件实际上既是输入源也是许多用户期望输出的目标格式。

## 4. 各品牌/协议作为输入、拆分来源与合成目标的能力与限制

下表总结了现有代码中对各协议的真实支持边界（严格区分**输入/拆分来源**与**合成目标**）：

| 协议 / 设备格式 | 物理形态 | 作为输入 / 拆分来源的能力与限制 | 作为合成目标的能力与限制 | 手机实机兼容风险与现状 |
|---|---|---|---|---|
| **Apple Live Photo** | 双文件 (`.HEIC/.JPG` + `.MOV`) | **仅能作为 Merge 输入**。通过 MakerNote Tag 0x927C 中的 ContentIdentifier UUID 与 MOV meta 轨配对；**不可作为 Split 来源**（Split 拒绝双文件）。 | **完全不可用**。底层写入器全为抛异常 Stub，Native TargetWriter 拒绝 `LPB_TARGET_APPLE`。 | 无法生成可导入 iPhone 相册的双文件。 |
| **vivo 新格式 (≥X300)** | 单文件 (`.jpg`) | **完全支持**。Native 识别其 XMP 与 UserComment，切分 Primary JPEG、GainMap 及 MP4，可正常拆分为中性文件。 | **代码已实现并接通**。写入 UserComment（`multi-frame: 1;\nispap:1;\nmodule: photo;`）及 XMP Directory。支持 JPEG+MP4。 | 电脑端校验通过。但官方文档明确记载：尚未取得实机匹配验证，缺少纯 SDR 真实样本证据，手机相册兼容处于“In testing”。 |
| **vivo 旧格式 (≤X200)** | 双文件 (`.jpg` + `.mp4`) | **仅能作为 Merge 输入**。通过图片尾部 JSON 及 MP4 `uuid(vivoMediaExtInfo)` 中的 `com.android.camera.livephoto` 配对；**不可作为 Split 来源**。 | **完全不可用**。`VivoDualFileMetadataWriter` 为抛异常 Stub，Native 拒绝 `LPB_TARGET_VIVO_LEGACY`。 | 无法将其他实况照片导出为老款 vivo 手机兼容的双文件。 |
| **OPPO O-Live Photo** | 单文件 (`.jpg`) | **完全支持**。Native 识别 UserComment（`oplus_10485792`）及 Google 风格 XMP，可完整拆分。 | **代码已实现并接通**。写入 UserComment 及 XMP 目录结构，支持 JPEG+MP4。仅支持单捕获时间戳。 | 电脑端结构校验通过。但实机 ColorOS 需依赖特定的时间戳和 UserComment 字节对齐，尚未完成所有设备闭环。 |
| **小米 / Google V2** | 单文件 (`.jpg` / `.heic`) | **完全支持**。通过标准 XMP Container Directory 规范切分，支持含有 GainMap 的多段结构拆分。 | **代码成熟且最稳定**。支持 JPEG+MP4、JPEG+MOV、HEIC+MOV。规范公开度最高。 | Google Photos 及小米相册实机兼容度最高。 |
| **Google MicroVideo V1** | 单文件 (`.jpg`) | **完全支持**。通过 `GCamera:MicroVideoOffset` 读取并剥离追加视频。 | **代码已接通**。支持 JPEG+MP4、JPEG+MOV。 | 老旧机型规范，新机型通常回退或支持 V2。 |
| **三星 Motion Photo** | 单文件 (`.jpg` / `.heic`) | **完全支持**。Native 能够精准解析 SEFH/SEFT 尾部索引及 0x0A30 标签，完整剥离视频并清理 SEF。 | **代码已实现**。支持 JPEG+MP4 及 HEIC+MP4，支持显式指定 mpv2 / mpv3 版本及写入 SEF Trailer。 | 电脑结构校验通过。三星相册严格依赖二进制 Trailer 而非 XMP，版本差异（mpv2 vs mpv3）在不同 OneUI 版本上识别敏感，仍处“In testing”。 |
| **华为 / 荣耀 Moving Photo** | 单文件 (`.jpg` / `.heic`) | **完全支持**。Native 识别文件末尾 `LIVE_` 标识及反向视频偏移，支持剥离。 | **代码已实现**。支持 JPEG+MP4、HEIC+MP4 及华为专属的 HEIC+MP4 (HEVC) 原生编码输出。 | 电脑结构校验通过。需实机检验鸿蒙系统图库对新合成照片的时长与播放兼容性。 |

### 缺陷 2：扫描目录遇到非标准/损坏视频抛出未捕获异常导致程序崩溃（稳定性阻塞）

## 7. 底层已有能力与产品实际使用的脱节盘点

在深入 Native 和 Core 的底层代码后，发现以下已被底层实现但未被产品入口充分利用或暴露的能力：

1. **Native 具备完整的图片/视频转码与定向转正能力，但产品层仅在部分格式暴露**
   - Native 的 `video_converter.cpp` 和 `image_converter.cpp` 已经实现了极高水准的视频重编码、旋转矩阵重置、方向转正和格式重封装能力。但在 GUI 和 CLI 的 Split/Merge 页面中，视频参数仅提供了预设模板，高级参数（如转码码率、HDR 降 SDR 选项、关键帧间隔等）完全未开放。
2. **`LivePhotoSplitScanService` 成为完全未被调用的僵尸服务**
   - `LivePhotoBox.Core/Services/LivePhotoSplitScanService.cs` 是一个历史遗留的扫描服务，只检查 `.jpg/.jpeg`，整个工程没有任何类引用它，实际扫描全部走的是 `LivePhotoDiscoveryService`。
3. **Native 支持完整的华为 HEVC 原生 Moving Photo，但界面未做机型适配提示**
   - Native `huawei_target.cpp` 支持原汁原味的 HEVC 视频轨合并，这在华为 Mate 60/70/80 系列上是原生规格，但 GUI 界面仅作为普通下拉项展示，缺乏对用户素材编码兼容性的引导。
4. **历史 Stub 文件仍留在正式工程中，造成代码阅读和维护误导**
   - `AppleMakerNoteWriter.cs`、`VivoDualFileMetadataWriter.cs`、`AppleLivePhotoMovBuilderV2.cs`、`AppleLivePhotoMebxWriter.cs` 中保留着数十个仅抛异常的方法。它们的存在给后续开发者造成了“底层有写入器”的假象，实际上生产全量走的是 `StructuredTargetWriterService` + Native 数据面。

## 8. 后续施工顺序规划与技术依据建议

要把合成与拆分功能彻底做完、做到产品级可用，**不能盲目铺开，也不能沿用已被废弃的旧规划**。根据当前代码真实状态与依赖拓扑关系，建议按以下顺序分阶段施工：

### 阶段一：打通普通媒体的同名配对通道（解决合成功能的“燃眉之急”）
- **优先级**：P0（最高，立即执行）
- **目标**：让用户在 GUI 和 CLI 中，无论单对还是批量，只要有同名的 `photo.jpg` + `photo.mp4`，就能立即配对并合成为实况照片。
- **具体工作**：
  1. 在 `LivePhotoMergeScanService.cs` 与 `LivePhotoMetadataMatcher.cs` 中增加真正的**按基础文件名（BaseName）配对逻辑**（将同目录下的支持格式图片与视频按同名聚合）。
  2. 修复 `LivePhotoMetadataMatcher.MatchVivo` 的异常过滤条件，捕获所有非法的视频/图片格式异常，防止坏文件导致扫描崩溃。
  3. 修改 `MergeViewModel.AddFilesToQueueAsync`，移除 `images.Count == 1 && videos.Count == 1` 的苛刻限制，允许多对同名文件一次性拖入队列。
- **依据**：单对合成管线（Native 写入、中性转换、校验发布）在底层已经 100% 具备且验证可用，目前仅仅是因为扫描配对器把普通文件丢弃而导致整个功能瘫痪。修通配对即可立刻盘活现有的全部合成写入能力。

### 阶段二：UI 与 CLI 的接口诚实化与防御性收口（清理误导性入口）
- **优先级**：P1
- **目标**：杜绝“界面看得见、点下就报错”的不诚实行为，对齐 GUI 与 CLI。
- **具体工作**：
  1. 检查并清理 GUI `SplitPage.xaml`：对尚未实现的“Apple 实况照片”与“vivo 实况照片”下拉选项添加 `(暂未支持)` 标记并将其禁用，或临时隐藏，并给出明确提示。
  2. 清理 CLI `lpb merge --help` 中的误导性提示（如提示 Apple Live Photo 是 split 目标等矛盾文案）。
  3. 彻底归档或删除 `LivePhotoSplitScanService.cs` 等未使用的孤立文件。
- **依据**：符合项目规范第 0 节“不虚报通过、不提供假入口”的硬规则，避免用户误解和差评。

### 阶段三：补齐 Apple 双文件实况照片的写入能力（实现完整跨生态互通）
- **优先级**：P2
- **目标**：实现将任何实况照片或普通图片+视频，输出为 iPhone 相册完全可识别的 Apple Live Photo（HEIC/JPG + MOV 双文件）。
- **具体工作**：
  1. 在 Native 数据面或 Core 中实现标准的 Apple 双文件目标写入器（Target 7）：
     - 照片端：写入 ExifIFD Tag 0x927C Apple MakerNote，注入匹配的 `ContentIdentifier` UUID。
     - 视频端：写入 QuickTime 顶级元数据 UUID、创建/修补 Track 4 mebx 封面轨道及 `StillImageTime`。
  2. 将 Apple 双文件同时接入为 **Merge 的目标协议** 与 **Split 的输出格式**。
  3. 编写针对 Apple 双文件的校验器（Validator），确保生成的 MOV 和 HEIC 能够通过 iOS 设备相册的因果识别测试。
- **依据**：Apple Live Photo 是目前移动端使用人数最多、接受度最广的实况照片格式。打通该目标，软件才能真正实现“将安卓实况照片转给 iPhone”或“将普通相机素材制作为 iPhone 实况照片”的核心产品价值。

### 阶段四：拓展拆分功能支持双文件输入（闭环双向流转）
- **优先级**：P3
- **目标**：允许用户将 Apple 双文件（HEIC+MOV）或 vivo 旧双文件拖入 Split 页面，一键去除私有协议标记、转码或解耦为普通媒体。
- **具体工作**：
  1. 改造 `LivePhotoSplitService`，允许接收 `secondaryPath`。
  2. 改造 GUI `SplitViewModel` 与 CLI `SplitCommand`，接入对 `DualFile` 类型的发现与解析。
  3. 复用已有完善的 `SourceExtractor` 和 `SourceProtocolCleaner` 进行双文件去协议清洗。
- **依据**：底层 Inspector 和 Cleaner 早就具备双文件解析清洗能力，此前仅仅是 Split 入口层人工加了一道“仅限单文件”的过滤锁。解除后即可实现双文件拆分。

### 阶段五：各品牌真实手机相册的兼容性收口验证（实机闭环）
- **优先级**：P4
- **目标**：在各品牌真实设备上进行 A 级（显示、播放、声音、方向、封面）实机验收。
- **具体工作**：
  1. 小米 / Google 目标实机导入与连续滑动验证。
  2. OPPO / 一加 ColorOS 实机导入与实况播放、封面拖拽验证。
  3. vivo X300+ 新一代相册对新 UserComment 格式的实机验证。
  4. 三星 S23/S24 OneUI 相册对 SEF mpv2/mpv3 格式的识别与播放测试。
  5. 华为鸿蒙相册对原生 HEVC MOVING PHOTO 的实机验证。
- **依据**：电脑端结构校验通过（XMP 合法、box 结构正确）绝不等于手机图库因果识别通过。真实手机系统有闭源的私有白名单机制，必须通过真机实测完成最终验收。
