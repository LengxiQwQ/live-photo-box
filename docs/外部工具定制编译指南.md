## 1. FFmpeg 功能清单

> 将 gyan.dev full_build 从 **97 MB** 瘦身至 **5.8 MB**（缩减 94%），精确保留项目实际所需的全部功能。

**版本号**: n9.0.1
**编译时间**: 2026-08-28

以下按 C# 服务文件逐一列出每个 ffmpeg 参数及其对应的编译组件。

### 1.1 ThumbnailService.cs — 视频缩略图提取

**文件**: `LivePhotoBox/Services/ThumbnailService.cs`

```bash
ffmpeg [-hwaccel cuda|qsv|d3d11va|vaapi] -i "{video}" -vframes 1 \
  -vf "scale=80:-1:force_original_aspect_ratio=decrease" \
  -q:v 2 "{thumb.jpg}" -y -loglevel error
```

| 参数 | 功能 | 编译要求 |
|------|------|---------|
| `-hwaccel cuda/qsv/d3d11va/vaapi` | GPU 硬件解码加速 | 对应 hwaccel |
| `scale=...` | 缩放到 80px 宽 | `--enable-filter=scale` |
| `-q:v 2` | JPEG 质量参数 | `--enable-encoder=mjpeg` |
| `.jpg` 输出 | 输出为 JPEG | `--enable-muxer=image2` |

### 1.2 VideoTranscodeService.cs — 视频转码 & Remux

**文件**: `LivePhotoBox.Core/Services/VideoTranscodeService.cs`

#### Remux 模式（流拷贝）

```bash
ffmpeg -y -i "{input}" -c copy -map 0:V:0 -map 0:a:0? \
  -map_metadata 0 [-movflags +faststart] "{output}"
```

#### 转码模式

```bash
ffmpeg -apply_cropping 0 -y -i "{input}" \
  -map 0:V:0 -map 0:a:0? -map_metadata 0 \
  -threads {N} -vf "{filter}" -pix_fmt yuv420p \
  -c:v {encoder} {params} {audio_args} \
  -movflags +faststart "{output}"
```

> **FFmpeg 9 NVENC 注意**：项目使用 `h264_nvenc`/`hevc_nvenc` 时传递 `-rc:v vbr`。
> 旧版 FFmpeg/SDK 中曾使用的 `vbr_hq` 是已弃用的别名，在当前 FFmpeg 9 定制构建中可能被禁用，
> 会导致 `Unable to parse "rc" option value "vbr_hq"`。质量由 `-cq:v`、`-b:v 0`、`-maxrate`、`-bufsize`
> 与 `-preset p5` 共同控制。

**项目支持的 8 种视频编码器**：

| 编码器 | 类型 | 编译要求 |
|--------|------|---------|
| `libx264` | CPU H.264 | `--enable-libx264` |
| `libx265` | CPU HEVC | `--enable-libx265` |
| `h264_amf` / `hevc_amf` | AMD GPU | `--enable-amf` |
| `h264_nvenc` / `hevc_nvenc` | NVIDIA GPU | `--enable-nvenc` + ffnvcodec |
| `h264_qsv` / `hevc_qsv` | Intel GPU | `--enable-libvpl` |

### 1.3 LivePhotoRepairService.cs — 视频修复

**文件**: `LivePhotoBox.Core/Services/LivePhotoRepairService.cs`

```bash
ffmpeg -apply_cropping 0 -y -i "{source}" \
```

### 1.5 EditViewModel.cs — GIF 动图导出

**文件**: `LivePhotoBox/ViewModels/EditViewModel.cs` + `LivePhotoBox.Core/Services/VideoTranscodeService.cs`

```bash
ffmpeg -y -i "{video}" \
  -vf "fps={fps},scale={w}:{h}:flags=lanczos,split[a][b];[a]palettegen=max_colors=256:stats_mode=diff[p];[b][p]paletteuse=dither=bayer:bayer_scale=5" \
  -loop {loop} "{output.gif}"
```

| 参数 | 功能 | 编译要求 |
|------|------|---------|
| `fps={n}` | 控制输出帧率 | `--enable-filter=fps`（已有） |
| `scale=w:h:flags=lanczos` | Lanczos 缩放到指定尺寸 | `--enable-filter=scale`（已有） |
| `split[a][b]` | 分流为两个输出 | `--enable-filter=split`（**新增**） |
| `palettegen=max_colors=256:stats_mode=diff` | 基于帧间差异生成最优 256 色 GIF 调色板 | `--enable-filter=palettegen`（**新增**） |
| `paletteuse=dither=bayer:bayer_scale=5` | Bayer 有序抖动应用调色板 | `--enable-filter=paletteuse`（**新增**） |
| `-loop {n}` | 循环次数（0=无限） | `--enable-muxer=gif`（**新增**） |
| `.gif` 输出 | GIF 编码 + 容器写入 | `--enable-encoder=gif` + `--enable-muxer=gif`（**新增**） |

> **设计说明**: 滤镜顺序刻意设为 scale 在 fps 之前——先缩小像素再降帧率，减少中间帧的内存占用。
> palettegen 的 `stats_mode=diff` 只分析帧间变化区域的色彩分布，避免静态背景浪费调色板条目。
> paletteuse 的 `dither=bayer` 采用 Bayer 有序抖动（非 Floyd-Steinberg 误差扩散），消除 GIF 帧间闪烁。

以下命令在 **MINGW64** shell 中执行。

### 2.1 安装 FFmpeg 编译依赖

```bash
pacman -S --needed --noconfirm \

    mingw-w64-x86_64-x265 \
```

| 包名 | 用途 |
|------|------|

| `mingw-w64-x86_64-x265` | HEVC 编码库（含头文件和静态库） |

| `mingw-w64-x86_64-ffnvcodec-headers` | NVIDIA NVENC SDK 头文件 |

### 2.2 克隆 & 编译

```bash
cd /c/Users/LengxiQwQ/Downloads
git clone --depth 1 --branch n9.0.1 https://git.ffmpeg.org/ffmpeg.git ffmpeg-src
cd ffmpeg-src

./configure \
    --prefix=/c/Users/LengxiQwQ/Downloads/ffmpeg-out \
    --target-os=mingw32 \
    --arch=x86_64 \
    --enable-gpl \
    --enable-version3 \
    --enable-static \
    --disable-shared \
    --disable-debug \
    --disable-doc \
    --enable-stripping \
    --enable-ffmpeg \
    --disable-ffplay \
    --disable-ffprobe \
    --disable-avdevice \
    --disable-network \
    --disable-everything \
    --enable-libx264 \
    --enable-libx265 \
    --enable-amf \
    --enable-libvpl \
    --enable-nvenc \
    --enable-d3d11va \
    --enable-dxva2 \
    --enable-pthreads \
    --disable-w32threads \
    --pkg-config-flags="--static" \
    --extra-libs="-lstdc++" \
    --enable-encoder=libx264,libx265,aac,mjpeg,gif \
    --enable-encoder=h264_amf,hevc_amf,h264_nvenc,hevc_nvenc,h264_qsv,hevc_qsv \
    --enable-decoder=h264,hevc,mjpeg,mpeg1video,mpeg2video,mpeg4 \
    --enable-decoder=aac,mp3,mp2,pcm_s16le,pcm_s24le,pcm_f32le,pcm_s16be \
    --enable-muxer=mp4,mov,mp3,image2,null,mjpeg,gif \
    --enable-demuxer=mov,mp4,mpegts,matroska,avi,image2,aac,mp3,wav,mjpeg \
    --enable-parser=h264,hevc,mpegaudio,aac,mjpeg,mpeg4video,mpegvideo \
    --enable-bsf=h264_mp4toannexb,hevc_mp4toannexb,aac_adtstoasc,extract_extradata,filter_units \
    --enable-filter=scale,transpose,hflip,vflip,crop,null,anull,format,setsar,fps,setpts,settb \
    --enable-filter=trim,atrim,aformat,aresample,pad,buffer,buffersink,palettegen,paletteuse,split \
    --enable-protocol=file,pipe \
    --enable-hwaccel=h264_d3d11va,h264_dxva2,hevc_d3d11va,hevc_dxva2 \
    --extra-cflags="-O2" \
    --extra-ldflags="-s -static -static-libgcc -static-libstdc++"

    # 关键步骤：移除 ffmpeg configure 多余加入的 -lgcc_s。MinGW 的 libgcc_s.a
    # 实际上是 DLL 导入桩，强行链接会导致 ffmpeg.exe 依赖 libgcc_s_seh-1.dll。
    # -static-libgcc 已让 GCC 内部使用 libgcc.a + libgcc_eh.a，
    # 所以 EXTRALIBS 里的 -lgcc_s 是多余且有害的，必须移除。
    sed -i 's/-lgcc_s//g' ffbuild/config.mak

make -j20
```

**Configure 核心参数说明**：

| 参数 | 说明 |
|------|------|
| `--disable-everything` | 先关闭一切，再精确启用所需组件 |
| `--enable-static --disable-shared` | 静态链接，产出单文件 exe |
| `--pkg-config-flags="--static"` | pkg-config 返回静态库链接参数 |
| `--extra-libs="-lstdc++"` | 链接 C++ 标准库（libvpl 需要） |
| `--extra-ldflags="-s -static -static-libgcc -static-libstdc++"` | 链接时 strip + 完全静态链接（包括 GCC 运行时） |
| `sed -i 's/-lgcc_s//g' ffbuild/config.mak` | **关键**：移除 configure 误加的 `-lgcc_s` 动态导入桩引用 |

## 3. FFmpeg 故障排查

### libvpl 检测失败

```
ERROR: libvpl >= 2.6 not found
```

原因：libvpl 是 C++ 库，configure 测试链接时缺少 C++ 标准库。
解决：添加 `--extra-libs="-lstdc++"` 到 configure 命令。

### x264 检测失败

```
ERROR: x264 not found using pkg-config
```

原因：配置静态链接时 pkg-config 默认返回动态库参数。
解决：添加 `--pkg-config-flags="--static"`。


### ffmpeg.exe 依赖 libgcc_s_seh-1.dll（STATUS_DLL_NOT_FOUND / 0xC0000135）

```
错误码: -1073741515 (0xC0000135 = STATUS_DLL_NOT_FOUND)
```

**症状**：ffmpeg.exe 在命令行（Git Bash、Cmd）中可以正常运行，但被 C# 程序
通过 Process.Start 调用时启动失败，程序报告 "错误编码 -1073741515"。
硬件检测页面显示 "FFmpeg — 不可用"、"版本: 未知"、"错误: Exit code: -1073741515"。

**原因**：MinGW GCC 16.1.0 的 `libgcc_s.a` 是一个 **DLL 导入桩**（仅 80 KB），
不是真正的静态库。即便 configure 加了 `--extra-ldflags="-static"`，
ffmpeg 的 configure 脚本仍然在 `EXTRALIBS-avcodec` 中加入了 `-lgcc_s`，
导致链接器找到导入桩，使 ffmpeg.exe 在运行时需要 `libgcc_s_seh-1.dll`。
同样 `libwinpthread-1.dll` 也会出现同样问题。
Git Bash 中能运行是因为 `/mingw64/bin/` 在 PATH 中带有这两个 DLL，
而普通 Windows 进程没有。

**解决方案**（二选一）：

**方案 A：在 configure 后移除 -lgcc_s（推荐）**

在 `./configure` 之后、`make` 之前执行：
```bash
sed -i 's/-lgcc_s//g' ffbuild/config.mak
```
同时 `--extra-ldflags` 必须包含 `-static-libgcc -static-libstdc++`：
```bash
--extra-ldflags="-s -static -static-libgcc -static-libstdc++"
```
这样 GCC 内部会使用 `libgcc.a` + `libgcc_eh.a`（真正的静态代码，3 MB），
不需要外部的 `libgcc_s_seh-1.dll`。

**方案 B：把运行时 DLL 放到 Tools 目录（不推荐）**
将 `libgcc_s_seh-1.dll` 和 `libwinpthread-1.dll` 复制到 ffmpeg.exe 旁边：
```bash
cp /mingw64/bin/libgcc_s_seh-1.dll /path/to/Tools/
cp /mingw64/bin/libwinpthread-1.dll /path/to/Tools/
```
缺点：每次编译都要带这两个 DLL，且 C# 项目中的 MSIX 打包可能会报 DEP1000 错误。

**验证方法**：
```bash
# 应该只有 Windows 系统 DLL，没有 /mingw64/bin/ 下的文件
objdump -p ffmpeg.exe | grep "DLL Name"
# 预期输出：
#   DLL Name: ADVAPI32.dll
#   DLL Name: bcrypt.dll
#   DLL Name: KERNEL32.dll
#   DLL Name: msvcrt.dll
#   DLL Name: ole32.dll
#   DLL Name: SHELL32.dll
#   DLL Name: USER32.dll
```

### 编译产物过大

- 检查 configure 输出中的 `External libraries` 列表
- 确保 `--disable-everything` 后没有连带多余组件
- UPX 压缩是最后的瘦身手段

### C# 项目 MSIX 打包报 DEP1000（文件找不到）

```
错误 DEP1000: 无法将文件 "...\\Tools\\xxx.dll" 复制到布局
```

**症状**：删除 Tools 目录中的某些文件后（如旧的备份 exe 或运行时 DLL），
重新编译 C# 项目时提示不能复制已不存在的文件。

**原因**：MSBuild 会将 `Content Include="Tools\**\*"` 匹配到的文件列表
缓存到 `obj` 目录中。文件从磁盘删除后，缓存仍然引用它，
导致 MSIX 打包阶段找不到该文件而报错。

**解决**：清除 MSBuild 缓存，让项目重新扫描 Tools 目录：
```bash
# 删除 obj 和 bin 目录（编译时会自动重建）
rm -rf "LivePhotoBox/obj" "LivePhotoBox/bin"
```

> **预防措施**：在 csproj 的 Content Include 中加入 `Exclude` 属性，
> 让备份文件等临时文件不进入 MSIX 追踪列表：
> ```xml
> <Content Include="Tools\**\*" Exclude="Tools\**\*backup*;**\*backup*\**\*;Tools\**\*.bak;Tools\**\*.tmp;Tools\**\*.old" />
> ```

### 4.2 heif-enc.exe — JPEG/PNG(8/16-bit) → HEIC 编码器

支持的输入格式：JPEG + PNG（8/16-bit；16-bit PNG 是 10-bit HDR 输入的入口）
支持的编码器：仅 x265（HEVC）

```bash
# 基本用法
heif-enc -q 90 -o output.heic input.jpg

# 10-bit HDR 编码（16-bit PNG 输入，nclx 显式指定，H.273 数值见文档正文）
heif-enc -b 10 -q 90 \
  --colour_primaries 9 --transfer_characteristic 18 --matrix_coefficients 9 \
  --full_range_flag 0 --clli 900,203 --enable-two-colr-boxes \
  -o output.heic input16.png

# 完整参数参考（本编译 = libheif 1.23.1 官方 heif-enc，仅启用 HEVC 编码器）
```

**输出 & 质量**

| 参数 | 说明 |
|------|------|

## 5. libheif 编译流程

### 5.1 设计原则

MSYS2 预编译的 `mingw-w64-x86_64-libheif` 包虽然提供了 `heif-enc.exe` / `heif-dec.exe`，但硬链接了全部编解码器（AV1 ×4、VVC ×2、JPEG2000 ×2……），产生 **64 MB 的 DLL 依赖**（33 个文件）。

本编译方案采用以下策略实现最小化：

1. **仅启用 HEVC**：x265 编码 + libde265 解码，禁用所有其他编解码器
2. **仅保留 JPEG + PNG 图像 I/O**：heif-enc 读 JPEG/PNG，heif-dec 写 JPEG/PNG（PNG 8/16-bit，是 10-bit HDR 中间格式的唯一入口）
3. **全静态链接**：x265、libde265、libjpeg 全部编译进 .exe
4. **UPX 极限压缩**：27 MB → 3 MB

### 5.2 安装 libheif 编译依赖

```bash

    mingw-w64-x86_64-x265 \
    mingw-w64-x86_64-libde265 \
    mingw-w64-x86_64-libpng \
    mingw-w64-x86_64-zlib
```

> **注意**：`mingw-w64-x86_64-libde265` 需要额外处理。MSYS2 的 libde265 头文件默认标记函数为 `__declspec(dllimport)`，静态链接时必须定义 `LIBDE265_STATIC_BUILD` 宏（见下文 cmake 配置）。

## 6. libheif 故障排查

### libde265 静态链接报 `undefined reference to __imp_de265_*`

原因：MSYS2 的 libde265 头文件默认标记为 `__declspec(dllimport)`，静态链接时产生未定义的导入符号。

解决：在 `CMAKE_C_FLAGS` 和 `CMAKE_CXX_FLAGS` 中加入 `-DLIBDE265_STATIC_BUILD`。

### JPEG 仍然动态链接（`libjpeg-8.dll` 依赖）

原因：cmake 的 FindJPEG 模块默认优先使用 `.dll.a` 导入库，即使 `JPEG_LIBRARY` 指向 `.a` 静态库，`JPEG_LIBRARY_RELEASE` 仍可能被覆盖为 `.dll.a`。

解决：同时设置 `-DJPEG_LIBRARY` 和 `-DJPEG_LIBRARY_RELEASE` 指向同一个 `.a` 文件。

### WebP 自动检测导致 DLL 依赖

原因：libheif 的 cmake 脚本会自动探测系统中已安装的 WebP 库。

解决：强制设置 `-DWEBP_LIBRARY=""`、`-DWEBPMUX_LIBRARY=""`、`-DWebP_FOUND=FALSE` 并将所有 WebP 相关 cmake 变量置空。

### 编译产物过大（>30 MB）

- 检查是否误链入了 libx265 的 10bit/12bit 变体（MSYS2 x265 包默认包含 multi-bit）
- 确认 `-DCMAKE_BUILD_TYPE=Release` 已设置
- `-s` 链接标志是否生效（`strip` 命令再次去除符号做双重保险）
