## 1. 任务目标与授权边界

本计划用于交接给实施 AI：改进合成、拆分、修复及它们依赖的共用媒体链路，使正常媒体差异不再因为无关附带信息或局部能力不足而被整项拒绝；对确实无法处理的文件给出准确单项结果，其他独立任务继续。完成后由用户交回审查者复核。

当前编写计划这一轮只新增本文，不修改产品、测试或当前执行状态。用户随后把执行提示词交给实施 AI 时，授权实施本计划限定范围内的代码、测试、本地验证和必要文档更新；不因仓库旧 TASK 恢复其他工作。

**交付目标：** 共用中性媒体主线保持不变，补齐通用准入、结构化降级、修复动作隔离、批量配对效率和状态表达。以可复现的问题和真实结果收口，不以减少红灯数量或让所有输入返回成功为目标。

### 范围内

- 合成、拆分及修复的扫描、配对、检查、转换、清理、写入、验证与结果展示。
- 这些功能依赖的 Core/Native 共用实现、GUI/CLI 接线与必要定向测试。
- 本文 M1—M6 及同一调用链上直接影响这些目标的共性缺陷。
- 测试所需的本地辅助工具和临时产物；不得悄悄进入产品依赖。

### 范围外

- 尚未重构/接入的实况照片编辑页面、封面编辑等独立功能。
- 新增品牌协议、Fusion、扩大图片/视频编码格式支持、单独的 HDR 大型工程；已有延期事项不自动恢复。
- 新的撤销导出系统、新错误界面、无关界面重构和通篇整理旧代码。
- 提交、推送、打标签、发布、部署、正式发布打包、真机验收。
- 未经用户事先同意的任何桌面自动化。优先脚本、CLI、定向测试；实际界面观察交给用户。

实施中普通工程选择自行完成，不为每个单元重复请求授权。确需改变公共 Contract/ABI、产品依赖、已约定质量策略或安全边界时，先说明具体方案和影响，再由用户决定；可继续不依赖该决定的工作。新发现的无关问题记录后交回，不无限扩大施工。

## 3. 不可放松的产品与媒体边界

- 保持 Source → Neutral → Target。来源协议差异在来源端解决；目标协议差异在目标端解决。中间按真实格式、编码、方向、时间、颜色和目标能力分派，不按型号、路径、文件名或样本 hash 分派。
- A 级基础内容必须正确：主图、完整视频、有效声音与同步、方向/镜像、封面语义、基础颜色、必要协议字段和安全发布。B 级复用已有可靠能力；C 级不扩建保留系统。未知信息不得直接等同损坏，也不能未经分析就当作无用数据删除。
- 严格模式保留明确含义，不通过放松它制造“通过”。默认尽力处理的产品策略与严格模式检查分开。
- 来源身份、配对唯一性、容器边界、越界/溢出、重复或影子结构、清理权限、输出所有权、事务发布与恢复必须继续有效。安全条件不成立时阻止相关动作，不猜配、不覆盖来源、不发布半成品。
- 不允许用任意位置字符串命中当协议依据；不允许让未知元数据取得封面、配对或文件范围的决定权。
- 不把所有异常吞掉后报成功。取消、外部文件问题、软件缺陷、共享环境故障分别处理；内部错误保留诊断。可以保留低层严格 API 的异常，但预期文件差异在产品边界形成正常分类结果。

| 结果 | 含义与行为 |
|---|---|
| 绿色 | 本次承诺的处理已完成且必要检查通过；或确实完成适用检查，确认无需修复。无关私有数据未完整理解本身不强制黄色。 |
| 黄色 | 有安全可用结果，但存在明确未完成动作、不确定性或降级；隔离导出，说明完成了什么、没完成什么和实际路径。不得对黄色项执行成功项的源文件删除/回收操作。 |
| 红色 | 没有安全可用路径，或受影响操作确实无法完成；说明原因，其他独立项继续。不能仅因某个非必要字段陌生就红灯。 |
| 跳过/未执行 | 明确原因，例如范围未选、选项关闭；不等于已验证健康，不计作修复成功。复用现有状态与文字，不另建颜色或界面体系。 |

没有发生修改且仅复制原文件时，必须明确“未修复／原样复制”；不能用复制代替修复完成。配对关系有歧义时，不能借黄色隔离选一个候选；只允许不依赖该歧义且能独立保证正确的动作。

## 4. 工作包与完成条件

### M1：消除目标视频普通元数据的过窄准入

**已确认代码线索：**

- `LivePhotoBox.Native/src/media/target_video_observation.cpp` 的 `inspector::meta`：iTunes 分支只接受少数标签；handler 名称区域出现非零字节就拒绝；未知 meta 子节点也直接拒绝。
- `LivePhotoBox.Native/src/media/target_writer.cpp` 写入前调用该观察器，验证器也依赖它。
- `tests/native/target_video_observation_tests.cpp` 已覆盖一部分未知 mdta/UUID 可保留场景，但这不能证明 iTunes 分支同样通用。

**怎么做：**

1. 构造相同音视频的对照输入，仅改变普通元数据标签、名称或有边界的附带数据。先确认格式合法和生产路径可达，记录拒绝发生在检查、清理还是写入阶段。
2. 按容器结构、字段实际类型、归属和是否承担实况绑定语义判定。普通标签不能靠继续扩充几个名字解决；结构合法的名称也不能仅因为非空就拒绝。
3. 保留必须识别的来源绑定检测和结构安全检查。未知类型是否可作为不解释的数据保留、可安全省略，或必须停止受影响动作，要有明确证据；不是所有未知 meta 子节点都可以盲目放行。
4. 源端清理、目标输入观察和成品验证采用一致语义，避免写入接受而验证拒绝，或仅修改验证器隐藏问题。

**完成条件：**

- 至少覆盖白名单之外的普通标签、合法非空名称、已有未知 mdta/UUID 路径；同一主媒体的合法无关差异不再导致不合理拒绝。
- 覆盖截断、越界、重复/影子身份、来源实况绑定等反例，仍正确阻止危险动作。
- 受影响的正式合成或目标转换 CLI 路径实际产出；独立检查媒体内容和必要目标字段。仅底层观察器单元通过不算完成。

### M2：用结构化能力结果统一降级，而非匹配异常文字

**已确认代码线索：** `LivePhotoBox.Core/Services/LivePhotoRepairService.cs` 的独立视频修复，仅在异常文字包含 `movie/track/media header metadata differs` 时从 Strict 重试 BestEffort；配对视频分支的处理不同。检查 `ProductOperationOutcome`、转换执行记录及现有诊断模型可否复用。

**怎么做：**

1. 追踪这条错误的真实来源，判断是普通元数据无法保留、基础媒体校验失败还是其他原因；不能把所有同类型异常归为可降级。
2. 优先复用现有错误分类、能力结果和执行记录；必要时在内部补足缺失信息。用类别和证据决定替代路线，移除对英文报错文本的控制流依赖。
3. 让图片配对视频、独立视频及 GUI/CLI 对同一语义给出一致决策；不要求安全前提不同的情形盲目得到相同结果。
4. 只能选择已有可靠的转换/重封装路径；确认几何、声音、同步和必需配对/封面正确后，才允许黄色导出。禁止无上限重试或偷偷切回 Legacy。
5. 因某一步产生的中间文件必须按所有权清理；重试不能遗留假成功或半发布结果。

**完成条件：**

- 合法可降级案例不再依赖异常原文；至少两种实际不同的受限条件有准确分类，能处理的处理，不能处理的明确拒绝。
- 配对与独立入口的适用情况有覆盖；无法保留有效声音/方向/必需配对等情况不得伪装成功。
- 黄灯说明实际变化、未保证内容、隔离路径；原件不变，其他独立项继续。

### M3：修复动作独立判断，局部受限不提前否决整项

**已确认代码线索：** `LivePhotoRepairService.RepairImageFileAsync` 在存在 EXIF/码流检查问题时返回失败；需要旋转且有 Extended XMP 时提前返回失败。部分后续失败只有已存在图片修复输出证据时才允许继续，策略未统一。诊断阶段的 Limited 与执行阶段也需核对。

**怎么做：**

1. 为图片方向、缩略图/预览、HEIF 方向、配对/内嵌视频方向列出实际依赖，先判定每个动作的能力与安全条件，再组合执行。使用适度的内部结构，不建设通用工作流平台。
2. 分开“基础媒体损坏”“某段附带信息无法理解”“某个修复动作受限”。不能简单删除 EXIF/码流校验；只对有独立证据的动作继续。
3. Extended XMP 应判断实际是否涉及方向或几何，而不是看到存在就整项失败。未能证明可安全改写时保持该部分不动，评估其他独立动作。
4. 诊断、执行、最后验证使用一致的能力定义。Limited 不应自动吞掉仍可完成的动作；也不能把未能诊断的项目当作健康。
5. 检查 JPEG 完美无损旋转的尺寸限制、XMP 方向冲突和附加媒体布局等相邻风险。无损旋转做不到不等于文件损坏；不允许静默裁切。若既有质量约定允许且已有通用重编码能力，可明确记录重编码并走安全降级；若需改变修复质量约定，则先提交具体选择给用户，不自行引入有损策略。
6. 有部分可用结果时按统一政策隔离导出；无动作可安全完成时如实未完成。不能通过生成未改变副本来凑修复成功。

**完成条件：**

- 覆盖：图片方向受限而另一动作可完成、视频受限而图片动作可完成、全部受限、完全无需修复、基础媒体真实损坏。
- Extended XMP 的无关信息与真实方向冲突分别覆盖；JPEG 尺寸限制有明确结果。
- 所有部分结果说明逐项实际动作；未执行部分仍保有原语义；成品可独立解码，配对关系正确。

### M4：建立批量配对索引，避免逐项重扫全目录

**已确认代码线索：** `InspectRepairSourceAsync`、`RepairImageFileAsync`、`RepairVideoFileAsync` 多处在每个文件处理中遍历同目录并重新检查候选。GUI 已有扫描结果，但服务执行仍可能重做；CLI 的图片与视频入口也会重复查找。

**怎么做：**

1. 测量候选检查调用次数与实际时间，区分初次扫描、配对、执行前身份验证，不能仅凭耗时猜原因。
2. 每批次建立目录/配对 ID 索引，复用已有扫描事实；索引记录候选集合而非先到先得。GUI/CLI 共用服务能力，单文件调用也保持可用。
3. 保持当前目录和递归范围语义，不意外跨目录猜配。重复 ID、缺失伴随文件、改名、大小写、同名不同内容和不同协议不得混淆。
4. 索引只是发现信息，不能代替执行时的对象身份与必要复验。扫描后替换、删除、修改文件必须被检测，不能因缓存绕过安全边界。
5. 使用批次生命周期管理索引，避免全局永久缓存、无界内存和多任务污染；保留取消与逐项故障隔离。

**完成条件：**

- 构造 n 与 2n 的批量目录，记录检查次数；发现/配对不再对每项重扫全部候选，必要的执行前核验可保持逐项。
- 记录实际文件数、大小、缓存条件、耗时和取消响应，不虚构固定性能倍数，也不把理论次数当实测。
- 改名、歧义、缺失、扫描后替换和混合坏文件测试通过；源保护与结果不因优化退化。

### M5：校正跳过、健康、受限、失败和成功的产品表达

**已确认代码线索：**

- `LivePhotoBox.Core/Models/RepairAnalysisResult.cs` 中 NonApple/其他无需修复类型的 `NeedsRepair` 为 false。
- `LivePhotoBox/Models/RepairFileEntry.cs` 的 `DisplayStatus` 将 `!NeedsRepair` 映射为成功。
- `LivePhotoBox/ViewModels/RepairViewModel.cs` 执行结果除 failed/warning 外默认成功；CLI 已分别统计 skipped 等状态，但仍需核查一致性。

**怎么做：**

1. 用明确结果类型或现有状态字段区分健康、修复完成、部分完成、范围外跳过、选项关闭、原样复制、失败、取消；不要继续依赖消息文本推断。
2. 复用现有状态列、详情提示、进度和统计。若无需新增公共枚举即可准确表达，优先最小改动；不为跳过新建整套界面。
3. 同时检查诊断状态、执行后状态、汇总和历史，防止一个层面显示跳过、另一个层面统计成功。
4. 详情包含简明中文原因、实际完成内容和输出路径；日志可保留原始技术诊断，内部错误不伪装成用户文件问题。遵循现有资源本地化方式。
5. 复核源文件后处理仅对真正符合成功和身份条件的项执行，黄灯、失败、未执行不得误触发。

**完成条件：** 各结果类别分别有准确显示与统计映射；未诊断、范围外文件不被认作已验证健康。GUI 接线可做非桌面检查，真实显示和交互列成简短用户检查清单，未经用户验证不写 GUI 已通过。

### M6：扫描同链路剩余过严点，建立结构变化回归

本项是有边界的补漏，不是要求重写全部解析器或扩大支持范围。

**怎么做：**

1. 检查 SourceInspector、Extractor、SourceProtocolCleaner、NeutralMediaService、Image/VideoConverter、Target Writer/Validator 以及三个产品入口。逐个追踪可能把 B/C 或未知内容升级为整项失败的主要分支，不以 `throw` 数量判定问题。
2. 对每个候选记录：可达入口、触发条件、影响 A/B/C 哪一级、是否必要安全拒绝、已有替代能力、最小复现和决策。
3. 特别核对保留验证失败与“不知道是否保留”的区别、辅助资产数量/形态硬约束、普通音视频布局变化、取消和共享环境故障。它们目前是调查线索，不能直接认定为缺陷并放松验证。
4. 与 M1—M5 同根且在授权内的共用缺陷一起修；必须新增协议/编码能力或大改架构的问题记录为明确后续项，不以“全通用”为由无限展开。
5. 新增测试优先保护同一媒体的合法结构变化和产品结果；保留已有真实样本与安全反例，不批量删除拒绝测试，不调整期望只为绿灯。

**完成条件：** 有可复核的分支审查清单，必要拒绝与过严拒绝已分开；范围内发现没有被含糊标成“支持有限”后遗漏。未解决项有影响、证据、原因和下一步；存在范围内未解决问题时整体仍是未完成。

## 5. 推荐实施顺序与验证矩阵

先完成基线调查和最小复现，再按完整单元推进：M1 → M2/M3 → M4 → M5 → M6 补漏与收口。M5 的结果模型可以在 M2/M3 时共同设计，避免返工；M6 贯穿过程中，末尾只补缺口。每单元完成关联修改后做必要定向验证，不逐函数验收，也不拖到最后才首次测试。
