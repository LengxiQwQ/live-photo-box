审查开始 HEAD 为 `8cc4fcf6fb8e64f0d3130841c3fc1056d950158a`，含大量既有未提交修改。交接前正常快进到远程 `535c88b18fd0dc68e60117527092bb0710fa6ed8`，新增两次流量统计提交，未改变本次审查的媒体实现。本文与全部当前可版本化改动一起提交，最终提交号以聊天交付和 Git 历史为准。

范围：合成、拆分、修复，以及共用的转换、目标检查、事务发布、清理、原件后处理、队列、历史和 CLI。编辑页只核对共享代码影响，不授权扩展编辑功能整改。未实施产品修复；本报告不是全产品审计通过、发布许可或设备兼容结论。

证据分级：**源码确认**＝实际调用链存在；**真实复现**＝正式 CLI 或已有用户运行日志证实；**待定位**＝现象存在但根因尚未锁定；**风险**＝实现耦合需要检查，不能当作已经发生的数据问题。

## 2. 用户最新确认的产品规则

以下决定优先于旧计划、旧测试、旧隔离说明；实施时同步实际受影响的现行项目记录，保留历史，不重写历史证据。

| 条件 | 结果与输出 |
| --- | --- |
| 完成用户要求的目标，必要媒体和协议检查通过 | 绿色，正常输出。正常图片/视频/音频重编码、转 AAC、正确转 SDR、可靠转正、不携带无关私有历史，不单独判黄 |
| 已生成目标文件，但内容检查失败，或关键质量/可用性存在具体疑问 | 黄色隔离，写明哪项不确定、实际位置和影响；可可靠修复并复检通过时正常绿色 |
| 转换失败、无法生成可用结果、无法安全读取或发布 | 红色，不额外复制原件、提取媒体或转换中间物，不建立 `original-随机串` 恢复目录 |
| 用户取消 | 独立取消状态，准确报告已提交输出；不把取消伪装为成功、照片损坏或恢复导出 |

“检查失败”必须区分内容可用性检查和文件身份/权限/事务安全失败。前者允许安全隔离完整生成物；后者不得把未知或被替换的对象强行发布。不能为了保留文件绕过来源保护、身份校验或伪造正常检查通过凭据。

无声来源不要求凭空生成声音；有声来源应保持正常声音。实况目标除了图片显示、视频播放，还须确认配对、必要封面/时间线等目标功能。正规厂商样本在已承诺支持范围内出现兼容性缺陷必须修复，不能把隔离当作完成支持；同样不能凭厂商品牌跳过检查。

修复页：检测告诉用户发现什么，修复选项决定执行什么。任何已发现的问题/可清理项在队列状态和现有详情中说明；未检查不能显示正常，不因未选择修复就隐藏诊断。内嵌缩略图属于可清理项，不等于照片损坏，也不等于列表预览缩略图。

批次完成后，有隔离或失败时提供“查看隔离和失败”，点击切换当前列表筛选。复用现有界面，支持隔离、失败及两者合并查看；清除会遮挡问题项的旧搜索和不兼容筛选，保留排序，不自动开始重试。

## 3. 已确认问题与整改待办

状态均为“待实施”，不是已经修复。P1＝结果正确性/安全/主要功能；P2＝使用闭环及主要性能；P3＝后续能力和维护。允许按新证据调整依赖和优先级，但必须说明理由。

### P1-01 正常处理事实直接升级为隔离原因

- **证据：源码确认＋用户日志。** `LivePhotoBox.Core/Services/ProductExportAssessment.cs:15–36` 把 AAC/音频 Reencoded、HDR/ICC降级、附带轨丢弃及所有 `NotCarriedItem.Reason` 转为字符串警告。合成 Runner 和 Split 根据 `warnings.Count > 0` 选择隔离路径与 Warning。
- `StructuredTargetWriterService.cs:116–128` 为目标不承接普通元数据产生说明；约 575 行为 optional history/private asset 产生说明，这些也进入隔离判定。用户 OPPO/一加/荣耀输出已实际触发。
- **整改：** 区分信息性处理事实、已正确完成的兼容转换、具体质量/功能不确定性，不让文案或“是否有任何提示”直接决定成功。按实际语义判断；普通 EXIF映射错误、基础颜色错误不能被笼统当作可忽略信息。
- **完成条件：** 单独的正常 AAC重编码、正确SDR输出、无关私有信息省略不再触发隔离；声音丢失、颜色异常、目标配对未确认仍正确分类。只增加事实记录不改变结果颜色。

### P1-02 转换/发布失败后额外复制原件或中间媒体

- **证据：源码确认＋三项真实复现。** `ProductRecoveryService.cs:17–120` 建立 `original-<operationId>`，发布 `Recovered*` / `OriginalUnconverted`；文件名直接沿用中间物。Merge Runner 的准备、封面、Writer失败分支和 Split 的检查、准备、Writer、普通发布失败分支均会调用，不止一个入口。
- **整改：** 删除产品默认失败路径的恢复复制行为；转换失败返回准确失败终态和空提交列表，按现有事务回滚/清理本次拥有的暂存和部分输出。不能清空输出目录、删除既有成品或原件。旧历史记录保持可读，不为兼容而继续生成恢复文件。
- **完成条件：** 多种失败阶段均不产生新原件副本、中性媒体或 original目录；独立正常项继续，原件与既有输出不变。磁盘/共享锁等真实故障与内部错误准确分类。

### P1-03 内容检查失败尚无独立的安全隔离出口

- **证据：源码确认。** `NativeTargetValidator.cs:71–83,215起` 将目标检查不符和新鲜文件证据不符返回失败；`WindowsSplitOutputPublisher.cs` 的 Prepare/Commit/Failed路径回滚。Native `target_writer.cpp:688起 finish` 对非OK结果销毁两个stage；双文件内容检查在约768行之后，检查不符时也走该清理路径。上层拿到的恢复输出通常是Neutral文件，不是未通过检查的最终目标。
- **整改：** 区分转换执行失败、最终内容验证不确定、文件身份/权限/事务失败。为仅内容检查不通过、但本次完整生成且身份明确的候选提供受控隔离路径，准确保存诊断；不要复制来源替代成品，也不要允许普通发布绕过Validator。
- **完成条件：** 普通内容检查失败可保留准确的本次候选并黄灯；转换失败无恢复复制；来源替换、对象身份变化、未完成写入仍阻止不安全发布。双文件不能留下假称完整的一半输出。若确需公开ABI变更，先说明具体必要性和范围，不自行放开权限。

### P1-04 三个正规样本转 Apple 最后准备失败

- **证据：真实复现。** 华为-Mate80.jpg、华为Mate80.heic、vivo.jpg 的缓存与原件SHA256一致。正式CLI `split <单文件> -p apple -f jpg+mov --json` 均得到 RecoveredMedia；错误为 Apple independently decodable frame preparation 的 sidecar Unsupported（status=2）。这证明失败阶段，不证明最底层Unsupported的唯一原因。
- **定位入口：** `target_writer.cpp::stage_pair`、`run_video_sidecar_transcode`、sidecar的profile/SEI/时间线/音频约束及准备后实际媒体事实。不得因为遇到三个来源就增加按品牌、文件名或hash的专用捷径。
- **完成条件：** 查明通用根因，正式CLI生成所选Apple目标，独立工具检查图片/完整音视频解码、方向/颜色/时间线/目标结构，准确说明仍未进行设备相册验收。未实现的HDR Vivid能力不能通过改状态冒充已实现。

### P1-05 修复扫描受动作开关影响，缩略图项被显示为无需修复

- **证据：源码确认。** `RepairViewModel.cs:743起` 默认 StripImageThumbnail=false、FixHeicOrientation=false；约922行把RepairOptions直接传入DiagnosticOptions。`LivePhotoRepairService.cs:849–963` 按选定动作做元数据检查，HasThumbnail来自检查changed位。约789行 SupplementAnalysisAsync 只补新选动作。GUI约1686行开始执行前补诊断，因此用户会在后期才看到缩略图项。
- `RepairTask.cs::GetDisplayStatusText` 对NeedsStrip明确返回“无需修复”，即使已经发现缩略图项。`FormatDiagnosisLabels` 能显示HasThumbnail，但前提是事实被采集，且OtherDevice等提前返回还可能遮挡已有诊断。
- **整改：** 支持的只读诊断事实与用户动作选择分离；保留设备范围和明确未检查状态，不通过为了诊断就执行破坏性清理。短状态概括、现有详情列出全部发现；选项只决定执行，不改变已经发现的事实。
- **关联：** SupplementAnalysisAsync 在约807行用 actionable?NeedsRebuild:added.IssueType 重算汇总，可能受局部补查结论影响；诊断缓存、NeedsRepair、只看待修复/完好筛选和ActionMask均需一起验证。风险不等于已证实所有项目误分类。
- **完成条件：** 清理未选时扫描也显示可清理缩略图；更改选项不会凭空改变来源事实；旋转+缩略图、多问题、HEIC动作关闭、范围排除、部分检查失败都无假正常，确认对话框不再首次暴露扫描可发现的问题。

### P1-06 扩大成功范围会扩大原件后处理资格

- **证据：源码确认/关联安全约束。** `ProductOperationOutcome.IsSuccess` 只有Success；Runner/Split在其后捕获SourceActionGuard，GUI/CLI只对成功结果执行用户选择的移动/回收。`ProductSourceActionGuard` 和 `ProductSourcePostProcessor` 检查身份、字节和事务；当前有安全约束，未发现本轮已造成误删的证据。
- **整改：** 新的正常绿色结果仍须目标真正完成并取得有效本次凭据；黄色、失败、取消不得获得原件后处理资格。去除过度隔离不等于放开原件删除。改变分类时同时核查CLI、批量与双文件路径。
- **完成条件：** 源对象变化、输出替换、无凭据、隔离/失败、取消均保留来源；正常成功仅执行用户明确选择的现有动作，执行失败不会反向宣称成品损坏。

### P2-01 黄色不一定真的隔离，UI与持久结果可能不一致

### P2-03 黄色被用作已完成，重试/扫描语义耦合

- **证据：源码确认。** Merge约1492–1499行，Split约1417行把Success或Warning排除出待执行集合；扫描刷新也保留Success/Warning，修复Supplement循环跳过success/warning。历史恢复复制也为Warning，因此未完成目标可能被当作无需再执行。

### P2-04 临时清理失败把正确成品改黄并迁移

- **证据：源码确认＋现有测试保护旧行为。** `CleanupCompletion.ApplyAsync` 对任何cleanup failures将Success改Warning并调用CleanupOutputIsolation；修复`RepairOutcome.ExecuteRecordedAsync`存在对应逻辑。编辑`EditExportService`也用共享CleanupOutputIsolation，故不能直接改公共helper就假定无其他影响。

- **完成条件：** 普通清理残留不打乱成品路径；真正对象替换、丢失或回滚失败不被隐藏；不重构编辑产品流程，只做必要共享兼容。

### P2-06 Apple额外编码路径与未记录的完整执行事实

- **证据：源码确认＋耗时线索。** `target_writer.cpp:725–753` 若非all-intra会再调用sidecar；上游Neutral准备可能已经为格式、显示区域、方向编码。`PreparationExecution`仅记录准备阶段，末段编码不在其Video.Duration内，也不能据此保证最终目标仍是原音频/像素。
- **整改：** 先核对目标全帧独立解码要求的协议依据，再尽可能合并处理或复用已达标视频，不直接删要求。至少准确记录最后写入阶段实际编码、音频变化和耗时，不把准备记录当最终保留证明。
- **完成条件：** 同参数同输入可比较的阶段计时；避免确实多余的重编码；方向、颜色、完整音视频、封面/时间线和目标结构不回退。最终检查是否覆盖可播放性要以真实实现为准，结构读取不等于所有帧解码。

### P2-07 并发和UI调度有卡顿风险，唯一根因未定

- **证据：用户现象＋源码风险。** Merge无HEIC时maxParallel硬编码20，有HEIC才使用设置；Split使用SplitThreadCount。两页60ms定时通知，即使计数不变也刷新部分文字。处理前在UI线程同步ProductCapabilityQuery→NativeRuntime.Probe；后台完成回调等待UI，Merge用GetAwaiter().GetResult，Split等待TCS。自动滚动和文本测量也是相关链路，不可凭源码判为唯一原因。
- **整改：** 补阶段/资源/UI排队数据，后台探测、合并按变化更新、限制处理资源占用；必要时局部统一任务预算。不得只把60ms改成大数就称流畅，也不能仅增加并发声称更快。
- **完成条件：** 实际GUI待用户观察；非桌面检查确认线程接线、完成更新和取消不丢。报告性能改善必须给参数、输入、冷/热条件及可比较数据。

### P2-08 硬件选择与实际执行不一致；P3-01 实际GPU能力接入

- **证据：源码确认＋用户日志。** `video_converter.cpp:2155,2372,2567` MF设置硬件转换FALSE；约3821行报告software forced。sidecar约1110行使用CPU线程预算，preset=medium；本次实际编码器为minimal-libav/.../libx265。配置NVENC不等于实际使用。

- **完成条件：** 可追踪实际后端；没有GPU路线就不声称启用；接入后验证质量、方向、色彩、音频、时间线、取消与错误，不只验证编码能启动。
