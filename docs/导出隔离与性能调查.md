2026-11-09；用户反馈 `designs/各个机型测试/` 导出频繁隔离、出现 original 子目录、处理慢及队列滚动卡顿。本轮为本地调查与真实 CLI 复现，不修改产品代码、测试或契约，不接管桌面，不提交推送。HEAD：`8cc4fcf6fb8e64f0d3130841c3fc1056d950158a`，工作区包含大量既有未提交修改。

## 已确认的问题

1. **隔离目录混合了不同性质的结果。** 当前 `ProductExportAssessment.Warnings` 把传入的所有 `NotCarriedItem.Reason` 都升级为警告，进而隔离。用户日志中 OPPO、一加、荣耀的原因包含普通元数据未承接，一加改封面样本还有 optional history/private asset 未承接。后者属于需要按 A/B/C 审查的可选内容，不能直接据此认为基础媒体损坏；目前用户难以分辨合理降级、可选内容未携带与目标生成失败。
2. **original 子目录可能保存的是已提取或转换的媒体。** `ProductRecoveryService` 对恢复输出沿用 `original-<operationId>` 命名，且直接使用工作文件名。目录名不能证明里面都是原始输入，也不能表示目标实况生成成功。
3. **华为 JPG、华为 HEIC、vivo 单文件的 Apple JPG+MOV 路径真实失败。** 三份缓存与原样本 SHA256 一致。正式 CLI 复现均返回 `RecoveredMedia`，失败在 Writer 的 Apple independently decodable frame preparation，内部转换返回 Unsupported。图片/视频恢复输出存在，但目标 Apple 实况没有完成。不能通过取消隔离或改绿灯解决。
4. **视频硬件选择没有接通这条媒体路径。** Native MF 显式禁用硬件转换；sidecar 使用 CPU x264/x265，preset=medium。本次日志实际使用 `minimal-libav/.../libx265`。设置里的 NVENC 选择不构成实际硬件编码证据。
5. **Apple 最后写入阶段还有一次编码路径。** `target_writer.cpp::stage_pair` 对非全帧独立解码视频再次调用 sidecar；上游可能已经为格式、方向或裁切编码一次。这解释了部分完整任务远慢于准备记录中的视频转换耗时，但各阶段耗时尚未完整测量，不能把全部差额都归因于二次编码。
6. **恢复结果未进入历史。** 三个 CLI 复现均出现 `Operation history could not be saved.`。当前历史校验只接受常规目标输出角色，恢复输出采用 `RecoveredPrimaryImage` / `RecoveredMotionVideo`，不符合该校验。用户 GUI 日志有 8 条拆分结构化结果，未找到三个恢复结果的对应记录。

## 性能证据和界限

用户 GUI 日志：11 个拆分任务，总用时约 125 秒，完成统计 2 succeeded / 0 failed；黄色不计 succeeded。8 条可读取的拆分结果为 2 绿、6 黄；另三个缺少历史记录，不能用 0 failed 宣称全部目标完成。

| 输入 | 任务耗时 | 准备阶段视频转换耗时 |
| --- | ---: | ---: |
| OPPO JPG | 30.39s | 6.86s |
| 一加改封面 JPG | 54.72s | 13.20s |
| 一加 JPG | 58.70s | 13.31s |
| 三星 JPG | 58.79s | 14.91s |

上述是用户运行的日志，不是本轮控制变量基准。另做 OPPO `none + keep` 正式 CLI，约 8.16 秒完成，其中视频准备约 5.23 秒，仍因显示处理进入 x265，说明 keep 不等于一定不编码；该结果与用户 Apple 导出条件不同，不能作为修复前后加速比。

**滚动卡顿尚未实际 GUI 验证或采样定因。** 已确认的代码风险：合成队列无 HEIC 时硬编码最多 20 项并行；合成/拆分每 60ms 发界面状态通知；开始处理时在 UI 线程同步做 Native 能力探测；后台完成回调等待 UI 应用状态。它们需要针对性测量，不能仅凭源码宣布卡顿已定位或修好。用户日志显示扫描时缩略图关闭，不能直接把本次问题归咎于缩略图。

## 后续修复顺序与完成条件

1. 修复三个真实输入的 Apple 最终准备失败；保留方向、颜色、时间线、音频、文件安全验证，正式 CLI 成品与离线独立检查通过后才能称电脑端修复完成。
2. 把目标要求尽可能合并到一次视频准备，避免先普通编码再全帧编码；先确定全帧要求的协议依据，不能为了速度直接移除兼容性要求。
3. 按实际语义区分必需媒体降级与可选历史信息未携带，减少无必要的隔离；恢复结果保留未完成标识，目录和文件名采用用户能识别的来源名称；修复历史记录对恢复结果的接纳。
4. 为合成/拆分设置有界资源预算、后台能力探测及按变化合并的 UI 更新，测量阶段耗时和界面调度延迟。硬件编码属于独立的实际接线工作，不能靠开启一个布尔开关就宣称完成。

本轮未实施上述修复；没有 GUI 流畅度、设备相册兼容或全产品导出通过结论。
