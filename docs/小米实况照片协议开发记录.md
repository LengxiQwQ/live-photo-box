## 1. 项目背景和目标

**LivePhotoBox** 是一款 Windows 实况照片工具箱，支持合成/拆分/修复/更换封面。

合成 (Combo) 页面最初支持 3 种协议：
- **MicroVideo V1** (Google V1, Id=0)
- **MotionPhoto V2** (Google V2, Id=1)
- **OPPO Live Photo** (Oppo 专属, Id=2)

目标是新增第 4 种协议 **XiaomiMotionPhoto (Id=3)**，使合成的输出文件能在以下环境中被识别为实况照片：
- **Windows 11 文件资源管理器** — 显示"实况照片"徽章
- **小米相册 (HyperOS)** — 正常播放动态效果

### 1.1 协议架构设计

所有协议继承自抽象基类 `LivePhotoProtocol.cs`：

```csharp
public abstract class LivePhotoProtocol {
    public abstract int Id { get; }              // 唯一 ID
    public abstract string Key { get; }          // 协议标识
    public abstract string DisplayName { get; }   // 显示名
    public abstract byte[] BuildXmpMetadata(long videoSize);
    public virtual Task<string> PrepareImageAsync(
        string sourceImagePath, string workDir, CancellationToken token)
        => Task.FromResult(sourceImagePath);     // 默认无需预处理
}
```

合成流程：
```
HEIC → JPEG (Magick.NET)
  → protocol.PrepareImageAsync()    [小米: exiftool 注入 EXIF 标签]
  → WriteNativeAsync()              [写入 SOI + XMP APP1 + JPEG数据段 + 视频]
```

## 2. 小米 MVIMG 格式研究

### 2.1 分析样本

共分析了 3 份小米实况照片样本:

| 样本 | 来源 | 文件特征 |
|------|------|----------|
| 12S Ultra 原版 | MIUI 系统拍摄 | 无 MiCamera 命名空间，纯 GCamera MicroVideo V1 |
| 14 Pro (HyperOS 3+) | HyperOS 3 系统拍摄 | 有 MiCamera 命名空间 + 私有 EXIF 标签 |
| K70 (微信传输版) | 微信接收 | 缺失 IFD0 基础标签, EXIF 部分丢失, 但有 MiCamera 命名空间 |

### 2.2 小米实况照片与 Google MotionPhoto V2 的差异

| 维度 | Google MotionPhoto V2 | 小米 MVIMG (14 Pro) |
|------|----------------------|---------------------|
| **XMP 基础字段** | `GCamera:MotionPhoto=1` + `Container:Directory` | ✅ 完全相同 |
| **XMP 额外命名空间** | 无 | `MiCamera` (`http://ns.xiaomi.com/photos/1.0/camera/`) — 部分设备有 |
| **EXIF Make/Model** | 不变 | 保留原设备 (Xiaomi / Xiaomi 14 Pro) |
| **EXIF 私有标签** | 无 | 8 个私有标签 (0x9a00, 0x889e, 0x889d, 0x88a3, 0x889a, 0x8895, 0x8897, 0xa661) |
| **视频容器** | MP4/HEIC 尾部追加 | 同样尾部追加 MP4 |

### 2.3 小米 8 个私有 EXIF 标签

| Tag ID | 名称 | IFD 位置 | 格式 | 示例值 | 用途推测 |
|--------|------|----------|------|--------|----------|
| `0x9a00` | XiaomiModel | IFD0 | string | `Xiaomi 14 Pro` | 设备型号标识 |
| `0x889e` | XiaomiDeviceInfo | ExifIFD | string (JSON) | `{"buildDevice":"shennong",...}` | 设备/镜头/滤镜信息 |
| `0x889d` | XiaomiRegion | IFD0 | string | `Madrid` | 区域/固件版本代码 |
| `0x88a3` | XiaomiEmptyJson | IFD0 | string | `{}` | 空占位符 |
| `0x889a` | XiaomiMarkerA | IFD0 | int8u | `0` | 标记位 |
| `0x8895` | XiaomiVersionFlag | ExifIFD | int8u | `3` | HyperOS 版本标记 (14 Pro = 3) |
| `0x8897` | XiaomiFlag2 | ExifIFD | int8u | `1` | 次要标记 |
| `0xa661` | XiaomiUnknownInt | ExifIFD | int16u | `163` | 未知数值 |

### 2.4 Windows 11 实况照片识别规则（后验总结）

通过大量测试反向推导出的 Windows 11 识别逻辑：

1. **XMP 层面** (必要条件):
   - 必须有 `GCamera:MotionPhoto="1"`
   - 必须有 `Container:Directory` + `Item:Semantic="MotionPhoto"` + `Item:Semantic="Primary"`
   - 以上即是 Google MotionPhoto V2 的完整 XMP

2. **EXIF 层面** (辅助条件):
   - 当 EXIF 中存在 Xiaomi 私有标签 (0x889x/0x9a00/0xa661) 时:
     - **Make 必须为 "Xiaomi"**
     - **Model 也必须为 Xiaomi 设备名**（如 "Xiaomi 14 Pro"）
     - Make 和 Model **两个都必须改**，只改 Make 不改 Model 不识别
   - 当没有私有标签时:
     - Make/Model 不影响识别 → 任何设备都行

3. **文件结构层面**:
   - EXIF IFD 的 padding 必须保留 (~4.5KB)
   - 用 exiftool 通过 stdin 写入标签会破坏 padding
   - 用 `-tagsFromFile @` 机制 (命令行直传) 可以保留 padding

## 4. 第二次实现（失败：MiCamera 命名空间破坏识别）

### 4.1 问题

当 8 个私有标签都成功写入后，Windows 11 仍然不识别合成文件。

### 4.2 假设与验证

**初始假设:** MiCamera XMP 命名空间是必要的（参考 14 Pro 原版文件有它）。

于是: 做了 3 个测试文件:

1. **`test_exact_copy.jpg`** — 直接把小米 14 Pro 原版文件的 JPEG 部分替换为 iPhone 图片内容，保留 EXIF + XMP 不变 → ✅ 可识别
2. **`test_exiftool_nop.jpg`** — 可识别的 V2 文件 + `exiftool -tagsFromFile @`（不改任何标签）→ ✅ 可识别
3. **`test_exiftool_xiaomi_tags.jpg`** — V2 文件 + exiftool 注入全部 8 个小米私有标签（有 -config 加载）→ ❌ 不可识别

这证明了: **小米私有标签本身不破坏识别**，但 **exiftool 的写入方式**破坏了文件结构。

然后测试: 给不可识别的文件加上 MiCamera XMP:
4. **`test_fix_micamera_xmp.jpg`** — 在 test_exiftool_xiaomi_tags.jpg 基础上 XMP 加上 MiCamera 命名空间 → ❌ 依然不可识别

### 4.3 关键转折

发现不可识别的文件和可识别文件之间 **相差 4.5KB**:

| 文件 | 大小 | 识别? |
|------|------|-------|
| `test_exact_copy.jpg` (原版改图) | 11,501,919 字节 | ✅ |
| `test_exiftool_nop.jpg` | 11,511,489 字节 | ✅ |
| `test_exiftool_xiaomi_tags.jpg` | 11,468,xxx 字节 | ❌ |

文件差异根源: **exiftool 通过 stdin (`-@ -`) 写入标签和通过命令行直传 (`-tagsFromFile @` 在命令行上) 行为不同**。

## 6. 根因分析汇总

### 6.1 根因 1: EXIF Padding 丢失 (最关键)

```
问题: exiftool 的 stdin 管道模式 (-@ -) 不保留 EXIF IFD padding
现象: 文件大小差 ~43KB 中的 4.5KB padding
机制: -tagsFromFile @ 在命令行上时和 tag 赋值是同一个进程上下文，
      exiftool 会保留原始 IFD 序列化布局（包括 padding）。
      通过 stdin 传入时，exiftool 重建 IFD 布局，丢弃 padding。
结果: Windows 11 的 Motion Photo 识别器对 IFD 布局敏感，
      重建后即使 XMP 和标签值完全正确也不识别。
```

#### ExifTool 调用方式对比

```
✅ 命令行直传 (RunExifToolDirectAsync):
  exiftool -config XiaomiTags.config -overwrite_original -tagsFromFile @ -Make=Xiaomi ... file.jpg
  文件大小: ~11,511KB
  EXIF padding: 保留 ~4.5KB padding
  Windows 识别: ✅

❌ stdin 管道 (RunExifToolAsync / -@ -):
  echo -overwrite_original -tagsFromFile @ -Make=Xiaomi ... | exiftool -@ - file.jpg
  -- 或 --
  Process.Start 传参时通过 stdin 管道
  文件大小: ~11,468KB
  EXIF padding: 丢失 (重建后 padding 消失)
  Windows 识别: ❌
```

### 6.2 根因 2: Make/Model 一致性检查

```
当 EXIF IFD0 中存在小米私有标签 (0x9a00, 0x889d, 0x88a3, 0x889a) 时，
Windows 11 会验证 Make 和 Model 是否匹配 Xiaomi。
  - Make 必须是 "Xiaomi"
  - Model 必须是 Xiaomi 设备名 (如 "Xiaomi 14 Pro")
  - 只改 Make 不改 Model → 通不过验证
```

### 6.3 根因 3: XiaomiModel 标签值的字符串长度

```
XiaomiModel (0x9a00) 的值直接影响 IFD0 的布局大小:
  "iPhone 16 Pro Max" = 20 字节 → 不同的 IFD 偏移 → 可能影响 padding 对齐
  "Xiaomi 14 Pro"     = 16 字节 → 与 Model 一致 → 正确的 IFD 布局

在 exiftool 中:
  -XiaomiModel<Model  ❌ 从原始文件取值 (拿到 "iPhone 16 Pro Max")
  -XiaomiModel=Xiaomi 14 Pro  ✅ 直接设固定值
```

### 6.4 根因 4: MiCamera 命名空间（实际不是根因）

```
最初以为是 MiCamera 命名空间导致的问题:
  xmlns:MiCamera="http://ns.xiaomi.com/photos/1.0/camera/"

但 test_A (无 MiCamera) 可识别 + test_C (无 MiCamera) 也可识别 →
  实际 MiCamera 命名空间不影响 Windows 11 识别
  之前的误判是因为同时有 EXIF padding 丢失的问题在干扰

注意: 小米原始 14 Pro 文件有 MiCamera，但标准 V2 没有也能被小米相册识别
```

### 6.5 完整因果链

```
HEIC → Magick.NET → JPEG 输出
  ↓
XiaomiMotionPhotoProtocol.PrepareImageAsync()
  ↓
exiftool (stdin 管道)                                            ❌
  → 丢失 4.5KB EXIF padding
  → Make/Model 被改
  → 输出文件: 不正确的大小 (~11,468KB 量级)
  → Windows 拒绝识别
  ↘
更换方案: exiftool (命令行直传, -tagsFromFile @)                 ✅
  → 保留 EXIF padding
  → Make=Xiaomi, Model=Xiaomi 14 Pro
  → XiaomiModel=Xiaomi 14 Pro (= 赋值, 不是 < 复制)
  → 全部 8 个私有标签
  → XMP = 标准 V2 (无 MiCamera)
  → 输出文件: 正确大小 (~11,511KB 量级)
  → Windows 识别 ✅
```

## 7. 最终代码方案

### 7.1 新增方法: `RunExifToolDirectAsync`

**文件:** `Services/LivePhotoRepairService.cs`

```csharp
/// <summary>
/// 运行 exiftool（一次性模式），所有参数直接放命令行（不走 stdin）。
/// 仅适用于文件路径不含特殊字符的场景。
/// 使用此方法时，-tagsFromFile @ 与标签覆盖在同一命令行上，
/// exiftool 会保留 4.5KB EXIF padding，使 Windows 11 能识别输出。
/// </summary>
public static async Task RunExifToolDirectAsync(
    string? configFilePath, CancellationToken token, params string[] args)
{
    var psi = new ProcessStartInfo
    {
        FileName = ExifToolPath,
        RedirectStandardOutput = true,
        RedirectStandardError = true,
        UseShellExecute = false,
        CreateNoWindow = true,
    };

    if (!string.IsNullOrEmpty(configFilePath))
    {
        psi.ArgumentList.Add("-config");
        psi.ArgumentList.Add(configFilePath);
    }

    foreach (var arg in args)
        psi.ArgumentList.Add(arg);

    using var process = Process.Start(psi);
    // ... 读 stdout/stderr，检查 "Error:" 关键字
}
```

## 8. 最终结论

### 8.1 当前状态

经过大量测试，最终的结论是：

**直接用 Google MotionPhoto V2 协议就够了。**

理由：
- **Windows 11 原生识别 V2** — 只要 XMP 结构正确（GCamera:MotionPhoto + Container:Directory）就识别
- **小米相册也识别 V2** — 不需要 MiCamera 命名空间，不需要私有 EXIF 标签
- **不需要改 Make/Model** — V2 协议不碰 EXIF，输出文件的 Make 还是 Apple/iPhone，完全保留原设备信息
- **代码最简单** — 不需要 exiftool、不需要 XiaomiTags.config、不需要私有标签注入

### 8.2 Xiaomi 私有 EXIF 标签的真正用途

所有 8 个私有 EXIF 标签 + Make/Model 修改 + MiCamera 命名空间，只是小米相册的**额外增强识别手段**，不是必需的。小米相册也会回退到标准 MotionPhoto V2 检测。

### 8.3 之前失败的总结

导致识别失败的不是任何一个单一因素，而是**多重因素叠加**：

```
错误流程:
  MiCamera 命名空间 ❌  →  (以为是根因 → 去掉)
  exiftool stdin 管道 ❌ →  丢失 padding → Windows 不识别
  Make 改了 Model 没改 ❌
  XiaomiModel 长度不对 ❌

正确流程:
  -tagsFromFile @ 命令行直传 ✅ → padding 保留
  全部标签正确赋值 ✅
  XMP 标准 V2 ✅
  → 可识别
```

### 8.4 如果以后要重新拾起 Xiaomi 协议

1. **先读当前代码:** `XiaomiMotionPhotoProtocol.cs` 的 `PrepareImageAsync`
2. **确认使用的是 `RunExifToolDirectAsync`** (不是 `RunExifToolAsync`)
3. **确认 `-tagsFromFile @` 在命令行上** (不在 stdin 管道理)
4. **确认 Make 和 Model 都改了** Xiaomi 值
5. **确认 XiaomiModel 用 `=` 赋值** (不用 `<` 从 Model 复制)
6. **`XiaomiTags.config` 必须随应用部署** (csproj 的 `<Content Include>` 要生效)
7. **测试时对比文件大小** — 可识别 vs 不可识别的 V2 文件大小应该接近 (差异 < 100 字节)，如果差了 ~43KB 说明 padding 有问题
