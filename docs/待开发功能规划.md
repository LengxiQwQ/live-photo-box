## 1. CLI 命令行工具（AI 接口）

> ✅ **已交付（v2.1.1）**。作为独立工程 `LivePhotoBox.CLI` 交付（可执行名 `livephotobox`），与 GUI 共享 100% 核心逻辑（`LivePhotoBox.Core`）。

最初规划新增 .NET 控制台应用，引用现有 Services 层，编译为独立 exe，让 AI Agent 和高级用户能通过终端调用核心功能——现已落地，实际命令集以 `merge` / `protocols` / `update-check` / `update` 为准：

```
livephotobox merge -i a.jpg -vid a.mov -o out -p huawei -f heic+mp4-h265
livephotobox merge -d "D:\Photos\" --pairing cid --after move:D:\整理
livephotobox protocols
livephotobox update-check
livephotobox update
```

- 框架：.NET 控制台应用 + System.CommandLine（4 个可执行别名：`livephotobox` / `livephoto` / `livebox` / `lpb`）
- 单对合成 + 批量合成（按文件名 / Apple `ContentIdentifier` UUID / vivo 相机 ID 配对）
- 命名模板、并行度 `-j`、`--dry-run`、`-y`、`--overwrite`、`--recursive`、`--preserve-subdirs`、`--after`（移动文件夹 / 回收站）
- 安装版用户：CLI exe（`livephotobox` 及别名）由 Inno Setup 可选注册到 PATH
- 商店版用户：仅通过 GUI 操作
- 使用文档：`docs/CLI-User-Guide.zh-CN.md` / `docs/CLI-User-Guide.md`

> 原规划的 `combo/split/repair/edit/scan` 命令集未采用（`combo` 最终命名 `merge`）；拆分 / 修复 / 编辑 / 扫描仍为 GUI 专属。

## 5. UI 框架变更 —— 三面板布局

去掉传统 WinUI 页面底色/背景面板设计，改为 **3 面板拼接布局**：

- **左面板**：文件列表/资源浏览树
- **中面板**：主操作区（预览/编辑/参数设置）
- **右面板**：信息详情/任务状态

优势：
- 视觉更简洁统一
- 主操作区更宽敞
- 各页面布局一致，减少切换割裂感

## 6. 其他待定想法

### 6.1 CLI 发布改为单文件（PublishSingleFile）——待定

**背景**：CLI 当前为自包含多文件发布，解压后 228 个文件、131 MB，其中约 200 个是 .NET 运行时 DLL；用户反馈根目录文件太多，README / 使用手册 / PATH 脚本难找。

**方案**：CLI 发布加 `PublishSingleFile=true`，把运行时 + 全部托管 DLL 打进一个 exe。

实测对比（同配置 Release x64 自包含，2026-08-13 编译验证）：

| 指标 | 多文件（现状） | 单文件 |
|------|--------------|--------|
| 文件数 | 228 | 1 个 exe + 4 个 2MB 别名 |
| 解压后占用 | 131 MB | ~99 MB |
| zip 下载体积 | 53 MB | ~38 MB |

注意点：
- **不影响 GUI/CLI 共享代码**——共享的是源码（`LivePhotoBox.Core` 项目），不是二进制；GUI 不依赖 CLI 的 dll，共存打包无冲突
- `Tools\`（exiftool / ffmpeg / heif 等外部进程）无法打进单文件，仍须与 exe 同目录
- 需先修构建：csproj `CreateAliases` target 会为别名复制 `.runtimeconfig.json` / `.deps.json`，单文件模式下这两个文件被内嵌、不存在，需按 `PublishSingleFile != true` 跳过
- 上线前必须真机验证：① 杀软误报（国内 360 / 腾讯管家对自解压单文件敏感）② `lpb update` 自更新 ③ Tools 外部工具调用

### 6.2 包根目录入口文件夹（1-START-HERE）——待定

把面向人的文件（README / CLI 手册 / PATH 脚本）在构建时收进一个顶层入口文件夹（如 `1-START-HERE/`），解决"几百个文件里找不到 CMD / 文档"的问题。已落地的部分：PATH 脚本末尾已加 `pause`（双击窗口不再一闪而过）。注意：约 200 个运行时 DLL 因 .NET 要求必须与 exe 同目录，无法归类。

## 7. HEIC HDR 增益图转换（待开发）

### 7.1 背景：HEIC 无损配对链路已交付（但不含 HDR）

当前已完成「HEIC → HEIC」的**字节级无损**链路：在源 HEIC 的 Exif item 里原位写入 Apple `ContentIdentifier`，不重编码像素，保留 10-bit 子图 / 增益图 / 辅助图 / 厂商私有数据，并跳过 exiftool 整文件重写。

已交付代码：

| 文件 | 作用 |
|------|------|
| `LivePhotoBox.Core/Services/Protocols/HeifBoxParser.cs`（新增） | 按 ISO/IEC 14496-12 + 23008-12 解析 `meta → iinf/infe → iloc`，定位 Exif item 的绝对字节偏移与长度 |
| `AppleMakerNoteWriter.TryInjectAppleMakerNoteIntoHeic` | 原位重建 Exif item 的 TIFF，写入唯一一条 Apple MakerNote（70 字节） |
| `AppleMakerNoteWriter.RemoveMakerNotesFromTiff` | 删除旧厂商 MakerNote 条目并回收其数据区（否则新 TIFF 放不下） |
| `LivePhotoSplitService.cs` | Apple 目标 + HEIC 源优先走无损，失败回退 HDR 重编码；无损路径跳过 `StripHeicXmpAsync` 与 `TryWriteLivePhotoBoxMarkerAsync` 两处 exiftool 重写 |

关键机制（标准依据）：

- HEIC 盒子结构是公开国际标准：ISO/IEC 14496-12（ISOBMFF）+ ISO/IEC 23008-12（HEIF）。
- `iloc`（ItemLocationBox）就是「每个 item 精确在哪个字节、多长」的登记表，解码器不靠猜位置；`iinf/infe` 给 item 的 ID 与类型（`hvc1`=像素、`Exif`=元数据）。
- Exif item 内部：`[4 字节 tiff 偏移]["Exif\0\0"][TIFF]`；MakerNote 是 TIFF 的 `0x927C` 标签（CIPA Exif）。

已验证（字节级、本地工具）：

- 华为 `原图.heic`：23 个 item 全保留（16 个 hvc1 瓦片 + 2 个 grid，含半分辨率 10-bit 子图），输出大小与源图像部分完全一致（2,073,984 字节），CID 图片/视频配对，仍可 `heif-dec` 解码。
- 苹果 `谷歌.heic`：120 个 item 全保留（含 `hdrgainmap` 增益图与 `linearthumbnail` 10-bit 线性缩略图），CID 配对。

### 7.2 问题：导出后 iPhone 上仍没有 HDR

上述无损链路只做到「原样保留 + 配对」，**并不能让 iPhone 显示 HDR**。真机实测：

- 华为 `原图.heic` 导出 → iPhone 无 HDR。
- 荣耀 `荣耀.jpg`（源文件直接看）→ iPhone 有 HDR。

### 7.3 关键结论：HDR 在主图之外，靠「增益图（gain map）」承载

三张样本的 HDR 载体各不相同：

| 样本 | 设备 | HDR 载体 | 苹果是否认 |
|------|------|----------|-----------|
| `荣耀.jpg` | HONOR BKQ-AN10（JPEG） | Google Ultra HDR 增益图：`GainMapImage`（326,047 字节）+ XMP `GContainer`（Primary, GainMap）+ MPF | ✅ 认（ISO 21496-1 / Ultra HDR） |
| `谷歌.heic` | iPhone 16 Pro Max | Apple `urn:com:apple:photo:2020:aux:hdrgainmap` + `linearthumbnail`（10-bit） | ✅ 认（自家格式） |
| `原图.heic` | 华为 | 主图 8-bit（3072×4096）+ 半分辨率 10-bit RGB 子图（1536×2048，`10 10 10`），没有 `auxC`，不是标准增益图 | ❌ 不认 |

关键证据（exiftool / 字节级）：

- 荣耀 `GainMapImage` 为 Binary data 326,047 字节，`XMP-GContainer` 的 `DirectoryItemSemantic = Primary, GainMap`。
- 华为 `原图.heic` 的 `ipco` 里没有 `auxC` 属性，那张 10-bit 子图是普通 grid item，不是标记为增益图的辅助图。
- 华为 `原图.heic` 有 BT.2020/HLG nclx + MaxCLL 900 / MaxFALL 203，但主图是 8-bit，HDR 实际寄存在那张半分辨率 10-bit 子图里。

**注意：软件界面显示「10-bit」不可靠，必须看字节（SPS/profile、`pixi`、`ispe`）。`heic` brand = HEVC Main/Main Still Picture（8-bit）；`heix` = Main 10（真 10-bit）。**

### 7.4 待开发目标

把华为 / 荣耀的增益图（或华为的 10-bit 子图）**转换成苹果认识的增益图格式**，使导出的 HEIC 在 iPhone 相册里真正显示 HDR。

### 7.5 三种增益图格式（调研笔记）

| 格式 | 载体 | 说明 |
|------|------|------|
| ISO 21496-1（Google Ultra HDR） | JPEG 的 MPF 第二张图 + XMP `GContainer` | Android / 荣耀 / 小米等；iOS 18+ 可读 |
| Apple `hdrgainmap` | HEIF 的 `auxl`/`auxC` 辅助 item（`urn:com:apple:photo:2020:aux:hdrgainmap`） | 苹果 HEIC 的增益图 |
| 华为 10-bit 子图 | 普通 grid item，半分辨率 10-bit RGB，无 `auxC` | 华为私有，非标准增益图 |

### 7.6 动手前必须先弄清的问题

1. 华为那张 10-bit 子图到底是什么：是「10-bit HDR 版本」，还是「残差图 / 深度图」？需要解出像素、和 8-bit 主图逐像素对比后才能确定。
2. 增益图的数学关系：通常 `gain map = log2(HDR / SDR)` 之类的单通道比值图（不是 RGB 图）。华为是 10-bit RGB，和标准 gain map 语义不同，转换不是简单重封装。
3. Apple `hdrgainmap` 的确切 bitstream 格式：需要查 libheif / 官方资料或反推苹果样本（`谷歌.heic`），确认它期望的编码（8-bit 单通道？HEVC？线性？）。

### 7.7 可能的实现方向（供评估，均未实施）

| 方向 | 思路 | 复杂度 | 依赖 |
|------|------|--------|------|
| A. 华为子图 → Apple hdrgainmap | 解码华为 10-bit 子图，算 gain map，重编码为苹果 aux item | 高（图像处理 + 苹果格式逆向） | heif-enc/dec、libheif C++ API、苹果格式调研 |
| B. 荣耀增益图 → 直接搬进 HEIC | 把 JPEG MPF 的 gain map 提出来，转成 ISO 21496-1 或 Apple hdrgainmap 放进 HEIC | 中 | 需搞清 HEIC 内 gain map 的封装 |
| C. 先做「不丢」 | 导出时至少别把源增益图丢（荣耀 JPEG 增益图在 HEIC 输出里保留一个 aux item） | 低 | 主要是容器级搬运 |

### 7.8 验证方法

- 本地：`exiftool -GainMapImage / -HDRType`、字节级确认 `hdrgainmap`/`auxC`、`heif-dec` 可解码。
- 真机：传到 iPhone 相册，看照片是否自动进入 HDR 显示（高光更亮、有 HDR 标记）。
