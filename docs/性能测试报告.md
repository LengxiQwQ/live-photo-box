# EditPage 资源浏览 — 性能测试报告

> **测试日期**: 2026-07-20  
> **测试目录**: `D:\图片\相册\苹果导出2025年`（Apple 实况照片导出）  
> **测试工具**: `tests/LivePhotoBoxStressTest/`（独立控制台，直接调用 exiftool / ffmpeg）  
> **测试数据规模**: 7,681 个文件（4,821 图片 + 2,860 视频），2,472 对实况照片

---

## 1. 背景

用户在 EditPage（实况照片编辑页）左侧资源浏览区遇到以下问题：
- **快速切换文件时卡顿**，有时直接闪退（无异常弹窗，弹出 debug 工具）
- **目录扫描耗时极长**，7,000+ 照片需要一分多钟
- **点击一个文件要响应好几秒**，时间轴区域效率低

---

## 2. 页面加载链路

用户点击 ListView 中的一个文件时，EditPage 触发的完整链路：

```
FileItemListView_SelectionChanged
  └─ EditViewModel.SelectFile(filePath)
       ├─ 取消上一次操作 (_propLoadCts, _timelineCts)
       ├─ LoadPreviewImageAsync()        — 大图预览解码（HEIC: BitmapDecoder + 缩放）
       ├─ LoadPropertiesAsync()           — exiftool 查询 EXIF / 视频元数据
       │    ├─ 提取嵌入式视频 (SingleFileJpeg)
       │    ├─ PersistentExifTool 查询    — -stay_open 进程复用
       │    └─ TriggerTimelineExtraction()
       │         └─ VideoFrameExtractionService.ExtractAllFramesAsync()  — ffmpeg 全帧提取
       ├─ 刷新 InfoPanel (EXIF/相机/日期/GPS/协议)
       └─ 刷新 TimelineFrames + 缩略图
```

目录扫描时的链路：

```
EditViewModel.TriggerScan()
  └─ ScanDirectoryAsync()
       ├─ Phase 1: LivePhotoDiscoveryService.ScanAsync()
       │    ├─ 文件枚举
       │    ├─ JPEG XMP 标记检测 (识别 MicroVideo V1 / MotionPhoto V2 / OPPO)
       │    ├─ HEIC ftyp box 视频轨检测
       │    └─ CID 配对 (ContentIdentifier UUID 匹配)
       ├─ Phase 2: ReadResolutionsAsync()
       │    └─ PersistentExifTool × 2 并行池 → 每个文件查询分辨率/日期
       └─ Phase 3: ThumbnailService → 生成缩略图
```

## 3. 测试工具

### 3.1 工具位置

```
tests/LivePhotoBoxStressTest/
├── LivePhotoBoxStressTest.csproj   # .NET 9 控制台项目
├── Program.cs                      # 单文件，全部测试逻辑
└── bin/Release/.../Tools/          # 构建时从主项目自动复制的 exiftool / ffmpeg
```

工具是一个**独立的 .NET 9 控制台程序**，不依赖 WinUI / WinAppSDK，不引用主项目。直接通过 `Process.Start` 调用 exiftool 和 ffmpeg 执行真实的后端操作，与主应用中的 `PersistentExifTool`、`VideoFrameExtractionService` 执行的是**同一套外部工具**。

### 3.2 为什么不用主项目代码

最初尝试过两种方式但都失败了：

| 尝试 | 方式 | 结果 |
|------|------|------|
| 方案 A | 控制台项目用 `<ProjectReference>` 引用主项目 | MSIX 打包目标冲突、XAML 编译器报错，无法编译 |
| 方案 B | 在主项目 `App.xaml.cs` 加 `--stress-test` 命令行入口 | `LivePhotoDiscoveryService.ScanAsync` 在 UI 线程上阻塞，进程卡死 |

最终采用方案 C：**独立控制台程序**，不引用主项目，用 `Process.Start` 直接调 exiftool / ffmpeg。虽然绕过了主项目的 C# 抽象层，但底层执行的 bash 命令完全一致——读取的是同一个文件、调用的是同一个 exiftool.exe / ffmpeg.exe。

> 差异说明：主项目用 `PersistentExifTool`（-stay_open 进程复用，省 200-400ms/次），测试工具用独立进程（每次新建进程）。因此测试中的 exiftool 阶段比真实 app **更慢**，属于保守估计。

### 3.3 编译和运行

```powershell
# 编译（首次需 restore NuGet 包）
cd tests/LivePhotoBoxStressTest
dotnet build -c Release

# 四种测试模式
dotnet run -c Release --no-build -- --dir "<测试目录>" --mode scan      # 仅扫描
dotnet run -c Release --no-build -- --dir "<测试目录>" --mode switch    # 仅exiftool切换
dotnet run -c Release --no-build -- --dir "<测试目录>" --mode timeline  # 仅ffmpeg帧提取
dotnet run -c Release --no-build -- --dir "<测试目录>" --mode full      # 全链路

# 参数说明
#   --dir <path>        测试目录路径（必填）
#   --mode <mode>       测试模式: scan | switch | timeline | full (默认 full)
#   --iterations <n>    迭代次数 (默认 30)
#   --delay <ms>        每次操作间隔毫秒 (默认 50, 0=极限)
```

编译时，csproj 的 `CopyTools` Target 自动从 `LivePhotoBox/Tools/` 复制 exiftool.exe、ffmpeg.exe 等外部工具到输出目录的 `Tools/` 子文件夹。

### 3.5 各测试阶段对应的真实代码

每个测试阶段模拟 EditPage 中的具体操作：

| 测试阶段 | 模拟的真实操作 | 真实代码位置 | 测试实现方式 |
|----------|---------------|-------------|-------------|
| Phase 1 — 文件枚举 | `Directory.EnumerateFiles` | `EditViewModel.ScanDirectoryAsync` | C# `Directory.EnumerateFiles` |
| Phase 2 — XMP/HEIC 检测 | `QuickCheckLivePhoto` + `LivePhotoSplitService.ReadMetadataTextSync` | `EditViewModel.ScanDirectoryAsync` → `LivePhotoDiscoveryService.ScanAsync` (JpegMarkers + HeicTrack) | 并行 `FileStream.Read` 读每个 JPEG 头部 64KB 搜索 XMP 标记（`Container:Directory`、`GCamera:MicroVideo`、`MotionPhoto`），读每个 HEIC 头部 8KB 搜索 `mdat`+`moov` |
| Phase 3 — 文件配对 | `LivePhotoMetadataMatcher.MatchAsync` (CID 匹配) | `EditViewModel.ScanDirectoryAsync` → `LivePhotoDiscoveryService.ScanAsync` (CidMatch) | JPG/HEIC ↔ MOV 按 basename 精确配对（Apple 导出是同名的） |
| Phase 4 — 元数据查询 | `ReadResolutionsAsync` | `EditViewModel.ScanDirectoryAsync` → `ReadResolutionsAsync` | 4 并发 `Process.Start(exiftool -j -ImageWidth -ImageHeight -Make -Model -DateTimeOriginal -ContentIdentifier ...)` 逐一查询每个图片 |
| Phase 5 — 文件切换 | `SelectFile → LoadPropertiesAsync` | `EditViewModel.SelectFile` → `LoadPropertiesAsync` → `PersistentExifTool.SendCommandAsync` | 随机选文件，`Process.Start(exiftool -j ...)` 查询 11 个标签（与 `PropTags` 数组一致），每次查询前取消上一次 |
| Phase 6 — 帧提取 | `TriggerTimelineExtraction → ExtractAllFramesAsync` | `EditViewModel.LoadPropertiesAsync` → `TriggerTimelineExtraction` → `VideoFrameExtractionService.ExtractAllFramesAsync` | `Process.Start(ffmpeg -i <video> -fps_mode passthrough -q:v 3 -f image2 <tmpdir>/frame_%06d.jpg)`，提取全部帧，计数后清理临时目录 |

> Phase 2-6 中所有对 exiftool / ffmpeg 的调用使用的**参数**与主项目中的 `PropTags` 数组和 `ExtractAllFramesAsync` 完全一致。

## 4. 测试结果

### 4.1 目录扫描 (完整四阶段)

| 阶段 | 耗时 | 占比 | 说明 |
|------|------|------|------|
| Phase 1 — 文件枚举 | 3ms | 0.001% | 读文件系统目录项 |
| Phase 2 — XMP/HEIC 标记检测 | 1,375ms | 0.6% | 并行读 4,821 个 JPEG 头部 64KB + HEIC 头部 8KB |
| Phase 3 — JPG↔MOV 配对 | 1ms | ~0% | 2,860 个 MOV 按 basename 建 HashMap，4,821 个图片逐一匹配 |
| Phase 4 — exiftool 元数据 | **243,540ms** | **99.4%** | 4 并发 exiftool 进程，每个图片查询 11 个标签 |
| **总计** | **~244,921ms (4 分 5 秒)** | | |

**结论：exiftool 全量元数据查询占了扫描时间的 99.4%。**

真实代码使用 `PersistentExifTool`（-stay_open 进程复用），每个查询节省 ~150ms 进程启动开销，预计总耗时 ~90-120 秒（1.5-2 分钟），与你描述的"7000 多张照片一分钟多"一致。

### 4.2 exiftool 快速切换 (模拟点击不同文件)

| 测试参数 | 迭代 | 平均 | P50 | P95 | P99 | 最慢 | 异常 |
|----------|------|------|-----|-----|-----|------|------|
| 50ms 间隔 | 50次 | 263ms | 199ms | 267ms | 3,404ms | 3,404ms | 0 |
| 10ms 间隔 | 200次 | 158ms | 172ms | 184ms | 194ms | 197ms | 0 |
| **0ms 间隔** | **100次** | **156ms** | **169ms** | **186ms** | **190ms** | **190ms** | **0** |

**结论：exiftool 查询本身非常稳定。即使 0ms 间隔连跑 100 次也不崩溃。P95 始终在 190ms 以下。**

但真实 app 中，点击一个实况照片不仅触发 exiftool，还触发 ffmpeg 帧提取（见下节），这才是"点一个文件要好几秒"的原因。

### 4.3 ffmpeg 帧提取 (模拟时间轴加载)

| 测试参数 | 迭代 | 平均 | 最快 | 最慢 | 帧数范围 | 异常 |
|----------|------|------|------|------|----------|------|
| 100ms 间隔 | 20次 | **608ms** | 522ms | 695ms | 55-89帧 | 0 |
| 50ms 间隔 (全链路) | 30次 | 640ms | 635ms | 703ms | 56-89帧 | 0 |

**结论：ffmpeg 全帧提取是最大的性能瓶颈。每次点实况照片都要等 500-700ms 提取 55-89 帧视频。如果用户快速切换实况照片，每次切换都要重新触发 ffmpeg。**

## 5. 问题诊断

### 问题 1: 目录扫描慢

| 项目 | 详情 |
|------|------|
| **根因** | `ReadResolutionsAsync` 对目录中**每一个图片文件**运行 exiftool 查询（-ImageWidth, -ImageHeight, -Make, -Model, -DateTimeOriginal 等）。4,821 个文件 × ~50ms/次 = ~240 秒 |
| **现状** | 使用 `PersistentExifTool` × 2 线程池（-stay_open 进程复用），已是最优方案 |
| **改进方向** | ① 考虑只对**可见区域**的文件加载元数据（虚拟化加载） ② 用 Windows Shell API (`Windows.Storage.FileProperties`) 替代 exiftool 读取基础属性（分辨率、日期） ③ 扫描时仅做快速协议检测，元数据延迟到文件被选中时再加载 |

### 问题 2: 切换实况照片响应慢

| 项目 | 详情 |
|------|------|
| **根因** | `TriggerTimelineExtraction` 对实况照片的配对 MOV 运行 ffmpeg 提取**全部视频帧**（`-fps_mode passthrough`），每张照片耗时 500-700ms |
| **现状** | 每帧输出为全分辨率 JPEG（-q:v 3），55-89 帧/视频 |
| **改进方向** | ① 仅提取关键帧（1fps 采样，减少到 ~3-5 帧） ② 首屏只提取封面附近帧，其余惰性加载 ③ 帧缩略图使用更小的分辨率（当前是全分辨率 JPEG 再缩放到 56×56） |

### 问题 3: 快速切换闪退

| 项目 | 详情 |
|------|------|
| **根因** | 待进一步定位。exiftool 测试中 0ms 间隔 100 次无崩溃。推测与以下因素有关：① ffmpeg 进程频繁取消/重启 (0xc000027b 已在代码注释中提到) ② `DispatcherQueue.TryEnqueue` 回调堆积 ③ `PersistentExifTool` 在快速取消+新请求时线程安全问题 |
| **改进方向** | ① ffmpeg 使用 `-stay_open` 类似机制避免频繁进程创建销毁 ② 帧提取增加去抖（debounce）：300ms 内多次切换仅执行最后一次 ③ 增加 `_selectionGeneration` 代数检查覆盖范围 |

### 问题 4: 真实 `LivePhotoDiscoveryService.ScanAsync` 在 UI 线程卡死

| 项目 | 详情 |
|------|------|
| **根因** | 2026-07-20 测试发现：在 `App.OnLaunched` (UI 线程) 中调用 `ScanAsync().GetAwaiter().GetResult()` 导致 UI 线程阻塞，内部 CID 匹配阶段可能尝试 Dispatch 回 UI 线程，形成死锁 |
| **现状** | 正常使用时扫描在后台线程运行，不会触发此问题。但说明了扫描内部有 UI 线程依赖 |
| **改进方向** | 扫描代码中避免对 `DispatcherQueue` 的隐式依赖 |
