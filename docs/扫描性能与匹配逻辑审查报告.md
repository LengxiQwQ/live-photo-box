# 合成、拆分、修复：扫描性能与匹配逻辑审查

审查日期：2026-11-06。审查对象：当前工作区实际源码，HEAD 为 `741b06f1050ad8a32ee85fb5d780b46932d738fc`，包含原有未提交改动。

本次交付是只读代码审查和修复建议，没有修改产品代码，没有启动桌面程序，没有提交、推送或打包。本报告中的“确认”表示已经沿实际调用链核对源码；没有运行大目录计时、界面流畅度或取消实测，因此不提供加速倍数，也不把推断写成实测结果。

## 一、先讲结论

扫描确实存在明显的设计和实现问题，不能简单归结为照片多、电脑慢。

主要原因有四个：

1. 找文件、判断谁和谁配对、完整检查媒体、准备界面显示，混在同一次扫描里做。很多本来可以晚一点做的重活，提前全部做了。
2. 同一个文件被多个环节反复完整读取，已经得到的信息没有在同次扫描中充分复用。
3. vivo 配对会让每张图片逐个尝试所有视频；拆分页也会走这条路，文件数量增加时工作量增长过快。
4. 进度没有覆盖完整流程，结果又集中刷新到界面上，容易出现“等很久没有动静，突然跳一下，快结束时又卡一下”的体验。

“文件名匹配还要检查内部信息”的观察基本属实。但不能直接把所有内部检查删掉：**用户指定图片和视频一起合成，与软件证明它们原本就是一组实况照片，是两件事。** 当前实现没有把这两件事清楚地呈现给用户。

## 二、三个页面现在实际怎么扫

### 合成页

列出目录里的图片和视频 → 逐个完整检查所有文件 → 按所选方式找搭档 → 对选中的图片和视频再做组合检查 → 必要时另查视频格式 → 一次性创建队列和显示列表。

即使选择“文件名”，前面的逐文件完整检查仍照做。同名只决定“先拿哪两个文件来试”，并不保证它们一定能进入队列。

证据：`LivePhotoBox/ViewModels/MergeViewModel.cs:1050–1126`；`LivePhotoBox.Core/Services/LivePhotoMergeScanService.cs:229–361、744–1068`。

### 拆分页

列出文件 → 跑一次 Apple 配对扫描 → 再跑一次 vivo 配对扫描 → 对尚未配对的图片再判断是否包含内嵌视频 → 回到界面后才应用用户选的协议筛选 → 一次性更新队列。

所以只选某一种格式，也不代表底层只检查这一种；尤其 vivo 的逐个尝试会拖累整个拆分扫描。

证据：`LivePhotoBox.Core/Models/LivePhotoDiscoveryModels.cs:153`；`LivePhotoBox.Core/Services/LivePhotoDiscoveryService.cs:71–115、175–253`；`LivePhotoBox/ViewModels/SplitViewModel.cs:1034–1048`。

### 修复页

先固定等待 1 秒 → 一次性列出目录文件 → 找同名组并完整检查单图及组合 → 默认情况下再逐个检查设备范围 → 开始显示正式进度 → 分析方向、缩略图等问题 → 分批把结果加到界面。

部分文件的诊断还会触发同目录候选索引，索引又读取同目录媒体文件。已有索引能复用，但前面的检查结果没有统一接入这份缓存。

证据：`LivePhotoBox/ViewModels/RepairViewModel.cs:875–1009`；`LivePhotoBox.Core/Services/LivePhotoRepairService.cs:646–744`；`LivePhotoBox.Core/Services/RepairBatchContext.cs:46–92`。

## 三、已经确认的问题与建议

### 1. 扫描使用了过重的检查方式——优先修

**问题：** 看起来是在读几个文件信息，实际底层先把整份图片或视频读进内存，再计算整份文件的校验值。校验值相当于文件的“指纹”，用于证明内容没有被换掉。文件越大，这笔开销越明显。

合成的逐文件扫描、双文件组合检查，以及拆分的多个扫描阶段，都走这套底层能力。普通同名图片和视频也可能先分别读一遍，再组合读一遍，之后另查视频。

**为什么改：** 只是为了把候选文件显示到列表，不应该提前完成所有正式处理前的证明工作。

**怎么改：** 将“快速发现候选”和“正式处理前完整检查”分开。扫描先读取合法结构中必要的文件类型、内部配对编号、内嵌视频位置等信息，避免无条件整文件读取和计算指纹；准备执行时再针对实际对象完整检查。不能用任意位置搜索字符串代替结构解析，也不能让快速扫描结果成为改文件的授权。

证据：`LivePhotoBox.Core/Interop/NativeMediaService.cs:398–448`；`LivePhotoBox.Native/src/media/media_inspector.cpp:770–823、3322–3340、3367–3385`。

### 2. vivo 匹配逐张图片尝试所有视频——优先修

**问题：** 当前是外层遍历图片、内层遍历所有视频，每种组合都调用一次完整检查。

例如有 100 张符合候选条件的图片和 100 个可检查的视频，循环可以尝试 10,000 种组合；各增加到 1,000 个，就可以达到 1,000,000 种组合。这是代码循环次数的举例，不是本次实测耗时。

**为什么改：** 文件多一倍，工作量可能变成四倍；而且每次尝试还涉及读取文件。

**怎么改：** 每个文件先读取一次内部配对编号，按“协议、编号、图片或视频角色”建立查找表，只对唯一对应的候选做完整组合确认。重复编号继续报告冲突，不能为了快就随便取第一个。

注意：现有 `NativePairingHint` 接口虽然名字像轻量查询，底层仍先调用完整检查，再读取文件和计算指纹。不能直接接上它就宣称解决性能问题，必须一起改底层读取方式。

证据：`LivePhotoBox.Core/Services/LivePhotoMergeScanService.cs:1380–1443`；`LivePhotoBox.Native/src/media/media_inspector.cpp:5491–5535`。

### 3. 拆分扫描重复检查同一批文件——优先修

**问题：** Apple 和 vivo 两轮分别进入合成扫描服务，都会先检查所有图片和视频；未配对图片之后还会再被检查一次。

**怎么改：** 同一次扫描只建立一份文件信息表，Apple、vivo、单文件识别共同使用。协议筛选尽早参与候选选择：已经确定无关的文件不再做不必要的深入检查；判断不清时保留必要检查。

扫描期间可复用结果，但执行前仍要重新确认文件身份和内容是否变化。

证据：`LivePhotoBox.Core/Services/LivePhotoDiscoveryService.cs:103–115、203`；`LivePhotoBox.Core/Services/LivePhotoMergeScanService.cs:249–293`。

### 4. “文件名匹配”和“严格扫描”的意思没有讲清——优先修

**合成页实际行为：** 普通、没有既有实况绑定的图片与视频，可以按同名形成合成请求，并非所有文件都必须内部编号一致。但已有实况关系的文件仍要求关系有效；同名不保证通过。

**修复页实际行为：** 即使关闭严格扫描，前置同名分组仍会调用底层组合检查，只有识别为 Apple 或旧 vivo 双文件才按组合加入。后面的严格扫描开关是在这之后再比较一次内部编号。因而“关闭严格扫描=只看文件名”的理解与实现不符。

**建议产品规则：**

| 用户目的 | 应呈现的行为 |
|---|---|
| 按同名合成 | 找同目录、同主文件名的图片和视频，展示为“同名合成候选”，标明依据；不冒充已确认的原始实况关系 |
| 找原本的一组实况照片 | 按文件内部配对信息查找，名字不同也可以确认 |
| 修复已有实况照片 | 文件名可帮助找候选，实际涉及关联媒体的修复仍须确认关系；单文件能安全做的修复独立处理 |

对存在相互矛盾的原始绑定信息，不能简单忽略内部信息后继续处理。是否需要额外提供“用户明确指定重新合成”的产品流程，应单独确定，不应暗中放宽现有修复安全规则。

证据：`LivePhotoBox.Core/Services/LivePhotoMergeScanService.cs:928–1040`；`LivePhotoBox/ViewModels/RepairViewModel.cs:919–934、1109–1121`；`LivePhotoBox/ViewModels/SettingsViewModel.cs:606–615`。

### 5. 修复页保留了一段实际不起作用的重新配对流程

**问题：** 扫描后会整理未配对图片和视频，调用 `MatchFromAnalysis`，代码还准备了重新建队列的分支。但是这个方法当前固定返回空配对列表。

**影响：** 从现有调用看，不能依赖这段逻辑在扫描队列中找回改过名字的搭档。底层修复服务另有同目录候选发现能力，不能把它当成界面分组已经正确的证明。这也是界面逻辑与实际处理逻辑脱节的地方。

**怎么改：** 用统一的真实配对服务产生最终关系，界面只显示结果；不要让诊断结果对象承担配对证明。确认接通后移除旧的空方法调用和无效重建分支。

证据：`LivePhotoBox/ViewModels/RepairViewModel.cs:1235–1367`；`LivePhotoBox.Core/Services/LivePhotoMetadataMatcher.cs:208–226`。

### 6. 修复扫描前固定等 1 秒，而且这一秒内取消有收尾漏洞

**问题：** 代码明确写了 `Task.Delay(1000)`。这会让很小的目录也先等一秒。等待后抛出取消异常的位置，在负责恢复 `IsScanning` 的 `try/finally` 之前。

**影响：** 存在点击取消后退出方法、却没有执行正常扫描收尾的路径。这是源码可确认的控制流缺陷；实际按钮是否一直停留在“扫描中”尚未实测。

**怎么改：** 删除无业务必要的固定等待；从进入扫描状态开始，就把所有可能取消或失败的步骤纳入同一套可靠收尾。

证据：`LivePhotoBox/ViewModels/RepairViewModel.cs:844、875–882、1439–1444`。

### 7. 进度条没有覆盖真正耗时的过程

**合成页：** 逐文件检查结束已报告“全部文件完成”，之后才开始配对；vivo 组合尝试期间没有对应的进度报告。

**拆分页：** 两轮配对调用没有把外层进度传进去，外层正式计数在两轮配对之后才开始。

**修复页：** 固定等待、目录列举、前置组合检查和设备筛选都在正式总数进度之前。

**怎么改：** 明确显示“正在查找文件／正在识别／正在配对／正在准备列表”。不知道总量时显示当前阶段和已找到数量，不能拿“第一轮读完”当整个扫描 100%。

证据：`LivePhotoBox.Core/Services/LivePhotoMergeScanService.cs:309–361`；`LivePhotoBox.Core/Services/LivePhotoDiscoveryService.cs:109–115、175–177`；`LivePhotoBox/ViewModels/RepairViewModel.cs:875–1003`。

### 8. 做了界面刷新限速，但限速的位置偏晚

**问题：** 公共进度报告器使用 `Progress<T>`，然后在收到回调后才限制为约每 100 毫秒更新一次。从当前界面线程创建时，逐文件报告已先投递回界面线程，并没有在进入界面队列前合并。

**怎么改：** 后台只更新“最新一份进度”，由界面定时取一次；完成、失败和取消单独可靠投递。避免大量已过期的进度消息占用界面时间。

证据：`LivePhotoBox/ViewModels/WorkViewModelBase.cs:298–325`。

### 9. 扫描结束时仍有一大块工作挤在界面上

**问题：** 合成页在应用结果时逐项创建任务，还同步读取图片拍摄日期。合成和拆分的显示列表刷新都会清空后逐项加入全部结果。拆分建队列时还对不断增长的列表反复查重。

**影响：** 后台检查结束，不等于用户马上能顺畅操作；队列越大，末尾集中工作越明显。具体卡顿时长需要测量。

**怎么改：** 日期等文件读取放后台；用查找表处理去重；界面按有上限的小批次接收结果，避免无变化也整表清空重建。保留列表按可见范围创建显示内容的能力。

证据：`LivePhotoBox/ViewModels/MergeViewModel.cs:1073–1126、1151–1176、367–418`；`LivePhotoBox/ViewModels/SplitViewModel.cs:1049–1069、355–402`。

### 10. 有些纯统计也会随着文件数量重复扩大

**问题：** 拆分发现服务每处理一个文件，都重新数一遍整份列表里有多少实况照片；检查某文件是否已有错误时，也反复遍历诊断列表。合成结束整理未配对项时同样重复搜索诊断。

**怎么改：** 数量在状态变化时加减；按路径建立诊断索引。省掉“处理一项就从头数一遍”的工作。

证据：`LivePhotoBox.Core/Services/LivePhotoDiscoveryService.cs:253、306–310`；`LivePhotoBox.Core/Services/LivePhotoMergeScanService.cs:389–428、592–596`。

### 11. 扫描安排一头串行、一头重复，并发数量不是主要解法

**问题：** 合成及发现服务的重检查逐个等待；修复页配对项分批并发，但独立文件逐个分析。修复的目录索引首次建立又要在一把共享锁下依次检查整个同目录的媒体文件，其他需要索引的任务要等它。

**怎么改：** 先减少检查次数，再按磁盘承受能力安排少量并行任务。一次建好索引并共享，不让每个阶段自己重读。对本地固态硬盘、机械硬盘、移动盘分别测量，不能只把并发数从 4 改成 8。

证据：`LivePhotoBox.Core/Services/LivePhotoMergeScanService.cs:249–293`；`LivePhotoBox/ViewModels/RepairViewModel.cs:1054–1085、1164–1203`；`LivePhotoBox.Core/Services/RepairBatchContext.cs:49–80`。

### 12. 还发现几处会让体验或结果变差的边界问题

| 问题 | 影响 | 建议 |
|---|---|---|
| 修复页一次性递归列文件，异常后返回空列表 | 某个子目录读不了，可能把整轮表现成没有文件，其他正常项也丢失 | 按目录隔离错误，正常文件继续；明确提示哪一处没扫到 |
| 修复入口筛后缀漏了 `.heif`，后面又支持它 | `.heif` 文件进不了后续诊断 | 与公共文件类型表统一 |
| 合成同名多候选时，先偏好扩展名，再把剩余项依次凑对 | 例如同一主文件名有 JPG、JPEG 和一个 MP4，可能选中其中一个，而没有清楚报告歧义 | 同名不是足够的唯一性证明；冲突时明确展示候选，禁止靠顺序决定 |
| 追加少量文件时会把已有未处理队列重新加入扫描 | 拖入几项也可能又等一次大扫描 | 复用同次有效信息，只检查新增项和受影响配对；新文件带来重复编号时仍须重算关系 |
| 底层整文件读取循环没有取消检查 | 大文件或慢盘上点击取消后可能仍要等当前读取和检查结束 | 在读文件分块、长计算和组合尝试之间响应取消，安全收尾 |

证据：`LivePhotoBox/ViewModels/RepairViewModel.cs:884–913`；`LivePhotoBox.Core/Services/LivePhotoMergeScanService.cs:792–876`；`LivePhotoBox/ViewModels/MergeViewModel.cs:1058–1059`；`LivePhotoBox/ViewModels/SplitViewModel.cs:1021–1023`；`LivePhotoBox.Native/src/media/media_inspector.cpp:770–823`。

## 四、哪些已有措施应保留

合成和拆分的主体扫描已经放在后台运行；修复页已经有分批投递和部分并发；公共扫描已有进度限速意图、取消令牌和部分扫描批次隔离；修复服务已有同目录索引。问题是这些措施没有完整覆盖前后各层。

缩略图也可能与扫描争用读取资源，但当前不能把它定为主因：修复页视频缩略图有默认关闭设置，界面也有可见区域分批加载。应在处理重复读取和逐个组合后，对缩略图开关分别计时，而不是先删预览功能。

不能为了提高扫描速度，删除执行前文件身份检查、冲突检查、原件保护或媒体边界检查。优化应减少不必要和重复的工作，并把必要工作放到合适的阶段。

## 五、建议按什么顺序修

1. **先修选项与实际行为。** 讲清同名候选与原始实况关系，处理同名多候选，接通修复页真实配对能力，修复早期取消收尾和目录错误隔离。
2. **再解决主要耗时。** 建立一次扫描共用的信息表，提供真正按需读取的发现能力，替换 vivo 的全组合尝试，去掉固定一秒等待和重复设备预扫。
3. **再解决卡顿和进度。** 进度在进入界面队列前合并；文件读取和队列准备放后台；分批更新列表；统计改为累计。
4. **最后按实测调并发、缓存和缩略图。** 用同一批输入前后比较，分别测首次扫描、重复扫描、追加少量文件和取消，不凭感觉给加速比例。

前三步应以一套共用扫描流程贯通三个页面，避免每个页面各自再写一套相似逻辑。实施时按完整小单元逐项验证，不要求一次重写整个媒体系统。

## 六、怎样证明修好了

| 要验证的事 | 检查办法 |
|---|---|
| 同名合成规则清楚 | 普通同名一图一视频能形成候选；有旧绑定冲突的明确说明；同名多图不靠排序猜配 |
| 真正配对规则可靠 | 改名后内部编号一致仍能找到；编号不同、缺失或重复不误认原始配对 |
| 扫描没有重复干重活 | 记录每阶段文件打开次数、读取字节数、完整检查次数、组合尝试次数，核对随文件数的增长方式 |
| 大目录明显改善 | 固定 100、1,000、10,000 级规模分别比较普通媒体、Apple、vivo、混合目录；记录文件体积与存储位置，测首次和重复扫描 |
| 界面流畅 | 记录从点击到首次显示、扫描完成到列表可操作的时间；用户实际滚动、切页和点击取消，不能用 CLI 代签 |
| 取消有效 | 在启动后 1 秒内、列目录、读大文件、配对和列表更新各阶段取消，确认状态能恢复、旧消息不污染新扫描 |
| 外部坏文件不拖垮正常项 | 含损坏文件、读不了的子目录、消失文件、重复候选时，正常项继续且错误明确 |
| 处理安全没退步 | 扫描后替换文件或新增冲突候选，正式处理仍重新验证并阻止危险操作；原件不变 |

上述是建议的修复验证范围，本次没有执行这些性能及 GUI 验证。没有启动后续实施任务。
