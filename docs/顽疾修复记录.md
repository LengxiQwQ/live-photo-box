## 1. WinUI 3 ListView 点击下压偏移动画

**日期**: 2026-07-06  
**影响范围**: `KeyPhotoPage` 文件列表  
**严重程度**: 高（视觉体验核心缺陷）

### 症状

点击 ListView 中的文件卡片时，卡片内容会往右下角偏移约 2-4 像素，像是被"按下去"了一样。松开鼠标后恢复原位。用户要求完全消除此效果，只保留选中态的颜色变化（边框+底色）。

### 试错过程

共尝试了 **7 种方案**，全部未能解决问题：

| # | 方案 | 结果 |
|---|------|------|
| 1 | `ListViewItem` 上设 `Transitions="{x:Null}"` | 无效。下压动画不走 Transitions 系统 |
| 2 | 覆盖 ControlTemplate 的 VisualState，把 `Pressed`/`PointerOverPressed` 设为空 | 无效。动画不在 VSM 状态里 |
| 3 | 换成 `ItemsControl` 替代 `ListView` | 动画消失了，但也失去了 `SelectionMode="Single"` 的内置选中逻辑，需要手动实现 |
| 4 | 用 `Border.Child` 的 `PointerPressed` + `e.Handled = true` 拦截事件 | 点击选中功能被吃掉了（事件被拦截未能路由到 ListViewItem） |
| 5 | `SelectionMode="None"` + 纯手动管理选中 | 过于复杂，不符合 WinUI 惯例 |
| 6 | 在 code-behind 里移除 `ListViewItem` 上的所有 `Transition` | 依然无效。`ListViewItemPresenter` 是 native C++/WinRT 类型，动画在 compositor 层执行，无法从托管代码触及 |
| 7 | 网上搜索 WinUI 社区方案 | WebSearch API 持续报错（`gemini-2.0-flash` 400），无法获取在线资料 |

### 根因定位

转折点：用户观察到点击前 `BorderThickness="0,0,0,0"`，点击后变成了 `"2,2,2,2"`。

**真正的根因不是动画系统，而是布局偏移。**

当 `BorderThickness` 从 0 变为 2 时：
- Border 控件在内容区域外围多出 2px 的边框空间
- 边框**向内侵占**内容区域（WinUI Border 的默认 box model）
- 内容实际可用空间减少 4px（左右各 2px、上下各 2px）
- 视觉上表现为：文字、缩略图等全部内容向右下偏移 2px

这和 WinUI 内置的 `PointerDownThemeAnimation` 效果非常相似（那个动画也是做轻微的 scale/offset），所以一直被误认为是动画问题。

### 最终方案

**双重修复**：

#### 第一层：剥离 ListViewItem 模板
```xml
<Setter Property="Template">
    <Setter.Value>
        <ControlTemplate TargetType="ListViewItem">
            <ContentPresenter x:Name="ContentPresenter"/>
        </ControlTemplate>
    </Setter.Value>
</Setter>
```
- 无 Grid、无 VSM、无 Transitions、无 ListViewItemPresenter
- `ListViewItem` 变成纯粹的透明容器，不再有任何内置动画能力

#### 第二层：BorderThickness 恒定 2px（核心修复）
```csharp
private void UpdateCardVisual(Border card, bool isSelected, bool hovered, bool pressed)
{
    // 边框厚度始终 2px，只改颜色——彻底消除布局偏移
    card.BorderThickness = new Thickness(2);
    card.BorderBrush = isSelected ? _selectedBorder : _transparent;
    // ...
}
```

关键理念：
- **不改变尺寸，只改变颜色**
- 未选中时：`BorderBrush = Transparent`（2px 透明边框，不可见但占据空间）
- 选中时：`BorderBrush = 强调色 88%`（2px 可见边框，空间不变）
- 任何时候 BorderThickness 都是 `Thickness(2)`，内容区域从不变化

### 经验教训

1. **布局偏移 vs 动画效果很难区分。** 当用户说"按下后有位移"，首先检查是否有尺寸/边距/边框厚度在状态切换时发生变化。
2. **WinUI 的 Border 向内侵占内容空间。** 这是 WPF/WinUI 的标准 box model，和 Web 的 `box-sizing: border-box` 不同。
3. **ListViewItemPresenter 是 native 层控件**，托管代码无法完全控制其动画行为。如果某些效果无论如何都关不掉，考虑剥离模板到裸 ContentPresenter。
4. **先检查数据，再怀疑框架。** 7 种方案都在假设"框架动画关不掉"，实际是自写代码里 BorderThickness 变了一下。

### 涉及文件

- `Views/KeyPhotoPage.xaml` — ItemContainerStyle 剥离模板 + DataTemplate 中的 Border 定义
- `Views/KeyPhotoPage.xaml.cs` — `UpdateCardVisual` 方法（核心修复）+ 指针事件处理 + 虚拟化生命周期管理

## 2. WinUI 3 ScrollBar 鼠标离开后自动缩为细条

**日期**: 2026-07-07  
**影响范围**: `KeyPhotoPage` 文件列表滚动条 + 时间轴滚动条  
**严重程度**: 中（视觉一致性缺陷，滚动条粗细闪烁影响操作手感）

### 症状

滚动条默认显示为细条（竖 8px / 横 8px），鼠标悬停时变粗（12px），移开后 167ms 内缩回细条。用户要求滚动条**始终保持粗态**，不要随着鼠标位置切换。

### 试错过程

| # | 方案 | 结果 |
|---|------|------|
| 1 | `ScrollViewer` 上设 `SmallScrollThumbScale=1` + `SmallScrollThumbOffset=0`（XAML 资源覆盖） | 无效。这两个资源键在 WinUI 3 模板中**根本不存在**，是 UWP 的遗留产物 |
| 2 | 代码里设 `ScrollBar.IndicatorMode = ScrollingIndicatorMode.TouchIndicator` | 无效。`TouchIndicator` 切换到的是 2px 细线触控指示器，比默认还细 |
| 3 | 运行时遍历可视树找 ScrollBar，反复设 `GoToState("Expanded")` | 无效。C++ 层会在鼠标事件触发时立刻切换回去，形成闪烁 |
| 4 | 覆盖 `ScrollBarVerticalThumbMinWidth` 等 ThemeResource | 部分有效但不足。元素的默认值用了 `ThemeResource`（可覆盖），但 **VisualState 的 Storyboard 动画关键帧里用了 `StaticResource`**，值已在模板加载时 baked in 为 8。动画执行后仍然缩回 8px |

### 根因定位

深入阅读 WinUI 3 SDK 的 `generic.xaml`（`Microsoft.WinUI\Themes\generic.xaml` 第 31071-31626 行），发现了 ScrollBar 的完整内部结构。

**ScrollBar 模板有两个 VisualStateGroup 控制视觉：**

| 组 | 作用 | 状态 | 谁在控制 |
|----|------|------|---------|
| `ScrollingIndicatorStates` | 选展示模式 | `MouseIndicator`(默认) / `TouchIndicator` / `NoIndicator` | `IndicatorMode` 属性 |
| **`ConsciousStates`** | **控制粗细** | **`Expanded`** ↔ **`Collapsed`** | **ScrollBar C++ native 层** |

默认资源值：
```
ScrollBarSize                    = 12   (展开态宽度)
ScrollBarVerticalThumbMinWidth   = 8    (收起态宽度)
ScrollBarThumbOffset             = 2    (收起态偏移)
ScrollBarContractDuration        = 0:0:0.167
```

**`ConsciousStates` 的状态切换完全由 C++ native 层控制**（鼠标进入→Expanded，离开→Collapsed），托管代码发出 `VisualStateManager.GoToState` 调用后会被 C++ 层立刻覆盖。

### 最终方案

**完全替换 ScrollBar 模板**——将 `ConsciousStates` 视觉状态组从模板中移除，同时把所有元素的默认属性值改为展开态。

核心原理：
```
ScrollBar C++ 层:
  mouse enter → GoToState("Expanded")   → 找不到 ConsciousStates 组 → 无操作
  mouse leave → GoToState("Collapsed")  → 找不到 ConsciousStates 组 → 无操作

元素始终使用 ControlTemplate 中的默认值（展开态），不响应任何状态切换。
```

**模板改动清单：**

| 修改项 | 旧值 | 新值 | 原因 |
|--------|------|------|------|
| `ConsciousStates` VSM 组 | 完整保留（3 状态 + 过渡动画） | **移除整个组** | C++ 层无法再切换粗细 |
| `VerticalThumb.Width` | `ScrollBarVerticalThumbMinWidth`(8) | `ScrollBarSize`(12) | 默认即粗 |
| `VerticalThumbTransform.X` | `ScrollBarThumbOffset`(2) | `0` | 居中而非偏置 |
| `HorizontalThumb.Height` | `ScrollBarHorizontalThumbMinHeight`(8) | `ScrollBarSize`(12) | 横向滚动条默认粗 |
| `HorizontalThumbTransform.Y` | `ScrollBarThumbOffset`(2) | `0` | 横向居中 |
| 所有 Track / Button `Opacity` | `0` | `1` | 轨道和滚动按钮始终可见 |
| Thumb `Opacity` | `0`(默认) / `1`(MouseIndicator 状态) | `1` | 无需等 MouseIndicator 状态设置 |

**实现方式：**
- 在 `Page.Resources` 中定义 `AlwaysThickScrollBarStyle`（`BasedOn="{StaticResource DefaultScrollBarStyle}"`）
- 添加隐式 `<Style TargetType="ScrollBar" BasedOn="{StaticResource AlwaysThickScrollBarStyle}" />` 使页面内所有 ScrollBar 自动应用
- `ForceScrollBarsAlwaysThick()` 简化——不再需要设置 `IndicatorMode`

### 经验教训

1. **`StaticResource` vs `ThemeResource` 是关键区别。** `StaticResource` 在模板加载时 baked in，运行时无法覆盖。如果 Storyboard 动画关键帧用了 `StaticResource`，覆盖 ThemeResource 定义是无效的。
2. **UWP 扩展资源 ≠ WinUI 3 扩展资源。** `SmallScrollThumbScale` 在 UWP 中存在，在 WinUI 3 中被移除。不要假设 UWP 的知识直接适用。
3. **GoToState 的访问权不等于控制权。** 可以通过 `VisualStateManager.GoToState` 调用 ScrollBar 的状态，但 native 层会立即切回。想控制就替换模板。
4. **阅读 SDK 源码是最可靠的手段。** 当官方文档和网络搜索都无法提供答案时，`C:\Users\<user>\.nuget\packages\microsoft.windowsappsdk.winui\<version>\...\generic.xaml` 里能找到一切。
5. **同一个项目里两次用到了"Remove VSM group"模式。** ListView 和 ScrollBar 都是因为 C++ native 层控制视觉状态无法覆盖，最终都通过移除/绕过框架控制的 VSM 组解决。这是 WinUI 3 设计的一个可预测模式：**native 层驱动状态机，托管代码无法介入 → 替换模板移除状态组**。

### 涉及文件

- `Views/KeyPhotoPage.xaml` `Page.Resources` — 完整的 `AlwaysThickScrollBarStyle` 自定义模板（~180 行）
- `Views/KeyPhotoPage.xaml.cs` — `ForceScrollBarsAlwaysThick()` 简化为仅设置 `ScrollBarVisibility`

## 3. 非打包模式下语言切换完全失效

**日期**: 2026-07-18  
**影响范围**: 全局 UI 语言（所有页面 `x:Uid` + `ResourceService` 代码路径）  
**严重程度**: 高（非打包模式=便携版+安装版用户无法切换语言）

### 症状

非打包模式下，在设置里切换语言（如系统中文 → 英文），**只有 NavigationView 内置的 Settings 标签变了**，其他所有文字都是中文。即使重启应用也无效。

### 试错过程

共尝试了 **8 种方案**，全部未能解决根本问题：

| # | 尝试 | 结果 |
|---|------|------|
| 1 | 去掉 `if (App.IsPackaged)` 守卫，始终调用 `Windows.Globalization.ApplicationLanguages.PrimaryLanguageOverride` | ❌ 旧 API 在非打包下始终抛 `InvalidOperationException: Operation is not valid due to the current state of the object.` |
| 2 | 通过 `makepri dump` 检查 `resources.pri` | ✅ PRI 文件包含完整的 en-US 和 zh-Hans 资源，资源编译无问题 |
| 3 | 调用 Win32 `SetProcessPreferredUILanguages` 设置进程级 MUI 语言 | ❌ API 返回成功，但 MRT Core 不使用进程 MUI 做资源语言解析；官方文档确认"非打包应用使用系统显示语言而非用户首选语言列表" |
| 4 | 在 `[ModuleInitializer]` 中 WinAppSDK 加载前调用 `SetProcessPreferredUILanguages` | ❌ MRT Core 仍使用系统显示语言，进程 MUI 对 MRT Core 无效 |
| 5 | 改造 `ResourceService` 使用共享 `ResourceContext` + 显式 Language 限定符 | ✅ 代码路径（`GetString()`）有效，但 XAML `x:Uid` 走的是框架内部 ResourceLoader，不走此路径 |
| 6 | `.csproj` 中 `EmbeddedResource` → `PRIResource` | ❌ SDK 自动发现 .resw 文件，显式声明导致重复项错误 |
| 7 | 删除 `.csproj` 中重复的 ItemGroup | ✅ 编译通过，但语言切换仍无效 |
| 8 | 诊断输出验证 | 关键发现：显式 `ResourceContext.QualifierValues["Language"] = "en-US"` 可解析英文资源，但**默认 ResourceContext** 返回的是 `"zh-Hans-CN;en-US;"`（系统语言在前），候选人匹配时前置命中 zh-Hans |

### 根因

**WinAppSDK 1.6 引入了一个全新的 API，在完全不同的命名空间下：**

| API | 命名空间 | 非打包下 |
|-----|---------|:---:|
| 旧 `PrimaryLanguageOverride` | `Windows.Globalization` | ❌ `InvalidOperationException` |
| **新 `PrimaryLanguageOverride`** | **`Microsoft.Windows.Globalization`** | ✅ **可用** |

旧 API（`Windows.Globalization`）是 UWP 时代产物，底层依赖包标识做持久化和权限检查，非打包下直接抛异常。

新 API（`Microsoft.Windows.Globalization`）是 WinAppSDK 团队为了解决非打包应用语言切换问题专门加的，通过 `microsoft/WindowsAppSDK PR #4181` 和 `#4523` 在 1.6 experimental2 中引入，**使用完全不同的底层存储机制，不依赖包标识**。

参考：
- [microsoft/WindowsAppSDK#1687](https://github.com/microsoft/WindowsAppSDK/issues/1687) — 原始 issue 报告
- [microsoft/WindowsAppSDK#6118](https://github.com/microsoft/WindowsAppSDK/issues/6118) — 不跨会话持久化（已知限制，我们通过 `AppSettingsService` JSON 兜底）
- [microsoft/WindowsAppSDK#5335](https://github.com/microsoft/WindowsAppSDK/issues/5335) — 无法清空覆盖（设为 "" 抛异常）
- [官方文档](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.globalization.applicationlanguages.primarylanguageoverride)

### 修复

**文件**: `Services/LanguageService.cs`，`ApplyLanguageOverride(string languageTag)` 方法

```csharp
// ❌ 旧代码（抛异常）：
if (App.IsPackaged)
{
    try
    {
        Windows.Globalization.ApplicationLanguages.PrimaryLanguageOverride = languageTag;
    }
    catch { }
}

// ✅ 新代码（打包+非打包都可用）：
try
{
    Microsoft.Windows.Globalization.ApplicationLanguages.PrimaryLanguageOverride = languageTag;
}
catch (Exception ex)
{
    System.Diagnostics.Debug.WriteLine(
        $"[LivePhotoBox] Failed to set PrimaryLanguageOverride: {ex.Message}");
}
```

**改动总结**：
1. 命名空间：`Windows.Globalization` → `Microsoft.Windows.Globalization`（关键！）
2. 去掉 `if (App.IsPackaged)` 守卫
3. catch 改为记录日志而非静默吞掉

### 已知限制

1. **[#6118](https://github.com/microsoft/WindowsAppSDK/issues/6118)**：新 API 不跨会话持久化。**兜底方案**：`AppSettingsService`（JSON 文件）持久化 `LanguageIndex`，启动时重新调用 `ApplyLanguageOverride`
2. **[#5335](https://github.com/microsoft/WindowsAppSDK/issues/5335)**：设置为 `""` 抛异常，无法清空覆盖。"跟随系统"模式通过将覆盖锁定为解析后的系统语言来实现，而非清空覆盖

### 经验教训

1. **WinUI 3 的 API 有两个命名空间体系**：`Windows.*`（UWP 遗产）和 `Microsoft.Windows.*`（WinAppSDK 原生）。API 名字相同但行为不同，遇到非打包兼容性问题时优先搜 `Microsoft.Windows.*` 命名空间下是否有新版本。
2. **GitHub Issues 是最好的文档**：官方文档没写 `Windows.Globalization.ApplicationLanguages` 在非打包下不可用，但 GitHub Issues 里有完整讨论和替代方案。
3. **makepri dump 是诊断利器**：当资源加载行为异常时，先 dump PRI 文件确认资源是否存在、语言限定符是否正确，排除"资源没编译进去"的可能性。
4. **`ResourceContext.QualifierValues` 显式指定 vs 默认上下文**：显式指定语言可以绕过很多 MRT Core 的复杂性，但无法影响 XAML `x:Uid`。`x:Uid` 的唯一控制入口是 `PrimaryLanguageOverride`。

### 涉及文件

- `Services/LanguageService.cs` — `ApplyLanguageOverride(string languageTag)` 方法，核心里仅改一行命名空间
- `App.xaml.cs` — `ApplyLanguageSetting()` 启动时调用，从 `AppSettingsService` 读取持久化的 LanguageIndex 并重新设置覆盖

## 4. 非打包模式下启动崩溃（0xc000027b）

**日期**: 2026-07-02  
**影响范围**: 全局（便携版 + 安装版所有用户）  
**严重程度**: 高（非打包模式完全无法启动）

### 症状

非打包模式（便携版 zip / Inno Setup 安装版）启动时立即崩溃，退出码 `0xc000027b`，异常为 `System.InvalidOperationException`（位于 `WinRT.Runtime.dll`）。打包模式（MSIX）正常。

### 背景

项目使用 WinAppSDK 1.8 + .NET 9 + SelfContained 部署，需要同时支持两种模式：

| 模式 | 用途 | 特征 |
|---|---|---|
| MSIX 打包 | Microsoft Store 发布 | 有包标识，App Container 沙箱 |
| Unpackaged（非打包） | GitHub Release + 开发调试 | 无包标识，普通 exe 直接运行 |

### 试错过程

问题分两个层面，且**缺一不可**：

| # | 尝试 | 结果 |
|---|------|------|
| 1 | 直接启动非打包 exe | ❌ 0xc000027b，WinRT 类型系统找不到 DLL |
| 2 | 加上 `WindowsAppSdkUndockedRegFreeWinRTInitialize=true` | ❌ 引导文件生成了，但代码里 `ApplicationData.Current` 等 API 仍然抛异常 |
| 3 | 加上 Bootstrap + 逐一定位抛异常的 WinRT API | ✅ 两个层面都修好后，非打包模式正常工作 |

### 根因定位

**这不是项目的 Bug，是 WinUI 3 的架构级设计。** Windows App SDK 默认假设应用运行在 App Container 中且拥有包标识，非打包支持是后来补的。

**第一层：WinRT 运行时找不到 DLL（框架级）**

```
打包版：  系统 → PackageGraph → 框架包声明 → 找到 DLL ✓
非打包：  系统 → ??? → 找不到 → 0xc000027b ✗
```

自包含部署把所有 WinAppSDK DLL 打包在 exe 同目录，但 WinRT 类型系统默认不找那里。必须手动告诉 WinRT "DLL 在我自己目录里"。

**第二层：应用代码调用了需要包标识的 WinRT API（应用级）**

| API | 作用 | 为何 unpackaged 炸 |
|---|---|---|
| `Windows.Storage.ApplicationData.Current` | 应用数据存储 | 依赖包标识做数据隔离 |
| `Windows.ApplicationModel.Package.Current` | 获取包信息/版本号 | 没有包当然没有 Package |
| 部分 WinRT 类的静态属性激活 | 语言/系统设置等 | 无包环境下类型激活链路可能失败 |

### 最终方案

#### 修复 1：让 WinRT 能找到自包含 DLL

**`LivePhotoBox.csproj`**（第 27 行）：
```xml
<WindowsAppSdkUndockedRegFreeWinRTInitialize>true</WindowsAppSdkUndockedRegFreeWinRTInitialize>
```

**`Services/WindowsAppSdkBootstrap.cs`** — 使用 `[ModuleInitializer]` 在所有代码之前执行：
```csharp
[ModuleInitializer]
internal static void Initialize()
{
    // 警告：此方法中绝对不能引用任何 WinRT 投影类型！
    Environment.SetEnvironmentVariable(
        "MICROSOFT_WINDOWSAPPRUNTIME_BASE_DIRECTORY",
        AppContext.BaseDirectory);          // 告诉 WinRT 去哪找 DLL
    WindowsAppRuntime_EnsureIsLoaded();    // 强制加载，触发 SxS 重定向
}
```

关键点：
- `[ModuleInitializer]` 保证在所有代码之前运行
- 只做两件事：设环境变量 + 加载 DLL
- **绝对不能**有 `using Microsoft.UI.Xaml` 等 WinRT 引用
- **绝对不能**调用 `TryInitialize`（那是给非自包含应用找系统框架包用的，会跟本地 DLL 冲突）

#### 修复 2：给需要包标识的 API 做双模式兜底

**模式 A：API 有包/无包行为完全不同 → 双路径**

`Services/AppSettingsService.cs` 完整重写：
- 打包模式：`ApplicationData.Current.LocalSettings`（系统 API）
- 非打包模式：JSON 文件 fallback（`AppContext.BaseDirectory\appsettings.json`）

**模式 B：API 功能非关键 → try-catch 静默降级**

`Services/LanguageService.cs` 中 WinRT 调用加保护：
```csharp
try { Windows.Globalization.ApplicationLanguages.PrimaryLanguageOverride = languageTag; }
catch (InvalidOperationException) { /* 非打包模式：使用默认语言 */ }
```

**模式 C：已知有风险但已有 try-catch → 确认安全**

- `Services/LogService.cs` — 日志目录解析已有 try-catch 兜底
- `App.xaml.cs` — AppVersion 属性已有 try-catch 兜底

### 经验教训

1. **`[ModuleInitializer]` 里不要引用 WinRT 类型。** 会触发 WinRT 投影 DLL 过早加载，导致类型激活失败损坏 WinRT 状态。
2. **自包含应用不要调 `TryInitialize`。** `MddBootstrapInitialize2` 是去系统注册表里找已安装的框架包，自包含应用的 DLL 在自己目录里，调它要么返回 `0x80670016`（找不到），要么找到系统版本后和本地版本冲突导致 `0xc0000602`（fail fast）。
3. **`ApplicationData` 需要包标识。** 所有用到 `ApplicationData.Current` 的地方都要 try-catch 并准备 JSON fallback。
4. **写新代码时检查 WinRT API。** 调用任何 `Windows.*` 命名空间下的 API 时，确认是否需要包标识，不确定就加 try-catch 兜底。
